一、题目一：长度最小的子数组

209. 长度最小的子数组力扣原题 ↗

题目要求

输入正整数数组nums和正整数target。在nums中选择一段连续、非空的子数组，使它的元素总和大于或等于target。

返回满足条件的最短长度；如果整份输入里没有满足条件的子数组，返回0。子数组必须保留原来的相邻关系，不能从不同位置挑出几个数拼成一段。

示例1

输入：target = 7, nums = [2,3,1,2,4,3]

输出：2

末尾的[4,3]之和为7，长度为2；没有单个元素达到7，因此最短长度是2。

示例2

输入：target = 4, nums = [1,4,4]

输出：1

任选其中一个4就已经达标。

示例3

输入：target = 11, nums = [1,1,1,1,1,1,1,1]

输出：0

全部元素相加也只有8，不存在达标区间。

约束条件

  • 1 ≤ target ≤ 10⁹
  • 1 ≤ nums.length ≤ 10⁵
  • 1 ≤ nums[i] ≤ 10⁴

进阶要求：完成O(n)解法后，还可以尝试实现O(n log n)的解法。

做完无重复字符的最长子串后，我继续尝试用左右边界维护一个连续区间。不过，209要找的是和已经达标时，长度最短的窗口。这会改变收缩窗口的目的，也会改变记录答案的位置。

1.1 从枚举区间到保留一个可以继续修改的窗口

先暂时只用数组和循环考虑。最直接的办法是选定一个起点，再逐个加入右边的数，直到总和达到target。因为所有数都是正数，对于这个起点而言，第一次达标就已经得到最短候选，再往右延长只会增加长度。然后换一个起点，重新做相同的事情。

这个办法能够求出答案，不过相邻起点会反复经过同一批元素。以target=7、nums=[2,3,1,2,4,3]为例，从下标0出发，依次得到2、5、6、8，第一次达标的是[2,3,1,2]；接着从下标1开始时，3、1、2这些刚加过的数又需要重新参与计算。即使每次都用一个变量累加，最坏也要枚举接近n(n+1)/2个位置组合，时间仍为O(n²)。

因此可以进一步考虑：换起点时能否保留已有的区间和，只减去离开的元素，而不从头重算？上面的窗口总和为8，删去开头的2后，剩下[3,1,2]，总和直接变成6。此时不够7，再把右边的4加入，就得到总和10。这些变化只涉及两个边界，不需要重新遍历中间的元素，这就是滑动窗口能节省的工作。

但只会更新总和还不够，还需要决定什么时候移动哪一端。这里可以分成两种情况：和不够时，加入右边的新元素；和已经够时，先把当前长度作为候选，再尝试删除左端，看看能否更短。正整数使这两个操作的方向很明确：加入会使和增加，删除会使和减少。

第3题需要先排除重复，恢复合法窗口，再记录长度；209则要在窗口达标时尝试缩短，每次移除左端之前，都有一个合法候选需要检查。两个题都在移动边界，但检查条件和记录答案的顺序需要重新从题意推出来。

1.2 第一版的末尾窗口漏检

我原先把扩展和收缩拆成了两部分：先检查手里已有的窗口，和已经够了就缩短；不够时，再把右边的新元素加进来。单看一次循环，这个顺序似乎也能继续向前走，所以写的时候没有把“最后一次加入后还会不会再检查”单独考虑进去。问题就出在这里：加入后的检查实际被留给了下一轮，而最后一次扩展之后已经没有下一轮了。

具体看代码时，先明确它使用的区间约定：right表示右开边界，total对应nums[left:right]，窗口长度为right-left。也就是说，下标right处的数还没有加入。关于这种右端不包含的范围，可以回看切片的起止下标。

展开末尾漏检的错误逻辑
python
def min_subarray_bug(target: int, nums: list[int]) -> int:
    left = right = total = 0
    best = len(nums) + 1
    while right < len(nums):
        while total >= target:
            total -= nums[left]
            left += 1
            # 该式恰等于收缩前长度，不是独立的加1错误。
            best = min(best, right - left + 1)
        total += nums[right]
        right += 1
    return best if best != len(nums) + 1 else 0

以target=7、nums=[7]为例，开始时和为0，不会进入收缩循环。随后把7加入，right变成1，已经等于数组长度，外层循环直接结束。刚加入的7还没有接受达标检查，答案就被返回了，所以得到0。

执行位置窗口与总和接下来发生什么
进入第一轮空窗口，total=0不满足收缩条件
加入nums[0]窗口为[7]，total=7right增加到1
再次检查外层循环right已经等于n退出，达标窗口没有被检查

这组只有一个元素的输入，把问题缩小到了最明显的一步：扩展成功并不等于已经处理了扩展后的结果。修正时需要把加入元素和检查新窗口放在同一轮，保证最后一次加入也有机会更新答案。

同样的问题也出现在[2,3,1,2,4,3]中：最后加入3后，本来还能把窗口缩成[4,3]，第一版却提前结束，留下的最短长度是3。

代码里的right-left+1也需要结合它出现的位置看。这里是先把left加1，再计算长度，因此数值恰好等于收缩前的right-left_old。这条算式本身没有多算一位，不过它使用的是修改后的下标，表达修改前的长度，读起来比较绕。把记录放回删除之前，区间含义就一致了。

1.3 改成先加入，再连续收缩达标窗口

下面将窗口统一为闭区间[left,right]，每轮先加入nums[right]。只要和仍然达到目标，就记录长度、删去左端，再检查是否还能缩短。

python
def min_subarray_window(target: int, nums: list[int]) -> int:
    left = total = 0
    best = len(nums) + 1
    for right, value in enumerate(nums):
        total += value  # 先加入当前元素，使闭区间[left,right]状态完整。
        while total >= target:
            best = min(best, right - left + 1)  # 在合法时记录，之后再删。
            total -= nums[left]
            left += 1  # 正数保证删前缀使和变小，尝试更短的达标窗口。
    return 0 if best == len(nums) + 1 else best

这些代码按解题思路整理成了独立函数，便于直接运行；错误版本也保留了对应的判断顺序。放入力扣时，可将正确函数体放到Solution.minSubArrayLen中。

展开逐步演示

在最后一个右端right=5处，依次会遇到[1,2,4,3]、[2,4,3]和[4,3]，它们的和分别为10、9、7，长度分别为4、3、2。再删去4后只剩3，才停止收缩。先记录当前合法窗口，再移动左端，就不会把长度2的答案跳过去。

1.4 起点无需回退的依据：正整数与最短窗口

这里起作用的是题目中的正整数条件。右端加入一个数，和增大；左端移出一个数，和减小。因此，固定右端后，可以不断缩短达标窗口，直到第一次不达标。

一个起点被移出前，已经记录过以它开始、以当前右端结束的合法窗口。将来右端只会更靠后，继续使用这个起点得到的窗口更长，不会改善最短答案。所以左边界可以一直向前，不需要回退重新尝试这些起点。

这也解释了内层为什么是while：一次扩展后，可能有多个起点都能形成达标窗口，只收缩一次会留下更短的候选没有检查。

还可以反过来检查停止条件。假设当前窗口已经不达标，继续删去左边的正数只会让和更小，所以此时所有“右端不变、左端继续向右”的候选都不用再试。等右端加入新元素后，才重新有可能达标。这样，扩展和收缩各自什么时候继续、什么时候停止，都有了依据。

循环不变量是：每次加入新右端之前，total准确表示此前尚未排除的窗口；所有已经移出的起点，都有一个已检查过、且不会被未来更长窗口改善的候选。这说明左端一直前进并没有随意漏掉起点。能够安全排除旧起点，才是把两层枚举减少到一次扫描的关键。

1.5 209的时间、空间复杂度与边界

右端读取每个元素一次，最多移动n次；左端也只会从0移到n，每个元素至多被删除一次。虽然代码中有两层循环，收缩循环的总次数仍不超过n，因此总时间复杂度为O(n)，额外空间为O(1)。代码只保存边界、和与答案，没有为每个窗口创建切片。

best=n+1表示还没找到答案，最后转为题目要求的0。单个元素就达标时应返回1；整个数组的和仍不够时返回0；最优窗口位于数组末尾时也必须检查，[7]就是很直接的测试。

如果数组允许负数，删除左端可能使和增大，未达标时继续扩展也可能让和减小，上面的移动证明就不成立了。例如target=3、nums=[1,-1,3]，直接照搬这段代码会停在长度3，漏掉末尾的[3]。这种最短且和至少达标的问题，不能仅凭“有前缀和和哈希表”就套用等值查询；后面的560前缀和笔记处理的是另一种条件。

题目还给出了O(n log n)的进阶方向。可以先建立前缀和P；由于nums全为正数，P严格递增。固定起点left后，寻找最早满足P[end]≥P[left]+target的end，就得到该起点的最短达标区间，这次查找可以使用二分搜索。对n个起点分别二分，总时间为O(n log n)，前缀表占O(n)空间。它把“每个起点向右找终点”改成了有序表查询，而滑动窗口进一步利用了不同起点之间可以连续推进的关系。这里先保留两条思路的联系，前缀和的含义可以在关联文章中展开理解。

二、题目二：找到字符串中所有字母异位词

438. 找到字符串中所有字母异位词力扣原题 ↗

题目要求

输入两个字符串s和p，找出s中所有与p互为字母异位词的连续子串，返回这些子串在s中的起始下标，下标从0开始。结果列表的排列顺序没有要求。

字母异位词可以调整字母的排列顺序，但每种字母的出现次数必须相同。因此候选子串的长度也必须等于p的长度。

示例1

输入：s = "cbaebabacd", p = "abc"

输出：[0,6]

起点0对应cba，起点6对应bac，两段都各有一个a、b、c。

示例2

输入：s = "abab", p = "ab"

输出：[0,1,2]

三个长度为2的子串依次是ab、ba、ab，全部满足要求；这些子串允许重叠。

约束条件

  • 1 ≤ s.length, p.length ≤ 3 × 10⁴
  • s和p的字符都属于小写英文字母a～z。

这次需要比较的是字符组成。最初我先考虑把字符串变成集合，看看窗口与p里包含的字符是否一样。这个办法能够忽略排列顺序，但字符重复时也会被集合合并，所以接着又需要考虑：重复的次数应该保存在哪里，保存下来以后，又怎样比较两个窗口？

这样就从“有没有这个字符”，转到了“每个字符分别出现几次”。频次字典同时保存字符和数量，而两个字典是否相等，正好可以用来判断这些数量有没有一一对应。

字母异位词要求各字符的出现次数相同，排列顺序可以不同。aab与abb都包含a和b，集合相同，但前者有两个a，后者有两个b，所以只记录“出现过哪些字符”还不够。

用频次字典保存字符→次数后，aab对应{a:2,b:1}，abb对应{a:1,b:2}，缺少的区别就保留下来了。Python的Counter(p)可以直接统计p中的字符；它属于计数映射，下面只用到创建、按键读取和比较，不需要先记全它的API。

2.1 固定窗口长度，再复用相邻子串的字符统计

异位词可以交换顺序，但不能增加或删除字符。因此，如果p长m，每个候选的长度就已经确定为m。无需再像209那样尝试各种长度，只需要依次检查起点0、1、2……对应的定长子串。

一种直接写法是对每个长度为m的子串重新统计。例如p为abc时，先统计s的前三个字符，再统计第2到第4个字符。这样容易理解，但相邻子串有m−1个位置是相同的，每次重新计数会反复处理这些字符，最坏需要O(NM)时间。

既然相邻候选只相差两个边界，就可以保留一张窗口频次表：右边进来一个字符，就把它的次数加1；左边离开一个字符，就把它的次数减1。以s="abab"、p="ab"为例，首个窗口ab的计数为{a:1,b:1}，下一步移出a、加入a，表仍然相同，但窗口起点已经从0变为1，对应的子串是ba。

到这一步，两个原本混在一起的问题就分清楚了：边界负责确定正在检查哪一段，频次表负责说明这一段包含什么。比较字典是在比较字符和次数组成的映射，插入顺序不影响普通dict的相等判断。如果对按键查询还不熟悉，可以先看哈希表与Python字典，再回来对照这里保存的内容。

2.2 首版的问题：指针长度与频次内容没有对应上

第一版在窗口未满时增加右端计数，满窗时却直接比较。这样下标上已经包含当前字符，频次表里还没有它；同时，记录答案的条件写成了window != need。

展开438首版错误逻辑
python
from collections import Counter

def anagrams_bug_initial(s: str, p: str) -> list[int]:
    answer, window, need = [], {}, Counter(p)
    left = 0
    for right in range(len(s)):
        if s[right] not in need:
            left, window = right + 1, {}  # 这个重置本身合理。
            continue
        if right - left + 1 != len(p):
            window[s[right]] = window.get(s[right], 0) + 1
        else:
            # 错误1：满窗时没有加入右端；错误2：相等条件写反。
            if window != need:
                answer.append(left)
                # 左移绑定在比较分支内，窗口控制也不清楚。
                window[s[left]] = window.get(s[left], 0) - 1
                left += 1
    return answer

对s="aa"、p="ab"，走到第二个a时，边界表示长度2，表里却只有一个a。此时window != need成立，错误地记录起点0。这里需要一起修正的是先让频次对应当前窗口，再在频次相等时记录答案。

收缩还应从比较分支中独立出来。无论这个长度为m的窗口匹不匹配，下一个候选都要向右移动，不能只在找到答案时删除左端。

例如首个候选不是异位词，也只能说明这个起点不行，不能说明后面的起点都不行。如果把左端移动写在“匹配成功”里面，遇到不匹配就会把旧字符留在表中，下一次比较的已经不是预期的定长窗口。因此这部分应分成更新状态、判断答案、准备下一个候选三个连续步骤；匹配条件只决定是否记录起点，不决定是否维护窗口。

2.3 直接比较频次字典，先把定长窗口维护正确

设m=len(p)。每个右端字符只入窗一次，窗口长度达到m时比较，然后移出左端，给下一次加入留出位置。

python
from collections import Counter

def anagrams_dict(s: str, p: str) -> list[int]:
    answer, window, need = [], {}, Counter(p)
    left = 0
    for right, ch in enumerate(s):
        if ch not in need:
            left, window = right + 1, {}  # 跨过这个字符的窗口不可能匹配。
            continue
        window[ch] = window.get(ch, 0) + 1
        if right - left + 1 == len(p):
            if window == need:
                answer.append(left)
            old = s[left]
            window[old] -= 1
            if window[old] == 0:
                del window[old]  # 普通dict比较时保留清楚的非零键集合。
            left += 1
    return answer

这个版本还保留了一个有效的重置：遇到p中不存在的字符，就把新窗口起点移到它之后，清空旧计数。任何跨过这个字符的子串都无法与p匹配，所以已经检查过它左侧的候选后，可以直接重新开始。

例如s="cbaebabacd"、p="abc"，前三个字符组成cba，得到起点0；遇到e后重置，后面继续维护长度3的窗口，最终还会得到起点6的bac。s比p短时，窗口始终达不到m，结果自然是空列表。

重置并不会跳过一个可能的答案：假设新读入的e在下标3，任何起点不大于3、终点又包含它的候选都带有e，而p中没有e，这些候选已经可以排除。把left移到4以后，新的候选仍会逐一建立。这个额外判断利用的是字符需求，单纯维护固定长度的窗口也可以求解，后面的26格数组版就没有依赖这种重置。

2.4 match优化：从全表比较到需求阈值

频次字典版正确后，我又按建议尝试用一个计数变量减少整张表的比较。原来是每形成一个窗口，就重新比较一次所有字符；换成match后，希望每次只处理刚进入、刚离开的字符，让这个变量直接反映当前还有多少需求没有满足。

但这里比直接比较字典多了一层需要自己维护的状态：字典里保存的次数要对，match还必须与这些次数保持一致。第一次改写时，满窗分支里又加了一次右端字符；移出左端时，判断阈值用的却是右端字符的需求量。

展开第一次match优化的错误逻辑
python
from collections import Counter

def anagrams_bug_match(s: str, p: str) -> list[int]:
    answer, window, need = [], {}, Counter(p)
    left = match = 0
    for right, ch in enumerate(s):
        if ch not in need:
            left, window, match = right + 1, {}, 0
            continue
        window[ch] = window.get(ch, 0) + 1
        if window[ch] == need[ch]:
            match += 1
        if right - left + 1 == len(p):
            window[ch] = window.get(ch, 0) + 1  # 错误：重复计入右端。
            if window[ch] == need[ch]:
                match += 1
            if match == len(need):
                answer.append(left)
            window[s[left]] -= 1
            if window[s[left]] == need[ch] - 1:  # 错误：查的是右端字符需求。
                match -= 1
            left += 1
    return answer

s="aab"、p="abb"能显示前一个问题：真实窗口只有一个b，重复入窗却把b记成了两个，最终误报起点0。指针范围没有变长，错误的是频次已经不再对应这个范围。

2.4.1 先给match一个能够持续维护的定义

最终采用的定义是：match表示p中有多少种字符，其窗口计数已经至少达到需求数量。设p中有K种字符，全部达标时match==K。

以p中的b需要2次为例，阈值的变化如下：

操作b的计数变化是否跨过“达到2次”的门槛match变化
加入b1→2从不足到达标+1
加入b2→3仍然达标不变
移出b3→2仍然达标不变
移出b2→1从达标到不足−1

这里没有在“超过需求”时减去match，因为它记录的是至少达标，不是恰好相等。按照这个定义，每次只检查新加入或被移出的那一种字符，就能维护计数。

这也是写更新条件之前需要先明确变量含义的原因。假如把match理解成“恰好相等的字符种类数”，那么2→3时也必须减1，3→2时又必须加1；这同样可以设计成另一种算法，但维护规则就不同了。当前代码使用“至少达到需求”的定义，所以只在跨过不足与达标的门槛时变化，不能在解释中临时把它改成恰好相等。

对应到代码，入窗时先加次数，再看新次数是否刚好等于need；出窗时先减次数，再看新次数是否刚好变成need−1。前者说明这次加入刚好补足需求，后者说明这次移出刚好使需求不足。两处判断都在检查当前操作是否跨过达标阈值，所以只有跨过时才修改match。这样理解后，就不必把几个if当作互不相关的写法去记。

2.4.3 固定窗口长度将全部达标转为频次相等

答案检查还有一个条件：窗口长度恰好为m，也就是p中所有需求次数的总和。

当每种字符都至少够用时，窗口至少需要m个字符；现在窗口正好只有m个位置。如果某种字符还多占一个位置，其他字符就必然有一种不够，与“全部达标”冲突。因此，在这个长度下，全部至少满足就能推出各频次恰好相等。

如果改成长度大于m的窗口，这个结论就不能沿用。比如p="ab"，窗口aab中两种需求都满足，却不是异位词。它可以被视为覆盖了需求，但不能作为438的答案。

python
from collections import Counter

def anagrams_match(s: str, p: str) -> list[int]:
    answer, window, need = [], {}, Counter(p)
    left = match = 0
    for right, ch in enumerate(s):
        if ch not in need:
            left, window, match = right + 1, {}, 0
            continue
        window[ch] = window.get(ch, 0) + 1
        if window[ch] == need[ch]:
            match += 1  # 仅“不足->达标”增加；从达标变过量不减。
        if right - left + 1 == len(p):
            if match == len(need):
                # 总长度相等且每种都至少够，才能推出每种恰好相等。
                answer.append(left)
            old = s[left]
            window[old] -= 1
            if window[old] == need[old] - 1:
                match -= 1  # “达标->不足”减少；过量减回达标不变。
            left += 1
    return answer

移出时先记住old=s[left]，随后查询need[old]，就能把“谁离开窗口”和“检查谁的阈值”对应起来。这份代码放到平台时，对应Solution.findAnagrams。

2.4.4 match计数与26格数组的适用条件和复杂度对比

设N为s长度、M为p长度、K为p中不同字符的数量，暂不计结果列表。

写法时间额外空间主要条件
频次字典，每次比较全表平均O(M+NK)O(K)每次相等比较最多检查K个键
频次字典，维护match平均O(N+M)O(K)哈希操作平均O(1)，定义并维护需求阈值
26格数组，每次比较O(M+26N)，即O(N+M)O(1)字符限定为26个小写英文字母

在本题中K最多为26，直接比较版也已经是线性时间。match省去了每个候选的整表比较，但不能写成“从平方时间优化到线性时间”。如果字符种类随输入增长，全表比较的K才会成为更明显的成本。代码中重置字典也会丢弃旧键，不过每段保存的键来自该段已经读过的字符，整个过程的累计清理成本仍可计入线性扫描。

补充：利用小写字母条件的26格数组
python
def anagrams_array26(s: str, p: str) -> list[int]:
    if len(s) < len(p):
        return []
    need, window, answer = [0] * 26, [0] * 26, []
    for ch in p:
        need[ord(ch) - ord("a")] += 1
    for right, ch in enumerate(s):
        window[ord(ch) - ord("a")] += 1
        if right >= len(p):
            # 始终只保留最近len(p)个字符。
            window[ord(s[right - len(p)]) - ord("a")] -= 1
        if right >= len(p) - 1 and window == need:
            answer.append(right - len(p) + 1)
    return answer

数组版使用ord(ch)-ord("a")把a到z映射到0到25；它的空间上限固定，适合本题字符集。需要处理更一般的字符时，字典更方便。两者没有做同环境计时，这里只比较状态、操作量和成立条件。

输出列表最多保存N-M+1个起点（N≥M时），输出空间最坏为O(N)，它与上表中的辅助状态空间应分开看。

补充：Counter与普通dict的零计数比较

Python3.10起，两个Counter比较时会把缺失键看成0；普通dict中多出一个零值键，仍然是不同的键值映射。本文的window是普通dict，直接比较版在计数降到0时删除键，使表内只保留实际存在的字符。match版只查询次数和阈值，可以保留归零的需求键。具体规则见Python的Counter文档。
