从点击按钮到收到任务编号

假设浏览器要向https://api.example.test/tasks提交任务。域名是示例地址，下面按HTTP/1.1或HTTP/2使用TCP、TLS1.3的典型情况讲解；HTTP/3使用QUIC，不能直接套用完全相同的连接过程。

浏览器先解析URL，确定协议、主机、端口和路径。没有可用地址缓存时，需要通过DNS查询域名对应的地址；没有可复用连接时，再建立传输连接。使用HTTPS还需要完成TLS握手，校验服务端身份并协商保护后续数据的密钥。已经存在缓存、连接池或会话恢复时，不必每次都从头重复全部步骤。

HTTP请求到达网关或应用服务器后，才进入路径路由、身份检查和业务处理。应用可能查询数据库、排队调用外部模型，最终返回任务编号。浏览器收到数据后，还要解析响应并更新页面。

网络传到了、HTTP返回了、任务完成了，是三个不同的判断。 例如HTTP的202 Accepted表示请求已被接受处理，并不表示处理已经完成。前端还应依据任务状态接口或事件确认结果。HTTP状态语义

TCP怎样让两端建立有序的字节流

TCP提供有序字节流。 每个方向都有自己的序号，用于标识数据在字节流中的位置；确认号通常表示接收方下一步期待的序号。连接建立时，两端需要交换并确认初始序号。

教学例中，客户端初始序号为100，服务端为900，暂不携带应用数据：

方向报文中的关键字段接收方知道了什么
客户端→服务端SYN，seq=100客户端希望建连，并声明发送起点
服务端→客户端SYN+ACK，seq=900，ack=101服务端确认客户端SYN，并声明自身起点
客户端→服务端ACK，seq=101，ack=901客户端已收到并确认服务端SYN

SYN占用一个序号，所以确认的是101和901。第三步让服务端获得对自身初始序号的确认，也有助于处理旧连接请求等异常情况。实际TCP还包含重传、同时打开等分支，这张表只演示常见主动连接。TCP规范§3.5

建立连接后，应用仍需定义自己的消息边界。假设连续发送ABC和DEF，接收方可能一次读到ABCDEF，也可能分多次得到AB、CD、EF。一次send不对应一次recv。 协议可以用长度字段、分隔符或自己的帧格式识别一条消息；读取程序要处理半条消息和一次读出多条消息的情况。

TCP的确认也不表示应用已经提交数据库。字节可能已经进入接收端缓冲区，而业务线程尚未处理，或者处理以后在返回前崩溃。这就是工具请求超时仍需要业务结果查询与幂等的原因。

TLS保护的内容与HTTP业务语义

TLS建立经过认证和加密保护的通信通道。 常见Web场景通过证书和握手校验服务端身份，再使用协商出的流量密钥保护数据。证书校验、密钥协商和应用层鉴权分别解决不同的问题。TLS1.3规范

HTTPS连接建立成功，只说明相应通信安全条件得到满足，不表示当前用户有权读取每一个任务。接口仍需验证登录状态、租户与资源归属。请求经过反向代理时，还要明确TLS在哪一段终止，以及代理到后端的链路怎样保护。

TLS也不负责判断任务是否成功。接口可以通过受保护的连接返回业务错误；同样，合法用户发出的参数也可能不满足业务约束。理解各层职责以后，排查时才知道该查看证书错误、HTTP状态，还是任务执行记录。

关闭连接为什么要分别处理两个方向

TCP允许两个方向分别结束发送。A发送FIN表示A没有更多数据要发；B确认以后，仍可能继续发送剩余数据。等B也结束发送，再发送自己的FIN，A确认后完成相应关闭过程。

因此常见教学过程是A FIN → B ACK → B FIN → A ACK。中间两个报文在条件允许时可以合并，实际还可能出现同时关闭，所以“四次挥手”描述的是常见分开关闭的过程，不能要求抓包必须恰好出现四个报文。TCP关闭与半关闭

常见主动关闭路径中的A会进入TIME_WAIT，为可靠完成关闭和处理旧报文保留一段时间。它通常与连接关闭速率有关，数量多不直接等于故障。需要结合连接失败、端口资源、延迟和连接复用情况判断。

CLOSE_WAIT则表示本端已收到对端的关闭通知，本地关闭流程尚未结束。持续累积时，要检查应用是否遗漏关闭连接、是否卡在某段处理过程；它不能简单套用TIME_WAIT的解释。

面试问答：握手、挥手与协议分层

介绍 TCP 协议的连接（三次握手）和断开过程（四次挥手），为什么断开要进行 4 次挥手？

回答： 常见建连过程是客户端发送SYN，服务端返回SYN+ACK，客户端再确认服务端SYN。两端由此交换并确认各自的初始序号，建立双向传输所需的状态。SYN占用一个序号，确认号需要相应增加。

关闭时，两端的发送方向独立结束。主动关闭方发送FIN，对方先确认；对方如果还有数据，可以发送完以后再发FIN，最后由主动方确认。因此常见过程包含两个FIN和分别对应的确认。若接收方已经可以立即关闭，ACK和FIN可以合并，报文数不必固定为4。

在常见关闭时序中，主动方经历FIN_WAIT_1、FIN_WAIT_2和TIME_WAIT，被动方在收到FIN后进入CLOSE_WAIT，发出自己的FIN后进入LAST_ACK。状态转换还受报文到达顺序影响；同时关闭不能完全套用这条单向主动关闭路径。

延伸追问（自拟）：为什么不能收到FIN就把两端都立即关闭？ FIN只声明发送者不再发送，另一方向可能仍有待发送数据。立即双向截断会破坏半关闭语义，并可能丢掉应用仍需要的内容。

原问ID：FQ-doxcnqvJOj8mlfECOElMVKISyPc。出处：原始面经。

HTTPS 握手和 TCP 四次挥手分别解决什么问题？

回答： HTTPS使用的TLS握手用于协商安全参数、建立密钥并按配置认证通信方；TCP关闭过程用于结束两个方向的数据发送并处理连接状态。前者属于安全通道建立，后者属于传输连接关闭，作用和发生时机不同。

在本文的TCP场景中，通常先建立TCP连接，再进行TLS握手，然后传输HTTP消息。TLS正常关闭还可能发送自己的关闭通知，这与TCP的FIN也不是同一个协议事件。关闭顺序应由所用库正确处理，不能把TCP收到了FIN解释成已经收到完整业务结果。

延伸追问（自拟）：HTTPS是否总要先进行TCP三次握手？ 不应这样泛化。本文限定HTTP/1.1或HTTP/2 over TCP；HTTP/3的传输基础是QUIC，其连接过程不能直接照搬TCP流程。
