写过简单JS后，应该已经接触过函数、对象和事件。做前后端交互时，还需要补上Promise、async/await、模块和错误处理。这几个内容可以用一个完整过程串起来：点击按钮，等待接口返回，然后更新页面。

模块怎样把代码组织起来

本站把HTTP请求放在src/lib/api.ts，表单组件再导入其中的函数。简化成JS，结构如下：

js
// api.js
export async function readReceipt(url) {
  const response = await fetch(url);
  if (!response.ok) throw new Error(`HTTP ${response.status}`);
  return response.json();
}

// 页面模块
import { readReceipt } from "./api.js";

export声明供其他模块使用的内容，import按名称取得它。相对路径需要相对于当前模块理解；本站的@/lib/api则使用了工程配置的路径别名，浏览器并不会天然认识@。构建工具负责解析这类工程写法。

代码拆分的直接收益是，同一套超时与错误提示可以被多个组件复用。如果每个表单各自拼接口地址，后面修改API前缀就容易漏掉一处。

Promise表示尚未确定的异步结果

调用fetch()时，请求还没有完成，它先返回Promise。Promise后续可能兑现为Response，也可能因为网络错误等原因被拒绝。await允许异步函数等到这个Promise完成，再继续执行后面的代码；等待期间，浏览器仍有机会处理其他任务。

js
async function loadTitle() {
  console.log("开始读取");
  const response = await fetch("/example.json");
  const data = await response.json();
  console.log(data.title);
}

这里有两次等待。第一次等待响应可用，第二次等待响应体读取并按JSON解析。async函数的返回值也会包装成Promise，因此调用者同样需要await或.then()取得结果。上面的路径是教学占位，不能当作本站已有接口。

需要注意，await不会把CPU密集计算自动移到另一个线程。如果等待结束后运行一个很长的同步循环，页面仍可能卡住。并行下载与并行计算也应分别考虑。

将成功、HTTP失败和网络失败分开

下面是适合阅读的独立函数示例。它只展示请求处理方式，没有在生产接口执行：

js
async function createFeedback(payload) {
  const response = await fetch("/api/v1/feedback", {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify(payload),
    signal: AbortSignal.timeout(15000),
  });
  if (!response.ok) {
    throw new Error(`请求没有成功：${response.status}`);
  }
  return response.json();
}

JS对象要先经过JSON.stringify变成JSON文本；请求头说明正文格式。接口返回422时，fetch本身通常没有失败，但response.ok为false，所以需要主动抛出错误。网络不可达、请求被中止等情况则可能直接使fetch拒绝。Fetch官方参考对这些行为及请求选项有更完整的说明。

实际项目的apiRequest还统一处理503、401、403、429和422，不把服务端未经筛选的诊断文字直接显示给用户。204没有响应体，因此会单独返回，避免对空响应调用json()。

表单等待期间应该保留哪些状态

一次提交至少有输入、等待、成功和失败几种状态。本站将等待标记放在busy里，并在finally恢复：

js
setBusy(true);
try {
  const receipt = await createFeedback(payload);
  setMessage("");
  setSuccess(`已收到反馈，编号：${receipt.id}`);
} catch (error) {
  setError("尚未确认发送成功，输入已保留。");
} finally {
  setBusy(false);
}

finally在成功和失败路径都会执行，适合释放等待状态。只有确认成功后才清空输入，失败时保留用户已经写好的内容。这里的setMessage等函数来自React状态，具体含义见React状态与Effect。

15秒超时控制的是客户端愿意等待多久。中止浏览器请求，不保证服务器事务也会同步取消。服务器可能已经提交，只是回执未到达，所以本站没有在这里自动重试POST。

两个请求怎样安排顺序

如果请求B需要请求A返回的ID，就应该先等A，再发B。两个互不依赖的只读请求可以用Promise.all一起等待，但其中一个拒绝后，其他已经发出的请求不会自动取消；需要全部结果时，可以考虑Promise.allSettled。

搜索还有一种常见问题：用户先输入react，很快改成next，前一个请求却更晚返回。如果直接用每次返回的数据覆盖结果，就会显示过时内容。可以中止旧请求，也可以给请求标记序号，只接受当前序号的结果。本站站内搜索先加载静态索引，再在本地匹配，并没有为每次输入访问服务器搜索接口，因此不要把这个教学场景写成本站现有缺陷。

继续追问时，可以把“异步”落实成三个问题：等待的是什么、谁能在等待期间继续工作、结果回来时还是否属于当前操作。比起只记住async/await的语法，这三个问题更有助于检查真实代码。
