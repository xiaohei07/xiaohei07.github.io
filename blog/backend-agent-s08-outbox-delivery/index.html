为什么写库成功以后，还可能永远没有通知

假设创建工单以后，需要向通知服务发一条消息。程序先提交数据库，再发送消息；如果在两步之间崩溃，工单已经存在，通知却没有任何持久待发记录。把顺序换过来，也可能出现消息已发出、数据库最后回滚的问题。

Outbox（事务发件箱）把“需要发送的事件”也写进本地数据库，并与业务修改放在同一个事务中。事务提交后，再由独立投递程序发送这些事件。这样即使发送程序暂时失败，待发事件仍然可以被发现。事务Outbox模式

一个教学事务可以同时写入工单T17和事件E17，事件记录包含业务对象ID、事件类型、版本和载荷。本地事务保护的是工单与待发记录一起提交，不是消息系统和消费者也在这一刻全部完成。

阶段已完成的事实尚不能推出什么
数据库提交工单与Outbox事件持久记录完成消息已经到达broker
broker确认接收按其确认契约接收了消息消费者已经完成业务
消费者提交业务目标状态已经改变消费确认一定已送达
消费确认完成broker可按协议更新投递状态任意外部副作用都只执行过一次

RabbitMQ将发布确认与消费者确认分开处理，两者保护不同的链路。具体耐久保证还取决于队列、消息和复制等配置；确认机制不能脱离配置单独讨论。发布确认与消费确认

投递和消费分别怎样产生重复

投递程序把E17发到broker，broker已接受，但投递程序在写“已发送”之前崩溃。恢复后Outbox仍显示未发，再发一次就会产生重复。若为了避免重复而先标记已发，再实际发送，标记后崩溃又可能造成漏发。

消费者也有类似窗口。若先确认消息再提交业务，确认后崩溃可能丢掉业务处理；若先提交业务再确认，提交后崩溃可能导致再次投递。

所以可靠设计通常需要接受某个边界上的重试，并确保重复不会产生错误业务效果。消息重复交付，与业务效果重复，是两个可以分别处理的问题。

去重标记必须和哪一步保持一致

假设消费者处理E17时需要更新自己的数据库。可以在同一事务中检查事件ID唯一约束、写业务变化并记录处理结果。事务成功后再确认消息。再次收到E17时，依据已持久化结果复用或跳过业务更新。

如果先在Redis里写“E17已处理”，随后更新数据库失败，重试可能因为这个标记而被错误跳过。如果先更新数据库再单独写去重标记，则又有重复执行的窗口。关键是去重记录与目标业务变化的原子边界。

如果目标动作是调用外部短信或支付服务，本地事务不能把外部提交一起回滚。需要下游提供稳定幂等键、结果查询或对账能力，按业务操作ID处理未决结果。

Kafka的事务和exactly-once相关能力也有范围。Kafka内的读取、处理与写回可以在相应配置和API下协调，但任意外部数据库或HTTP副作用需要额外配合，不能从一个配置开关推出整个业务链都恰好执行一次。Kafka4.1消息交付语义

重复下单和真的想再买一次怎样区分

幂等键应代表一次业务意图。用户点击提交后因网络问题重试，沿用同一操作ID；用户完成一次购买以后又决定再买，应产生新的业务操作ID。

只用用户ID去重，会把这个用户后续合法订单挡住；永久使用“用户+商品”去重，也会混淆重试与再次购买。服务端需要核对相同ID是否携带相同参数，处理中返回真实状态，已完成返回已有结果，并约定记录保留期。

关掉页面再进入，不应自动决定这是新意图还是旧重试。前后端需要保存并展示可查询的订单状态，让用户继续尚未确认的提交，或明确发起新的购买。幂等不能替产品流程替用户猜意图。

事件顺序还需另外设计。取消事件先到、创建事件后到时，如果仅按接收顺序执行，就可能把已取消对象重新创建。可以依据业务版本和终态规则拒绝过时事件，但具体规则必须符合业务含义，不能用队列顺序代替所有状态判断。

面试问答：重复消费与幂等身份

如何保证消息不会重复消费？

回答： 先说明所要求的边界。消息系统在确认丢失、消费者重启等情况下可能重新投递，业务通常需要通过幂等处理保证重复消息不会产生重复效果，而不是承诺任何故障下都只收到一次消息。

消费者为事件建立稳定ID，并将去重结果与目标业务更新放在同一可靠事务边界，业务提交后再确认消息。若提交成功但确认丢失，消息会重来，但去重记录可阻止业务再次更新。先确认后处理有丢失窗口，先单独写去重标记再执行业务则可能产生假成功。

对于外部HTTP副作用，本地数据库去重不足以覆盖远端提交，必须结合下游幂等与状态查询。还要规定去重记录保留时间、重复事件参数冲突、乱序和失败重试，监测积压与无法自动处理的事件。

延伸追问（自拟）：exactly-once是否就不需要业务幂等？ 要看保证范围。消息系统内部的事务语义不自动扩展到任意外部资源；跨出该边界时仍需协议支持。

一个用户下两次单怎么办？一个用户下一次单立刻退出并进入再下两次单怎么办（想买两件商品）？幂等性实现。

回答： 先区分重复提交与新的购买意图。一次提交生成稳定业务操作ID，网络重试沿用该ID；用户明确再次购买则生成新的操作ID。不能只用用户ID或用户与商品的组合永久去重，否则会误拦合法的第二次购买。

服务端通过唯一约束或等效原子机制登记操作，校验参数摘要，保存处理中、成功或失败状态及已有订单号。相同ID相同参数返回已有结果，相同ID不同参数报告冲突。退出再进入时，前端应能查询尚未确认的操作，避免页面重建就无条件产生新的提交身份。

如果用户想在一次订单里购买两件，应通过数量或订单明细表达；如果想分别下两张单，则是两个明确意图。订单创建、库存与支付还各自需要协调边界，单个入口去重不能自动保证所有下游操作只执行一次。

延伸追问（自拟）：为什么锁不够？ 锁限制同时执行，锁释放后仍可能收到同一意图的迟到重试。幂等记录跨时间保留操作身份和结果，作用不同。
