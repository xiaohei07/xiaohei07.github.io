协程对象、Task调度与实际执行

假设要查三份相互独立的资料。如果每查完一份才开始下一份，等待时间会逐项累积；它们没有数据依赖时，就可以在等待网络响应的过程中交错推进。

Python调用async def函数会得到协程对象，这一步本身不代表函数体已经执行。await用于等待可等待对象；asyncio.create_task把协程包装为受事件循环调度的Task。调度以后何时获得执行机会，还取决于事件循环和其他任务的行为。Python3.13协程与Task

任务真正挂起等待时，事件循环才能推进其他任务；如果等待对象已经就绪，await也可能直接返回。长时间纯计算如果没有让出控制权，仍可能占据事件循环线程。

工具数据依赖、副作用与并行条件

查订单和查物流可能都需要同一个订单号，若订单号已经确认，两者可以并发；如果必须先通过用户信息找到订单号，就不能把后续查询无条件同时发出。

工具副作用也会限制并行。两个读取可以独立完成，但“创建工单”和“关闭同一工单”有业务顺序；两个同时修改同一对象的工具则需要并发协议。Task负责安排执行，业务依赖与并发协议决定哪些动作可以同时进行。

结果应通过调用ID或预先确定的位置与输入关联。较慢任务可能后完成，但输入与输出关系必须保持正确。

用Semaphore限制同时执行的工具数量

Semaphore（信号量）在这里用于限制同时进入调用区间的任务数量。下面只用asyncio.sleep模拟可让出执行权的等待，不访问外部服务。示例兼容Python3.11及以上，不依赖额外库。

python
import asyncio

async def query_one(name, slots):
    async with slots:  # 进入实际调用前占用一个并发名额
        await asyncio.sleep(0.01)
        return f"result:{name}"

async def main():
    slots = asyncio.Semaphore(2)
    tasks = [asyncio.create_task(query_one(name, slots))
             for name in ["A", "B", "C"]]
    # gather按传入任务的位置组织结果，不按完成先后重新排序
    results = await asyncio.gather(*tasks)
    assert results == ["result:A", "result:B", "result:C"]
    print(results)

if __name__ == "__main__":
    asyncio.run(main())

三个Task都已经创建，但最多两个同时进入受限区间。第三个等待名额，直到前面的任务退出。真实工具应把并发限制覆盖到实际资源占用区间，而不是刚发出请求就提前释放。

这个例子只适合有限数量的任务。如果一次创建一百万个Task，全部Task对象都会占用内存，即使信号量只允许少量任务进入调用区间。更大的输入适合有界队列和固定工作者，让生产速度也受到约束。

同步库、失败和取消的边界

在事件循环线程里直接调用阻塞HTTP客户端，会让整个线程等待，其他Task也无法按预期推进。可以选择真正的异步客户端；对于适合转移的阻塞I/O，也可以使用asyncio.to_thread等方式。但把计算放进线程，不等于在所有CPython构建中都能并行执行Python字节码，具体还要看版本、GIL配置和扩展是否释放GIL。

gather默认传播异常时，不应假定其他任务都会自动停止。若希望一组任务按结构化并发管理，可以考虑Python3.11开始提供的TaskGroup，并按其异常和取消规则设计清理。无论采用哪种方式，都要回收已经创建的任务，不把后台未决动作遗忘。

取消通常是协作式的控制信号，不是任意位置强制回滚。 协程需要在合适的等待位置响应取消，通过finally或上下文管理器清理本地资源。已经交给线程或外部系统的工作，不一定随调用方停止等待而终止。

比如创建工单请求超时后，协程可能已经结束，工单服务却仍在处理或已经提交。外部状态仍按结果未知与幂等处理；读取类任务与有副作用任务不能使用完全相同的重试策略。

面试问答：多个Tool的异步并发组织

Python 里多个 Tool 同时调用时，怎么做异步并发？

回答： 先根据数据依赖和副作用确定可并行工具，再使用异步客户端与Task调度，并通过信号量或工作队列限制实际并发。每个调用应关联ID、超时、错误类别和结果状态，不能仅创建Task后等待一个结果列表。

少量独立任务可以用create_task和gather组织；需要共同生命周期时，可按Python版本使用TaskGroup。阻塞库不能直接放在事件循环中执行长时间I/O，应更换异步接口或转移到合适的工作线程。大量任务还需要有界队列，避免全部Task先创建出来导致内存积压。

失败处理要区分一个结果失败是否影响其他任务。如果任务互相独立，可以保留已成功结果并单独报告失败；如果后续步骤需要所有结果，就应停止依赖步骤。取消后还要清理本地资源，并核对已经发出的外部副作用，不能把“调用方不再等”写成“远端已停止”。

延伸追问（自拟）：async是否让CPU密集工具自动并行？ 不会。协程主要帮助等待期间交错推进。CPU任务需要依据运行时与部署选择进程、合适的线程或其他执行资源，同时控制开销与数据传递。
