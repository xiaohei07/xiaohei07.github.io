记忆需要保存什么，才能在下一次正确使用

把历史对话压成一段摘要，可以减少上下文长度，但会丢掉一些更新时很重要的信息。例如“使用Python3.10”究竟是某个旧项目的环境，还是用户所有项目的偏好？如果只剩一句话，后续很容易用错范围。

记忆是可再次检索和使用的信息记录。除了内容，还需要保存它适用于谁、哪个项目、什么时间，以及依据是什么。短期记忆通常服务当前会话，长期记忆可以跨会话检索；存储范围扩大以后，权限与更新规则也要相应明确。LangGraph记忆概念

一个教学记录可以写为：

json
{
  "key": "python_version",
  "scope": "project:atlas",
  "value": "3.10",
  "source": "environment-check",
  "observed_at": "2026-10-01",
  "valid_from": "2026-10-01",
  "revision": 3
}

observed_at表示什么时候获知，valid_from表示事实从什么时候适用。两者不一定相同：今天才读到一份上个月生效的迁移说明，就不能把事实生效时间也写成今天。

两条内容不一样，未必互相冲突

旧记录写“项目Atlas使用Python3.10”，新记录写“项目Nova使用Python3.12”，对象不同，可以并存。旧记录是“2025年使用3.10”，新记录是“2026年迁移到3.12”，时间范围不同，也可以保留历史并更新当前值。

真正的冲突是同一对象、同一属性、适用时间重叠，却给出不能同时成立的值。例如两个来源都声称当前Atlas环境版本不同，就需要进一步核查，不能只按消息到达顺序覆盖。

偏好还会有任务级例外。用户平时喜欢简洁说明，某次明确要求详细推导，只对该任务生效。把这个例外写成全局偏好，会影响后续不相关工作。

覆盖、并存与拒绝的判断过程

情况合适的处理原因
同范围，明确的新事实替代旧事实更新当前值，保留历史来源事实发生变化
对象或时间范围不同分开保存不构成直接冲突
两个可信来源互相矛盾标记待核查，暂不合并结论证据不足
外部文档要求修改用户全局偏好拒绝作为用户指令写入来源没有相应权限
同一内容重复出现合并引用或去重无需增加相同记忆

新近程度只是证据之一。一段刚生成的摘要不应该覆盖用户明确确认的原始规则；旧文档里的有效协议，也不应被没有来源的最新猜测替换。

对事实类记忆，可以按“可核验环境结果、明确的用户更新、可信文档”等来源设计业务规则，但这个顺序也要符合对象本身。环境检测能说明当前安装版本，却不能替用户决定喜欢什么表达方式。

一个版本冲突怎样处理

假设记忆revision=3，值为Python3.10。任务A准备根据迁移记录更新为3.12，任务B仍拿着旧副本，想补充3.10的备注。如果两者直接覆盖整条记录，B可能把A的新版本改回去。

可以采用乐观并发控制：更新时携带预期revision，只有数据库中的revision仍为3才接受；成功后递增到4。B再用revision=3更新会失败，需要重新读取并决定如何合并。

这与普通业务数据的版本控制相同。LLM可以提出合并建议，但最终更新条件应该由代码与数据库检查，不能只靠提示词要求“不要覆盖新值”。

检索记忆时还要处理有效范围

写入正确以后，读取也不能只按向量相似度取TopK。先限定用户、项目与访问权限，再过滤失效或被替代的记录；必要时把历史值作为背景单独展示。

例如用户询问Atlas当前运行环境，应该返回最新有效版本；询问“上次升级前的环境”，则需要历史记录。把历史全部删除会失去追溯能力，把历史与当前混在一起又会造成冲突。

记忆删除也要考虑派生摘要与缓存。如果用户要求移除某项信息，原记录删除后，包含相同信息的摘要不能继续作为可用记忆返回。具体保留策略要按用户要求和产品约定实现，不能把“忘记”仅做成检索排名降低。

怎样验证更新规则

可以用本地小字典模拟四个版本：原值、同范围新值、不同项目值、过期历史值。检查当前查询只取当前范围的新值，历史查询保留旧值；再模拟两个写入者使用同一revision，确认第二次更新被拒绝。

还应加入一段外部文档中的指令性文本，验证它只能成为待分析资料，不能自动改写用户偏好或工具权限。本篇给出的是记忆管理设计，没有宣称某个框架默认实现了这些规则。

面试追问：冲突时怎样选择处理方式

Agent 记忆发生事实冲突时，如何判断覆盖、并存还是拒绝写入？

回答：先比较主体、属性、作用域和有效时间，确认是否真冲突。明确的新事实可以更新当前值并保留历史；范围不同或时间不同的事实可以并存；来源无权修改目标信息、内容无法核实或违反访问规则时拒绝写入。可信来源相互矛盾时保留冲突状态并补充核查。写入还需要版本条件，防止并发任务用旧副本覆盖新记录。

自拟追问：用一个模型总结全部记忆能解决冲突吗？摘要能压缩文字，但可能丢掉来源与适用范围。冲突处理依赖结构化元数据和业务规则，不能只靠生成一段更流畅的总结。
