兼容性首先是旧代码还能按原来的含义工作

假设旧客户端读取{"price": 12.5}，单位约定为元。新版本为了避免浮点金额问题，想改成{"price": 1250}，单位变为分。

字段名称和JSON类型似乎都没变，旧客户端也能解析，但显示结果已经错了。兼容性既包括格式能够读取，也包括读取后的含义保持一致。字段类型、默认值、单位、排序、分页和错误处理都属于接口约定。

Google的AIP-180区分源码兼容、传输兼容和语义兼容，并强调新增字段时保留旧行为。例如把原来返回全部结果的接口改成默认只返回第一页，即使新增参数是可选的，也会改变旧客户端的结果。AIP-180兼容性说明

金额字段怎样逐步演进

一种教学方案是保留price，新增明确单位的price_cents：

json
{
  "id": "p7",
  "price": 12.5,
  "price_cents": 1250,
  "currency": "CNY"
}

新客户端优先使用price_cents，旧客户端继续按原约定使用price。服务端从同一份规范金额数据生成两种表示，避免两份字段独立变化。

这里仍需处理几个边界：旧客户端会不会拒绝未知字段；请求同时携带两个金额字段且不一致时如何处理；负数、折扣和多币种是否允许；旧浮点数据如何按已约定的精度舍入。新增字段通常比直接改字段更容易兼容，但仍然要根据真实客户端验证。

若响应结构或行为变化太大，可以通过/v2等显式版本入口提供新的协议。多个版本入口可以复用同一核心业务逻辑，由适配层转换输入输出，不必为每个客户端复制一套完整后端。

API版本与App版本为什么要分开

App1.0和2.0可能都调用APIv1，也可能只有2.0的某个新功能调用APIv2。App版本描述整个客户端发布，API版本描述某项交互协议，不能只用“客户端比较新”来推断它支持所有字段。

服务端可以根据明确的版本或能力标识选择行为；能力标识用于兼容，不用于授权。用户是否有权限访问某个资源，仍然由服务端身份与权限规则决定。

返回新枚举值也要谨慎。旧客户端如果只处理pending/complete，收到cancelled时可能崩溃或误显示。接口应约定未知值处理方式，发布前用真实旧版本验证，而不是只检查JSON是否有效。

数据库结构怎样配合滚动升级

滚动发布时，新旧服务进程会同时存在。如果新版本上线第一步就删除旧字段，旧进程可能立即报错。可以采用扩展—迁移—收缩（expand–migrate–contract）的分阶段过程：

阶段数据库变化应用行为
扩展增加兼容字段或表新旧版本均能运行
迁移分批回填并核对新代码逐步读新结构，必要时兼容旧值
收缩确认旧读写退出后删除旧结构仅保留新协议

例如新增price_cents时，先允许旧记录为空；应用写入时按迁移协议维护必要字段；后台小批量回填，再验证约束。直接给大表增加某些约束或执行全表更新，可能产生锁等待、日志与复制延迟，需要根据数据库版本和实际表结构评估。

回填不能覆盖迁移期间的新写入。可以只更新仍未迁移的记录，并结合版本条件控制并发；发现冲突则重新读取转换。若回填从旧字段转换，而新代码已经修改了新字段，盲目覆盖会把新值改回旧状态。

回滚为什么也要检查数据兼容

代码回滚只把程序换回旧版本，数据库可能已经接受新结构或新语义的数据。旧代码能否读取这些数据，是回滚方案的一部分。

金额例子中，如果新版本支持旧版本完全不理解的币种或精度，回滚到旧代码可能无法正确展示。发布前应确定回滚窗口、允许的新数据范围和必要适配。删除旧字段、改变含义等不可逆步骤应晚于观察窗口，并有备份与恢复方案。

这里描述的是迁移方法，没有修改任何真实数据库。实际上线需要单独核对表规模、锁行为、备份与变更授权。

兼容性测试怎样组织

测试矩阵至少覆盖以下组合：

客户端服务端主要检查
旧版新版旧请求、旧默认行为是否保留
新版新版新功能和新字段
新版旧版发布期间是否能降级或明确拒绝
新旧并存新旧并存会话、缓存、消息和数据结构的交叉影响

测试数据包含旧字段缺失、新字段未知、枚举新增、空值与缺省值、大金额、分页边界和历史记录。还要保留典型的旧请求与响应作为契约样本，比较字段和业务含义，不能只看HTTP状态码。

如果消息队列也传递相同数据，消息Schema需要同时演进；如果缓存键没有区分不兼容格式，旧进程可能读取新缓存后出错。版本兼容会沿整个数据流传播，应逐段检查。

面试追问：兼容性测试从哪里开始

如果让你做兼容性测试，你会怎么做？

回答：先明确兼容对象与支持范围，包括客户端、API、运行环境、数据库和消息格式。再根据实际升级方式建立新旧版本组合矩阵，保存旧请求样本，检查格式与业务语义。重点覆盖缺省值、未知字段、枚举变化、历史数据和灰度期间的交叉读写，同时验证回滚。通过分层测试定位问题，再用少量关键业务链路检查整个流程。

自拟追问：既然都支持v2了，为什么不能马上删除v1？仍可能有长期未升级的客户端、后台任务或第三方调用方。应先观察实际调用、明确支持期限并完成迁移，再撤掉旧协议。
