27:T1fca,<h2 id="section-兼容性首先是旧代码还能按原来的含义工作">兼容性首先是旧代码还能按原来的含义工作</h2>
<p>假设旧客户端读取<code>{"price": 12.5}</code>，单位约定为元。新版本为了避免浮点金额问题，想改成<code>{"price": 1250}</code>，单位变为分。</p>
<p>字段名称和JSON类型似乎都没变，旧客户端也能解析，但显示结果已经错了。<strong>兼容性既包括格式能够读取，也包括读取后的含义保持一致。</strong>字段类型、默认值、单位、排序、分页和错误处理都属于接口约定。</p>
<p>Google的AIP-180区分源码兼容、传输兼容和语义兼容，并强调新增字段时保留旧行为。例如把原来返回全部结果的接口改成默认只返回第一页，即使新增参数是可选的，也会改变旧客户端的结果。<a href="https://google.aip.dev/180" rel="noopener noreferrer">AIP-180兼容性说明</a></p>
<h2 id="section-金额字段怎样逐步演进">金额字段怎样逐步演进</h2>
<p>一种教学方案是保留<code>price</code>，新增明确单位的<code>price_cents</code>：</p>
<div class="code-block"><div class="code-toolbar"><span>json</span><button type="button" data-copy-code="true" aria-label="复制代码">复制代码</button></div><pre><code class="hljs language-json"><span class="hljs-punctuation">{</span>
  <span class="hljs-attr">"id"</span><span class="hljs-punctuation">:</span> <span class="hljs-string">"p7"</span><span class="hljs-punctuation">,</span>
  <span class="hljs-attr">"price"</span><span class="hljs-punctuation">:</span> <span class="hljs-number">12.5</span><span class="hljs-punctuation">,</span>
  <span class="hljs-attr">"price_cents"</span><span class="hljs-punctuation">:</span> <span class="hljs-number">1250</span><span class="hljs-punctuation">,</span>
  <span class="hljs-attr">"currency"</span><span class="hljs-punctuation">:</span> <span class="hljs-string">"CNY"</span>
<span class="hljs-punctuation">}</span>
</code></pre></div>
<p>新客户端优先使用<code>price_cents</code>，旧客户端继续按原约定使用<code>price</code>。服务端从同一份规范金额数据生成两种表示，避免两份字段独立变化。</p>
<p>这里仍需处理几个边界：旧客户端会不会拒绝未知字段；请求同时携带两个金额字段且不一致时如何处理；负数、折扣和多币种是否允许；旧浮点数据如何按已约定的精度舍入。<strong>新增字段通常比直接改字段更容易兼容，但仍然要根据真实客户端验证。</strong></p>
<p>若响应结构或行为变化太大，可以通过<code>/v2</code>等显式版本入口提供新的协议。多个版本入口可以复用同一核心业务逻辑，由适配层转换输入输出，不必为每个客户端复制一套完整后端。</p>
<h2 id="section-api版本与app版本为什么要分开">API版本与App版本为什么要分开</h2>
<p>App1.0和2.0可能都调用APIv1，也可能只有2.0的某个新功能调用APIv2。App版本描述整个客户端发布，API版本描述某项交互协议，不能只用“客户端比较新”来推断它支持所有字段。</p>
<p>服务端可以根据明确的版本或能力标识选择行为；能力标识用于兼容，不用于授权。用户是否有权限访问某个资源，仍然由服务端身份与权限规则决定。</p>
<p>返回新枚举值也要谨慎。旧客户端如果只处理<code>pending/complete</code>，收到<code>cancelled</code>时可能崩溃或误显示。接口应约定未知值处理方式，发布前用真实旧版本验证，而不是只检查JSON是否有效。</p>
<h2 id="section-数据库结构怎样配合滚动升级">数据库结构怎样配合滚动升级</h2>
<p>滚动发布时，新旧服务进程会同时存在。如果新版本上线第一步就删除旧字段，旧进程可能立即报错。可以采用<strong>扩展—迁移—收缩（expand–migrate–contract）</strong>的分阶段过程：</p>

























<table><thead><tr><th>阶段</th><th>数据库变化</th><th>应用行为</th></tr></thead><tbody><tr><td>扩展</td><td>增加兼容字段或表</td><td>新旧版本均能运行</td></tr><tr><td>迁移</td><td>分批回填并核对</td><td>新代码逐步读新结构，必要时兼容旧值</td></tr><tr><td>收缩</td><td>确认旧读写退出后删除旧结构</td><td>仅保留新协议</td></tr></tbody></table>
<p>例如新增<code>price_cents</code>时，先允许旧记录为空；应用写入时按迁移协议维护必要字段；后台小批量回填，再验证约束。直接给大表增加某些约束或执行全表更新，可能产生锁等待、日志与复制延迟，需要根据数据库版本和实际表结构评估。</p>
<p><strong>回填不能覆盖迁移期间的新写入。</strong>可以只更新仍未迁移的记录，并结合版本条件控制并发；发现冲突则重新读取转换。若回填从旧字段转换，而新代码已经修改了新字段，盲目覆盖会把新值改回旧状态。</p>
<h2 id="section-回滚为什么也要检查数据兼容">回滚为什么也要检查数据兼容</h2>
<p>代码回滚只把程序换回旧版本，数据库可能已经接受新结构或新语义的数据。旧代码能否读取这些数据，是回滚方案的一部分。</p>
<p>金额例子中，如果新版本支持旧版本完全不理解的币种或精度，回滚到旧代码可能无法正确展示。发布前应确定回滚窗口、允许的新数据范围和必要适配。删除旧字段、改变含义等不可逆步骤应晚于观察窗口，并有备份与恢复方案。</p>
<p>这里描述的是迁移方法，没有修改任何真实数据库。实际上线需要单独核对表规模、锁行为、备份与变更授权。</p>
<h2 id="section-兼容性测试怎样组织">兼容性测试怎样组织</h2>
<p>测试矩阵至少覆盖以下组合：</p>






























<table><thead><tr><th>客户端</th><th>服务端</th><th>主要检查</th></tr></thead><tbody><tr><td>旧版</td><td>新版</td><td>旧请求、旧默认行为是否保留</td></tr><tr><td>新版</td><td>新版</td><td>新功能和新字段</td></tr><tr><td>新版</td><td>旧版</td><td>发布期间是否能降级或明确拒绝</td></tr><tr><td>新旧并存</td><td>新旧并存</td><td>会话、缓存、消息和数据结构的交叉影响</td></tr></tbody></table>
<p>测试数据包含旧字段缺失、新字段未知、枚举新增、空值与缺省值、大金额、分页边界和历史记录。还要保留典型的旧请求与响应作为契约样本，比较字段和业务含义，不能只看HTTP状态码。</p>
<p>如果消息队列也传递相同数据，消息Schema需要同时演进；如果缓存键没有区分不兼容格式，旧进程可能读取新缓存后出错。版本兼容会沿整个数据流传播，应逐段检查。</p>
<h2 id="section-面试追问兼容性测试从哪里开始">面试追问：兼容性测试从哪里开始</h2>
<p><span id="q-FQ-doxcnkLNOUdrLUpZy80HXVtybYb" class="legacy-anchor" aria-hidden="true"></span><a id="user-content-q-FQ-doxcnkLNOUdrLUpZy80HXVtybYb"></a></p>
<blockquote>
<p>如果让你做兼容性测试，你会怎么做？</p>
</blockquote>
<p><strong>回答：</strong>先明确兼容对象与支持范围，包括客户端、API、运行环境、数据库和消息格式。再根据实际升级方式建立新旧版本组合矩阵，保存旧请求样本，检查格式与业务语义。重点覆盖缺省值、未知字段、枚举变化、历史数据和灰度期间的交叉读写，同时验证回滚。通过分层测试定位问题，再用少量关键业务链路检查整个流程。</p>
<p><strong>自拟追问：既然都支持v2了，为什么不能马上删除v1？</strong>仍可能有长期未升级的客户端、后台任务或第三方调用方。应先观察实际调用、明确支持期限并完成迁移，再撤掉旧协议。</p>
