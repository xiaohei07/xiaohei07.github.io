goroutine与channel各自负责什么

goroutine是Go运行时调度的并发执行单元。用go f()启动函数后，当前函数可以继续执行，但新任务何时运行、是否与其他任务同时占用CPU，取决于调度与可用资源。

channel是带元素类型的通信对象，用来发送和接收值，也建立相应同步关系。它可以传整数、结构体、指针等符合声明类型的数据。把指针发过去只复制指针值，不会复制它指向的全部对象，因此所有权仍需约定。

例如生产者创建任务，消费者处理任务，channel可以把“某项工作已经准备好”的交接与数据一起表达。若双方还在任意修改同一对象，就仍可能发生数据竞争；channel不是给整个程序自动加锁。Go内存模型

无缓冲和有缓冲channel怎样改变等待

make(chan int)创建无缓冲channel，发送需要与接收方完成交接；make(chan int, 2)创建容量2的channel，前两次发送可以先放入缓冲区，满了之后再等待接收腾出位置。

状态发送接收
无缓冲，缺少对方等待交接等待交接
有缓冲且未满可放入值有值时可取出
已关闭发送触发panic先读剩余值，再得到零值和ok=false
nil channel一直阻塞一直阻塞

关闭channel表示不会再发送值，不是“清空缓存”。for v := range ch会读取已有值，直到关闭且缓冲耗尽才结束。单纯停止生产者而不关闭，消费者可能一直等下去。Go语言规范中的channel

谁负责close需要明确定义。常见做法是由唯一生产者或协调多个生产者的拥有者关闭，避免消费者关闭后仍有生产者发送。关闭已关闭channel会panic，因此“所有人退出时都close一下”不是安全清理方案。

一条支持取消的简化流水线

下面的函数把输入整数乘2，通过channel输出；调用方通过context表达不再需要后续结果。例子使用Go1.20及以上已有的基础接口，不依赖外部库。

go
package main

import (
    "context"
    "fmt"
)

func doubled(ctx context.Context, input []int) <-chan int {
    output := make(chan int)
    go func() {
        defer close(output) // 唯一发送方负责关闭
        for _, value := range input {
            select {
            case <-ctx.Done():
                return
            case output <- value * 2:
            }
        }
    }()
    return output
}

func main() {
    ctx, cancel := context.WithCancel(context.Background())
    defer cancel()
    for value := range doubled(ctx, []int{1, 2, 3}) {
        fmt.Println(value)
    }
}

正常路径预期逐行输出2、4、6。若调用方提前停止接收，就需要执行cancel，让生产者不会永久阻塞在发送上。取消是协作信号：函数必须实际检查它，下游I/O也应使用支持取消或超时的接口。Go流水线与取消

如果取消和发送同时就绪，select可以选择其中一个分支，不能承诺取消一发生就绝不会再产生一个结果。若业务要求严格的停止边界，还需要状态协议。cancel也不是join；需要确认所有任务退出时，应额外使用等待机制。

channel建立的顺序怎样保护可见性

发送前写入的数据，在匹配接收完成后具有内存模型规定的同步关系。例如生产者先设置任务字段，再发送任务，消费者接收后读取，就有明确的发布路径。

但生产者发送后继续修改同一个任务，消费者又同时读取，依然可能竞争。可以约定发送后转移所有权、发送副本，或使用锁保护共享对象。对slice尤其要小心：传递slice描述符不复制底层数组，两个slice也可能指向同一片存储。

map也不会因为运行在goroutine中就变成并发容器。共享写入应通过互斥锁、单一拥有者消息循环或适合场景的并发结构组织，不能把运行时偶尔报错当成完整的数据竞争检测。

GC为什么不能自动回收一个忘记退出的goroutine

垃圾回收能处理不可达内存，但一个仍在等待channel的goroutine及其栈可能继续持有对象。请求已经结束而任务还在等，资源就没有按业务生命周期结束。

固定worker与有界任务channel有利于限制并发和排队内存。每个输入都新开goroutine再在内部等待信号量，只限制活跃工作，仍可能先创建很多等待者。这个区别与Python有界并发类似，但调度和运行时机制不能照搬。

逃逸分析决定对象是否需要超出当前栈帧生命周期，具体分配应以编译器分析和测量为准。“返回指针一定分配到堆”或“局部变量一定在栈”都过于绝对。处理大批任务时，还要观察分配速率与保留关系，而非只减少语法上的new。

面试问答：channel怎样使用

讲讲 channel

回答： channel是带类型的通信与同步机制，发送和接收在规定条件下建立顺序。无缓冲channel需要交接，有缓冲channel允许有限排队；缓冲满时发送等待。关闭表示不再发送，接收方会先读完缓冲，再得到零值和ok=false；向关闭的channel发送会panic，nil channel的发送接收会阻塞。

设计时要明确发送者、关闭者、容量和取消路径。例如消费者提前退出却没有取消生产者，生产者可能永久等待发送，形成goroutine泄漏。传递指针或slice也不自动消除共享修改的数据竞争，仍要约定所有权或同步。

延伸追问（自拟）：容量从0改成1只是性能优化吗？ 不一定。它改变了发送方等待接收方的时机及可依赖的同步关系，可能让原来依靠交接顺序的程序失去条件。需要重新检查协议，而不是仅调整一个数字。
