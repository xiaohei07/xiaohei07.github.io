7B模型的BF16权重需要多少空间

7B通常表示约70亿参数。BF16每参数2字节，权重大小约为：

7×109×2=14×109 bytes≈13.04 GiB7\times10^9\times2=14\times10^9\text{ bytes} \approx13.04\text{ GiB}

这只是权重存储，不是整个任务的显存需求。推理还需要KV Cache、激活、工作区和框架开销；训练还要保存梯度、优化器状态以及反向传播所需信息。

模型结构中也可能有不同精度的参数或缓冲，参数量本身通常是近似名称。因此估算用于判断数量级，真正运行前应读取checkpoint和训练配置。

混合精度Adam训练怎样估算模型状态

采用一种常见但并非唯一的配置：BF16权重2字节、BF16梯度2字节、FP32主权重4字节、Adam的一阶和二阶矩各4字节，则每参数约16字节。

70亿参数对应约112GB模型状态，约104.3GiB。这仍未计入激活与通信缓冲。有些实现使用FP32梯度、不保留独立主权重或采用不同优化器，必须重新计算，不能把16字节当成所有框架的固定值。

激活与批量、序列长度、层数和实现有关。激活检查点可以减少保存的中间结果，在反向传播时重新计算，以额外计算换取显存。

四种并行分别把什么分开

方式拆分对象主要通信或限制
DP，数据并行不同样本同步梯度，普通DP仍复制模型状态
TP，张量并行层内矩阵等张量层内通信频繁，依赖互联带宽
PP，流水线并行不同层或阶段传递激活与梯度，存在流水空泡
EP，专家并行MoE的不同专家Token分发与聚合，负载可能不均

DP适合模型已能放进单卡、希望提高训练吞吐的情况。普通DP不会因为卡数增加就自动把单卡权重变小。

TP将一个大矩阵的计算拆到多卡，Megatron-LM是相关代表实现。PP则让不同卡负责不同阶段，用微批次推动流水；如果阶段耗时不平衡或微批次太少，部分卡会等待。Megatron-LM论文

EP常用于MoE，后文会解释专家路由。多种并行可以组合，但并行维度的乘积、数据分配和通信组必须与真实设备数对应。

ZeRO怎样减少数据并行中的重复存储

ZeRO保留数据并行的处理方式，逐步分片模型状态：

  • ZeRO-1分片优化器状态。
  • ZeRO-2进一步分片梯度。
  • ZeRO-3进一步分片参数，计算需要时再获取相应部分。

它改变的是各卡长期保存哪些状态，并增加相应通信与调度。DeepSpeed ZeRO说明

按前面的16字节配置，用4卡做理想化估算：

方式每参数每卡模型状态7B对应十进制GB
普通DP16字节112
ZeRO-12+2+12/4=7字节49
ZeRO-22+(2+12)/4=5.5字节38.5
ZeRO-316/4=4字节28

这些只是分片后的模型状态项。临时聚合参数、通信桶、激活、内存对齐与峰值仍可能让实际占用更高。“理论28GB”不能直接作为28GB显卡可运行的保证。

卸载与梯度累积能解决哪些问题

Offload把部分状态放到CPU内存或NVMe，需要时再搬运，可降低GPU驻留空间，但增加传输与等待。小型ECS没有足够资源时，不能把模型训练简单转到它的内存或磁盘上。

梯度累积让多个微批次依次前向与反向，再统一更新。有效批量近似为每卡微批量×数据并行数×累积次数。它可以降低单次激活峰值，但不会把权重和优化器状态全部缩小。

训练吞吐还取决于通信拓扑、算子利用率和输入流水。更多卡可能被跨节点通信抵消，尤其是层内频繁通信的TP；方案应结合设备连接方式，而非只看卡数。

推理容量还要单独估算KV Cache

KV Cache大致随批量、序列长度、层数、KV头数和单头维度线性增长，计算方法见KV Cache。GQA减少KV头数能降低相应缓存，但不能消除长上下文带来的增长。

本篇全部为配置明确的资源估算，没有启动多卡训练、分布式通信或模型推理。小型服务器只承担文档与轻量计算，不用来验证大模型容量。

面试追问：BF16模型还有哪些显存开销

一个7B的模型，用BF16精度需要多少显存？还有可能有什么显存开销？存放在哪里？

回答：仅70亿参数的BF16权重约14GB，也就是13.04GiB。推理还需要GPU上的KV Cache、激活与工作区；训练还包括梯度、优化器状态和可能存在的FP32主权重。默认通常驻留在加速器内存，具体框架可通过状态分片、CPU/NVMe卸载改变位置，代价是通信或数据搬运。应区分权重大小、稳定占用与运行峰值。
