1d:T1f24,<h2 id="section-登录成功以后后续请求怎样证明身份">登录成功以后，后续请求怎样证明身份</h2>
<p>用户提交账号和密码，服务端验证成功后，需要让后续请求关联到这个用户。常见方案是生成一个随机会话ID，由服务端保存对应的登录状态，再通过Cookie把ID交给浏览器。</p>
<p>也可以签发包含身份声明的令牌，例如<strong>JWT（JSON Web Token）</strong>。JWT是一种承载声明的格式，其中可以包含签发者、用户标识、接收对象和过期时间。常见的签名JWT使用三段编码内容：Header、Payload和Signature，分别表示头部、声明数据和签名。</p>
<p><strong>能解析Payload，不等于已经验证令牌。</strong>Base64url编码不提供保密性，签名用于检查内容是否被篡改及其来源。需要保密时还要采用适合的加密方案，不能把密码或敏感资料直接塞进普通签名JWT。<a href="https://www.rfc-editor.org/rfc/rfc7519.html" rel="noopener noreferrer">JWT规范</a></p>
<p>JWT和Cookie也不属于同一层：JWT描述令牌内容，Cookie描述浏览器保存和发送数据的一种机制。JWT可以放在Cookie里，会话ID也可以通过其他约定传递。</p>
<h2 id="section-一个修改资料请求经过哪些校验">一个修改资料请求经过哪些校验</h2>
<p>假设浏览器请求<code>PATCH /users/7/profile</code>。服务端的处理顺序可以理解为：</p>
<div class="code-block"><div class="code-toolbar"><span>text</span><button type="button" data-copy-code="true" aria-label="复制代码">复制代码</button></div><pre><code class="hljs language-text">提取凭证
 → 验证可信签发方、签名算法与签名
 → 验证有效期和目标服务
 → 确认用户与会话状态
 → 检查用户能否修改users/7
 → 校验字段并执行修改
</code></pre></div>
<p><strong>认证</strong>回答“请求对应谁”，<strong>授权</strong>回答“这个身份能操作什么”。用户8持有合法令牌，并不意味着可以修改用户7的资料。服务端应从已验证的身份与权限规则判断资源归属，不能仅信任URL或请求体里的<code>user_id</code>。</p>
<p>签名校验还要固定允许的算法和可信密钥来源，验证<code>iss</code>（签发者）、<code>aud</code>（目标接收方）、<code>exp</code>（过期时间），并按协议处理<code>nbf</code>（生效时间）等声明。不能让来历不明的令牌头部任意决定密钥下载地址，或用一个服务的合法令牌访问另一个服务。<a href="https://www.rfc-editor.org/rfc/rfc8725.html" rel="noopener noreferrer">JWT安全实践</a></p>
<h2 id="section-jwt到期前退出登录能不能立即生效">JWT到期前，退出登录能不能立即生效</h2>
<p>假设访问令牌有效期15分钟，用户在第2分钟退出。如果退出只删除浏览器里的令牌，已经复制出去的那份仍可能通过签名和有效期校验。</p>
<p>因此要先确定退出的要求。允许访问令牌短时间继续有效，可以采用短有效期配合撤销刷新凭证；要求立即失效，则需要服务端检查会话版本、撤销列表或其他状态。<strong>无状态验签与立即撤销之间存在成本取舍</strong>，增加撤销能力通常意味着额外状态与查询。</p>
<p>刷新令牌用于换取新的访问令牌，需要单独设计生命周期、存储和撤销。轮换时还要考虑并发刷新：同一个旧刷新凭证被两个请求使用，服务端怎样原子识别、怎样处理合法并发与疑似重放，都要在实现中明确。本文只说明边界，不提供自行实现签名或密码学的代码。</p>
<h2 id="section-csrf为什么和浏览器自动发送cookie有关">CSRF为什么和浏览器自动发送Cookie有关</h2>
<p><strong>CSRF（Cross-Site Request Forgery，跨站请求伪造）</strong>指攻击者诱导已登录用户的浏览器，对受信任网站发送非用户本意的请求。</p>
<p>用一个简化场景理解：用户已经登录A站，浏览器保存了A站的会话Cookie。随后打开了不可信页面，页面尝试向A站提交修改资料的表单。如果这个请求符合浏览器发送Cookie的规则，A站可能收到一个携带有效登录凭证、却并非用户主动发起的操作。</p>
<p>攻击者不一定需要读取Cookie或响应内容。<strong>危险发生在服务端把“携带登录凭证”直接当成“用户同意执行这个操作”。</strong>同源策略主要限制跨源读取能力，不能据此假定所有跨站请求都不会到达服务器。</p>
<p>如果前端显式在Authorization头里携带令牌，外部站点通常无法凭空得到这个头中的值，经典的Cookie自动携带型CSRF条件会不同。但脚本注入、错误的跨源配置和令牌泄露仍需分别处理。</p>
<h2 id="section-csrf防护的几层检查">CSRF防护的几层检查</h2>
<p>对改变状态的接口，可以使用框架提供的<strong>CSRF Token</strong>：服务端要求请求携带一个与当前会话绑定、攻击站点无法取得的随机值，并校验它。采用双提交Cookie方案时，应使用经过正确绑定与签名设计的实现，避免只比较两个可被注入的值。</p>
<p>再配合Origin/Referer来源校验、合适的SameSite策略和安全Cookie属性。<code>HttpOnly</code>限制脚本读取Cookie，<code>Secure</code>限制其在安全传输中发送，二者都不直接证明一次状态修改由用户同意。<a href="https://cheatsheetseries.owasp.org/cheatsheets/Cross-Site_Request_Forgery_Prevention_Cheat_Sheet.html" rel="noopener noreferrer">OWASP CSRF防护</a></p>
<p>SameSite中的site与完整origin不是同一个概念，同一主域下的不同子域也需要检查信任边界。<code>SameSite=Lax</code>允许部分顶层导航携带Cookie，所以GET接口应保持安全方法语义，不能用一个链接完成转账或删除。</p>
<p>对高风险操作，还可以要求再次确认身份或使用操作级确认。CORS用于控制跨源访问策略，不能笼统代替CSRF防护。</p>
<h2 id="section-用小样本验证身份和授权边界">用小样本验证身份和授权边界</h2>
<p>本篇没有运行登录服务。实现时至少应覆盖这些结果：过期或签名错误的令牌被拒绝；签名正确但aud不匹配仍被拒绝；用户8不能修改用户7；缺少有效CSRF凭证的Cookie会话修改请求被拒绝；合法同源请求按预期成功；退出后的旧令牌按已声明的撤销策略处理。</p>
<p>这些检查针对不同层，不能仅凭“登录成功且能修改资料”判断整个鉴权流程正确。日志也只记录必要的错误类别和请求关联信息，避免保存完整令牌。</p>
<h2 id="section-面试追问csrf到底利用了什么">面试追问：CSRF到底利用了什么</h2>
<p><span id="q-FQ-doxcnKjXHjYmxL3TkeamDl3NCMh" class="legacy-anchor" aria-hidden="true"></span><a id="user-content-q-FQ-doxcnKjXHjYmxL3TkeamDl3NCMh"></a></p>
<blockquote>
<p>什么是 CSRF 攻击？</p>
</blockquote>
<p><strong>回答：</strong>攻击者诱导用户浏览器向目标网站发送请求，利用浏览器在某些情况下自动携带已有凭证的行为，让服务端执行非用户本意的操作。防护重点是验证状态修改请求的来源和会话绑定凭证，使用CSRF Token、Origin检查及合适的SameSite策略，并保持GET等安全方法不修改业务状态。仅有合法Cookie、HTTPS或HttpOnly都不足以说明请求获得了用户授权。</p>
<p><strong>自拟追问：JWT是否天然防止CSRF？</strong>不能只根据令牌格式判断。JWT放在自动携带的Cookie中时，仍需考虑相同的CSRF条件；如果显式放入Authorization头，则要结合令牌可获取性和跨源策略分析。</p>
