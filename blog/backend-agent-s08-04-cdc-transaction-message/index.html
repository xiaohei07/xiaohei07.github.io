数据库和消息队列之间，缺的是哪一步保证

Outbox与幂等消费介绍过一种写法：把业务数据和待发送事件放进同一个数据库事务，再由另外的程序发送事件。这样，订单提交后即使发送程序退出，数据库中仍然留着需要发送的记录。

接下来需要解决的是，发送程序怎样发现已经提交的事件，以及发生中断后从哪里继续。一种办法是定期查询Outbox表；另一种办法是读取数据库的变更日志。这种从数据源捕获新增、修改和删除的方式，叫作CDC（Change Data Capture，变更数据捕获）。

CDC可以同步普通业务表，也可以专门订阅Outbox表。两者提供的含义有所不同：订单表的一次字段更新描述“数据变了”，Outbox中的OrderPaid事件则可以明确表达“订单已支付”，并携带业务版本、事件ID和发生时间。

从数据库日志到消费者的完整过程

以MySQL、Debezium和Kafka的组合为例，教学数据流可以写成：

text
本地事务：更新订单 + 插入Outbox事件
       ↓ COMMIT
MySQL binlog中的已提交变更
       ↓ 连接器读取并记录进度
转换为带event_id和order_id的消息
       ↓
Kafka分区 → 消费者业务事务 → 提交消费进度

这里的进度是读到了数据源的什么位置，不能只用“最后成功时间”代替。相同时间内可能有多次更新，数据库重启或故障切换也需要使用连接器支持的日志位置、GTID等恢复信息。Debezium的MySQL连接器还需要维护理解历史事件所用的表结构信息；日志位置正确而表结构解释错误，同样无法可靠恢复。Debezium MySQL连接器

首次接入时，旧数据已经存在，日志也可能只保留了最近几天。通常需要快照与后续日志衔接：先建立某个一致性位置对应的数据视图，再继续处理该位置之后的变更。具体快照模式、锁和并发限制要按连接器版本配置，不能直接用“导出表，然后开始订阅”来假定没有空档。

对Outbox事件，event_id负责识别同一件事，order_id可以作为消息Key，把同一订单的事件送入同一个分区。去重标识与分区标识的目的不同。Debezium的Outbox Event Router也区分事件ID与聚合对象ID；是否采用默认字段名，需要与应用表结构对应。Outbox Event Router

连接器恢复以后，为什么仍可能收到重复消息

假设事件E17已经发送到消息队列，发送结果也已经确认，但连接器还没来得及持久保存最新读取进度就退出。恢复后再次读取E17，就可能再次发送它。

因此，消费端可以在一个本地事务中完成：

text
检查并登记event_id=E17
更新订单对应的下游业务状态
提交事务

去重记录与业务修改必须一起成功或一起回滚。先登记“已消费”再单独修改业务，第二步失败后会把真正需要执行的消息当成重复消息跳过。外部支付或发送短信等操作，还需要相应服务支持幂等键或可查询的执行状态；数据库事务无法把外部请求自动纳入原子提交。

还有一种恢复失败更难发现：连接器暂停太久，尚未读取的binlog已经过期。这时不能直接移动进度跳过缺口。应根据业务可接受的恢复方式重新建立快照、补读或对账，并检查缺失的历史事件是否还能从业务记录重建。

RocketMQ事务消息怎样使用本地事务结果

RocketMQ事务消息采用另一条路径：先将消息交给Broker，暂时不允许消费者读取；再执行本地事务，根据结果决定消息是否可以投递。这个暂不可消费的消息通常叫作半消息。

时刻本地业务Broker中的消息
发送半消息成功尚未提交消费者不可见
本地事务提交订单已落库等待提交确认
提交确认送达已提交可以投递
确认丢失可能已提交通过事务回查确认

事务回查就是Broker向生产者询问对应本地事务的最终结果。生产者应查询可以持久保存的业务状态或事务记录，不能只查某个进程内变量。RocketMQ也明确要求，正在执行的事务应返回Unknown，避免过早作出提交或回滚决定。RocketMQ事务消息机制

例如订单O8的数据库事务已经提交，但提交消息的网络请求超时。回查通过O8的事务记录确认成功，就可以让消息继续投递。反过来，“查询暂时没找到记录”不一定等于“事务已回滚”：事务可能尚未结束，读取的副本也可能有延迟。回查的数据源和状态模型必须能够区分这些情况。

事务消息有回查次数、超时等运行边界。如果长期无法确认，本地状态与消息状态仍需对账和补偿，不能把回查理解成无限等待且必然恢复。

两种方案应该怎样选择

已经使用数据库事务、又希望业务代码与消息发送解耦时，Outbox通常便于说明正确性。轮询实现较直接，需要处理扫描成本；CDC降低反复扫描的需要，同时增加连接器、日志保留、Schema变更与恢复运维工作。

已有RocketMQ事务消息能力，并且能提供可靠的事务回查逻辑时，可以围绕半消息与回查组织实现。两种路径都要继续考虑下游幂等、重试期限和失败对账。消息已经可以消费，只说明上游的消息发布条件成立，下游业务是否完成需要另外确认。

本篇没有启动Debezium、Kafka或RocketMQ。验证重点是下面的故障推演：业务提交前失败不应产生有效事件；业务提交后发送失败必须可恢复；发送成功但进度未保存允许重复，不能丢失；消费业务提交后确认丢失必须能安全重放。

面试追问：事务消息保证到哪一层

RocketMQ 事务消息的原理。

回答：先发送消费者不可见的半消息，再执行本地事务。生产者根据事务结果提交或回滚消息；如果Broker没有得到明确结果，就触发事务回查，由生产者查询持久化状态后返回结果。这个机制协调的是本地事务和消息发布，适合允许异步完成的业务。消费侧仍然要处理重复投递、失败重试和业务幂等，不能据此断言上下游同时完成。

自拟追问：已经有事务消息，为什么还需要对账？网络故障可能持续超过重试窗口，回查逻辑可能有缺陷，下游也可能发生无法自动恢复的业务错误。对账根据业务ID比较应有状态与实际状态，用于发现并处理这些长期未收敛的情况。
