在浏览器里打开一篇文章，看起来只做了一件事：输入网址，然后等页面出来。不过网页里的HTML、样式、脚本和图片通常要分别获取。后面点击“发送反馈”，浏览器又会发出新的请求，这次服务器返回的是JSON数据。

先把这两个过程分清，后面再看Next.js和FastAPI的分工就会容易一些。下面用本站的文章与反馈举例，请求中的内容是教学数据。

URL怎样确定要访问的资源

例如https://blog.07xiaohei.com/blog/python-slices/，https指定协议，blog.07xiaohei.com是主机名，/blog/python-slices/是路径。HTTPS默认使用443端口，所以网址里通常不用再写:443。查询参数放在?后面；#后面的片段用于定位页面内部位置，一般不会随HTTP请求发给服务器。

浏览器需要先确定域名对应的地址。DNS负责域名解析；连接建立后，再按协议交换数据。HTTPS还要建立经过身份验证的加密连接，浏览器会检查证书是否适用于访问的域名。DNS、连接、TLS、HTTP属于不同层次，排错时也应分别确认。

连接不一定每次重新建立，DNS结果也可能被缓存。因此，“打开网页必定从头做一遍全部步骤”只是简化模型。HTTP/1.1和HTTP/2通常使用TCP；HTTP/3使用基于UDP的QUIC。本文用HTTP/1.1的文本形式展示报文，便于阅读，不代表实际线上协议一定是这个版本。

请求和响应各自包含什么

读取文章的简化请求如下：

http
GET /blog/python-slices/ HTTP/1.1
Host: blog.07xiaohei.com
Accept: text/html

GET是方法，说明当前要取得资源；路径指定资源；Host让服务器知道要处理哪个站点。响应可以写成：

http
HTTP/1.1 200 OK
Content-Type: text/html; charset=utf-8
Cache-Control: no-cache

<!doctype html>
<html>...</html>

状态码描述请求结果，响应头补充内容类型、缓存等信息，空行之后是响应体。Content-Type帮助浏览器解释这些字节；同一个服务器可以返回HTML、JSON、图片或其他格式。MDN的HTTP说明介绍了这套请求与响应模型。

读取HTML后，浏览器构建DOM，解析CSS并计算布局，再进行绘制；脚本还可能修改页面或继续获取数据。这些工作会交错进行，图片和脚本也可能并行下载。把所有资源下载时间相加，并不能直接得到页面总加载时间。

从读文章到提交反馈，数据在哪里变了

假设给文章提交一条“切片例子建议补充边界说明”的反馈，浏览器把输入组织成JSON：

http
POST /api/v1/feedback HTTP/1.1
Content-Type: application/json
Origin: https://blog.07xiaohei.com

{"content_id":"python-slices","kind":"question","message":"切片例子建议补充边界说明"}

JSON是文本格式，里面的字段还需要后端检查。服务器不会因为字段名叫content_id就自动知道它是一篇已发布文章；也不会因为请求带了Origin就知道发送者是谁。

本站中，Nginx把/api/请求转给FastAPI。通过校验并成功提交数据库事务后，API返回201，以及新反馈的ID和pending状态。前端读取回执，再把页面上的提示改成发送成功。正文页面早已存在，这次更新不需要重新构建文章HTML。

观察位置能看到的内容不能直接推出的结论
输入框用户当前填写的字符串数据已经保存
Network请求体浏览器尝试发送的JSONAPI已经收到或提交
201响应API按接口约定返回创建成功作者已经阅读或审核
数据库记录对应反馈及其状态浏览器一定收到回执

最后一行尤其值得留意：数据库提交之后，响应仍可能在网络中丢失。客户端超时与服务器没有写入，并不是同一个事实。

HTTP状态码怎样帮助排查

本站反馈链里，422可能表示输入字段不符合要求，也可能表示内容ID不存在；429表示触发频率限制；503表示依赖暂时不可用。网关联系不到API时还可能返回502，等待上游超时可能返回504。具体原因要结合响应来自哪一层和对应日志判断。

fetch收到404、422或500时，通常仍会取得一个Response对象。只有请求层面的失败等情况才会进入拒绝分支，所以代码要主动检查response.ok。这一点会在异步JS与Fetch中继续展开。

HTTP无状态，指协议本身不会自动把两次请求归为同一个登录用户。网站可以通过Cookie和服务端会话保存这种关联。HTTP缓存也不等于登录状态：缓存复用资源，会话识别身份，这两者要分别设计。

HTTPS解决了什么，还有什么要靠应用检查

HTTPS保护浏览器与TLS终止点之间传输的机密性、完整性，并帮助验证服务器身份。在本站，外部HTTPS由入口服务器处理，内部代理链仍要控制可访问范围。

加密不会替应用检查“这篇文章是否存在”“当前用户能否审核”“SQL有没有拼接用户输入”。同样，页面上出现小锁图标，也不能证明页面引用的所有逻辑都正确。浏览器安全和API权限会在Cookie、CORS与CSRF中分开说明。

可以在开发者工具的Network中做一个只读观察：打开文章，筛选Document看首个文档响应，再筛选Img和JS观察资源；打开站内搜索，查看是否新增JSON请求。不要为了验证流程随意向生产反馈接口提交测试数据。本系列提供的交互推演会直接展示这两条路线。
