根据数据操作选择Redis类型

Redis把数据组织为键及对应的值。值可以是字符串，也可以是Hash、List、Set、Sorted Set等结构。比如任务摘要可以保存为字符串，多个任务属性可以放进Hash；需要按时间或分数取一段成员时，可以考虑Sorted Set。

数据类型规定可执行的操作，内部编码负责怎样存储这些数据。 相同类型可能根据数据规模、元素大小和Redis版本使用不同编码，不能把“Hash类型”直接等同于某一种永远不变的底层结构。选择类型以后，还要检查命令复杂度、单个大键的处理成本及实际内存占用。Redis数据类型

例如“最新的10个任务”涉及排序，“任务ID是否存在”涉及成员查找，“各字段怎样局部更新”涉及字段访问。把所有数据序列化进一个大JSON虽然容易开始，但更新一个字段可能需要读取、解析再写回整个值，并且要另行处理并发覆盖。

RDB保存某个时间点的数据集，AOF记录后续修改

RDB保存数据集的时间点快照。加载时可以从快照重建状态，文件也便于按一定周期备份。仅依靠这份快照恢复时，只能恢复到快照记录的状态，之后的新修改需要其他恢复依据。

AOF（Append Only File）通过追加记录保存写操作相关信息，恢复时据此重建数据。一条记录需要依次经历追加到AOF缓冲、写入操作系统、完成fsync等阶段；具体配置决定何时将记录推进到持久存储。

AOF刷盘策略主要取舍
always更频繁地等待刷盘，可结合批处理；延迟与吞吐取决于负载和存储
everysec通常按秒进行后台刷盘，在性能与可能丢失最近写入之间取舍
no由操作系统决定刷盘时机，失去更明确的应用侧控制

“everysec”描述刷盘策略，不能承诺任何存储故障下都严格最多丢1秒。后台调度、阻塞和设备故障会影响实际边界。Redis7开始的多部分AOF组织方式也不同于旧版本单文件直觉，配置与恢复步骤应按实际版本核对。Redis持久化文档

库存变化示例：不同持久化进度下的恢复结果

下面只作教学推演，假设每次持久化都真实成功：

时间事件
t0RDB成功保存，库存为10
t1扣减1，内存变成9；相应AOF已经fsync
t2再扣减1，内存变成8；相应AOF仍未完成持久化
t3发生断电，无法依赖易失缓存

若只能使用t0的快照，恢复依据是库存10。若有完整有效的AOF，至少已经持久化到t1，那么可以恢复到9；t2是否保留下来需要看实际保存状态，不能只凭Redis曾向客户端回复成功判断。

如果业务数据库已经确认两笔扣减，而Redis恢复成9，就要按业务数据和变更记录重建缓存，不能让缓存值直接覆盖数据库。缓存恢复、业务账目恢复和消息补发分别需要自己的权威依据。 两套数据如何保持一致，见缓存与数据库的更新时序。

异步复制、WAIT确认与故障接管

复制把主节点的变更传播给副本，能支持读扩展和故障接管。Redis默认采用异步复制：主节点已经回复成功的写入，副本可能还没有收到。此时主节点故障，提升一个落后的副本，就可能丢失最近确认过的写入。

WAIT可以等待此前写入得到指定数量副本的确认，减少某些故障下的风险；副本确认并不自动把Redis变成强一致系统，也不等于每份数据都已按预期持久化。 恢复结果仍受副本持久化、故障组合和接管选择影响。Redis复制与WAIT的边界

持久化、复制、备份因此需要分别验收：能否重启恢复、丢失一个节点后能否继续服务、能否回到误操作前的数据，这三种故障不是同一件事。

大键、热点和持久化过程中的资源压力

热点键承受大量访问，大键则在体积或成员数量上很大，两者可能重合，也可能完全不同。排查时需要分别看命令延迟、传输量、内存和访问分布。

快照或AOF重写也会占用CPU、内存及磁盘资源。这些后台操作仍会与前台请求共享资源，应结合写入速率、写时复制导致的内存增长和磁盘延迟观察影响。恢复后若大量键同时缺失，回源也应限流并合并相同键的重建请求，避免下游数据库承受突发压力。副本数量与重建流量需要分别规划。

面试问答：Redis持久化

redis持久化

回答： Redis常见持久化方式为RDB快照与AOF记录。RDB保存某个时间点的数据集，恢复较直接，但两个快照之间的写入可能丢失；AOF保留写操作相关记录，恢复粒度受追加及fsync策略影响，需要考虑文件增长、重写和恢复耗时。实际可组合使用，并按所用Redis版本验证恢复规则。

选择时先明确数据角色和可接受损失。如果Redis只是可重建缓存，重点可能是恢复速度、回源压力和内存容量；如果保存不能轻易丢失的状态，就必须验证持久化、复制和备份策略的共同边界。客户端收到成功响应，不自动证明写入已在所有故障场景下安全。

例如RDB在库存10时生成，随后两次扣减中只有一次AOF记录持久化，断电后不同恢复依据可能得到10或9，不能凭内存故障前为8就承诺恢复到8。也要验证恢复结果与数据库、消息及业务操作ID如何对账。

延伸追问（自拟）：有副本就可以关闭持久化吗？ 需要按故障模型判断。异步副本会落后，也可能与主节点同时失去内存数据。副本解决的是复制和接管能力，是否需要持久化与备份仍由可接受的数据损失和恢复目标决定。
