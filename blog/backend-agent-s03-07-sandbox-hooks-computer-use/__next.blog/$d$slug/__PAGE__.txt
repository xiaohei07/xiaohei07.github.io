25:T1f3c,<span id="section-模型提出操作以后谁来限制实际能力" class="legacy-anchor" aria-hidden="true"></span><h2 id="section-宿主工具hook与沙箱的执行职责">宿主工具、Hook与沙箱的执行职责</h2>
<p>Coding Agent可能修改文件、运行测试、下载依赖，也可能通过界面点击按钮。模型生成的是下一步动作，真正执行动作的是宿主提供的工具与运行环境。</p>
<p><strong>沙箱</strong>通过系统机制限制进程能访问的资源；<strong>Hook</strong>是在某个执行时机运行的检查或处理逻辑。两者作用不同：Hook可以检查一次操作是否符合任务规则，沙箱则限制操作即使进入执行阶段也不能越过的边界。</p>
<p>例如任务只允许修改一个项目目录，Hook可以检查目标路径，沙箱还应从文件系统权限或挂载方式限制目录外写入。<strong>路径规则需要同时体现在操作检查与实际文件访问权限中</strong>，模型说明则帮助理解任务范围。</p>
<span id="section-文件网络与系统调用分别怎样隔离" class="legacy-anchor" aria-hidden="true"></span><h2 id="section-文件系统网络与系统调用的隔离">文件系统、网络与系统调用的隔离</h2>
<p>文件系统可以只挂载必要工作区，把其他路径设为不可见或只读，并使用非特权用户。路径判断要处理规范化、符号链接和执行时变化，并按最终解析和访问的目标确认权限。</p>
<p>网络可以默认关闭，或只允许访问完成任务所需的服务。需要安装依赖时，网络策略应与包来源、代理及凭证分离，避免把整个宿主网络权限直接交给执行进程。</p>
<p>Linux的<strong>seccomp限制系统调用，namespace隔离资源视图，capability拆分进程特权，cgroup约束和统计资源用量</strong>，容器可组合使用这些机制。Docker的默认seccomp配置提供一组限制，但不是对所有不可信程序都充分的隔离方案。<a href="https://docs.docker.com/engine/security/seccomp/" rel="noopener noreferrer">Docker seccomp说明</a></p>
<p><strong>容器与宿主共享内核。</strong>对威胁更高的代码，可能需要虚拟机或更强隔离环境；具体选择取决于攻击面、启动成本和维护能力。选择后需要在隔离测试环境中检查具体限制是否生效。</p>
<span id="section-hook适合检查什么" class="legacy-anchor" aria-hidden="true"></span><h2 id="section-执行前与执行后hook的检查内容">执行前与执行后Hook的检查内容</h2>
<p>执行前Hook可以检查工具名称、参数、路径与当前授权；执行后Hook可以收集退出状态、测试摘要和产物位置。它也可以阻止明显不符合范围的操作，要求进入已有的审批流程。</p>
<p>例如一次保存操作已经获得授权，但目标路径改到了另一个项目。执行前检查应该识别这是不同的写入对象，而不是因为前面有过一次批准就全部放行。</p>
<p>Hook失败时的策略要明确。关键权限检查报错后应阻止操作；可选日志采集失败则可以按业务规则降级。若Hook自身能运行Shell命令，它也需要受控配置与权限，不能加载来自待审代码仓库的任意脚本作为可信规则。</p>
<p>Hook可以记录<strong>权限检查、退出码和产物位置</strong>。确认功能是否满足要求时，还需要把实际输出与任务预期对应起来，例如检查生成文件的内容或接口返回的数据。</p>
<span id="section-computer-use为什么需要观察动作后的状态" class="legacy-anchor" aria-hidden="true"></span><h2 id="section-computer-use的观察操作与结果确认">Computer Use的观察、操作与结果确认</h2>
<p><strong>Computer Use</strong>通过截图、可访问性信息或浏览器界面结构观察页面，再执行点击、输入等动作。它适合没有可用API、必须与已有界面交互的场景。</p>
<p>界面会变化：页面加载后按钮位置可能移动，弹窗可能挡住原目标，输入框可能失去焦点。因此动作应基于新近观察，并在关键步骤后读取结果。直接复用几分钟前的坐标，可能点到另一个按钮。</p>
<p>可以把过程写成：</p>
<div class="code-block"><div class="code-toolbar"><span>text</span><button type="button" data-copy-code="true" aria-label="复制代码">复制代码</button></div><pre><code class="hljs language-text">读取当前界面
 → 识别具体对象与操作条件
 → 执行一个动作
 → 观察是否出现预期状态
 → 决定继续、重试或停止
</code></pre></div>
<p>如果点击“提交”以后没有明显响应，应先检查任务或记录是否已创建，再决定重试。否则双击或重复提交可能产生两份外部结果。</p>
<span id="section-页面内容能不能给执行工具下指令" class="legacy-anchor" aria-hidden="true"></span><h2 id="section-外部页面内容与真实任务授权的区分">外部页面内容与真实任务授权的区分</h2>
<p>网页、文件和工具返回内容可以包含恶意指令。Agent需要把它们当作待处理资料，不能让页面上的文字提升操作权限或要求发送凭证。</p>
<p>界面中的登录会话提供账户访问能力，<strong>当前任务授权决定本次可以操作哪些对象</strong>。执行时需要把目标、动作和可能产生的真实修改与授权范围对应起来。</p>
<p>对于修改文件，可以保留差异与测试结果；对于界面写操作，可以记录提交对象、操作时间和返回状态。记录应去除敏感凭证，不把完整浏览器会话或无关个人数据复制到日志。</p>
<span id="section-小型实验怎样限制资源" class="legacy-anchor" aria-hidden="true"></span><h2 id="section-小型隔离实验的资源范围与检查对象">小型隔离实验的资源范围与检查对象</h2>
<p>机制验证可以只使用一个临时目录、一个很小的文件和一个受限进程：尝试读取允许文件、写入允许路径，确认拒绝路径被阻止，再验证超时后子进程是否结束。网络隔离则用模拟目标或明确授权的测试服务检查。</p>
<p>除了内存与CPU，还要限制进程数、输出长度、文件总量与运行时间。单次命令只使用少量内存，也可能通过创建大量子进程耗尽机器资源。</p>
<p>普通进程与I/O实验用于观察程序行为；验证沙箱时则要分别检查访问拒绝、子进程约束和资源回收，Computer Use还需要沿实际界面操作观察结果。这些检查分别针对不同的执行机制。</p>
<span id="section-面试追问shell执行怎样隔离" class="legacy-anchor" aria-hidden="true"></span><h2 id="section-面试追问shell执行的文件网络与系统隔离">面试追问：Shell执行的文件、网络与系统隔离</h2>
<p><span id="q-FQ-doxcnv1gmCxLUIFSc7MtcFxf3Dc" class="legacy-anchor" aria-hidden="true"></span><a id="user-content-q-FQ-doxcnv1gmCxLUIFSc7MtcFxf3Dc"></a></p>
<blockquote>
<p>Coding Agent 执行 Shell 命令时如何隔离文件系统、网络和系统调用？</p>
</blockquote>
<p><strong>回答：</strong>在受限用户与独立运行环境中执行，只暴露必要工作目录，限制其他路径读写；网络采用默认拒绝或受控出口；系统调用与特权通过seccomp、capability等机制限制，并设置CPU、内存、进程数、磁盘和时间预算。执行前再检查命令与任务授权，执行后收集真实结果。对更高风险代码采用更强隔离，不能只依赖提示词或一个路径字符串检查。</p>
<p><strong>自拟追问：有Hook以后还需要沙箱吗？</strong>需要根据风险配置系统隔离。Hook容易受参数解析、竞态或自身错误影响，系统边界能够限制漏检之后的实际能力。</p>
