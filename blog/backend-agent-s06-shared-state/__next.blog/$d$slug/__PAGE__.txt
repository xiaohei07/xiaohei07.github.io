27:T1bf0,<h2 id="section-同一个变量被两个线程使用要检查哪些关系">同一个变量被两个线程使用，要检查哪些关系</h2>
<p>线程共享内存以后，正确性不能只看单个函数从上到下的代码。一个线程的写入是否能按要求被另一个线程观察到，是<strong>可见性</strong>问题；几个动作是否作为不可分割的整体发生，是<strong>原子性</strong>问题。编译器和处理器允许怎样调整执行，还要服从语言的<strong>内存模型</strong>。</p>
<p>本文使用Java21的语言规则。JMM是Java Memory Model的简称，它描述允许观察到哪些行为，不要求所有机器采用同一种缓存实现。把它解释成“每个线程都有一个装着全部变量副本的小仓库”，容易把教学比喻误当成硬件事实。</p>
<h2 id="section-happens-before怎样连接生产者与消费者">happens-before怎样连接生产者与消费者</h2>
<p><strong>happens-before</strong>规定操作之间的可见性与顺序关系。Java的程序内顺序、同一监视器的解锁与后续加锁、volatile写与后续读等，都能建立相关关系，并通过传递性连接更早和更晚的操作。<a href="https://docs.oracle.com/javase/specs/jls/se21/html/jls-17.html#jls-17.4.5" rel="noopener noreferrer">Java21内存模型</a></p>
<p>下面是一次发布的示意，省略线程启动代码：</p>
<div class="code-block"><div class="code-toolbar"><span>java</span><button type="button" data-copy-code="true" aria-label="复制代码">复制代码</button></div><pre><code class="hljs language-java"><span class="hljs-type">int</span> <span class="hljs-variable">answer</span> <span class="hljs-operator">=</span> <span class="hljs-number">0</span>;
<span class="hljs-keyword">volatile</span> <span class="hljs-type">boolean</span> <span class="hljs-variable">ready</span> <span class="hljs-operator">=</span> <span class="hljs-literal">false</span>;

<span class="hljs-comment">// 生产者，仅发布这一次</span>
answer = <span class="hljs-number">42</span>;
ready = <span class="hljs-literal">true</span>;

<span class="hljs-comment">// 消费者</span>
<span class="hljs-keyword">if</span> (ready) {
    use(answer);
}
</code></pre></div>
<p>生产者先写answer，再写volatile标志。消费者观察到这次<code>ready = true</code>后，再读取answer，通过volatile建立的同步关系和程序顺序，可以观察到发布前的42。这里需要明确“一次发布，之后没有别的线程继续改answer”等前提。</p>
<p>这个规则没有承诺消费者一定在某个时限内获得调度，也没有把读取判断改造成等待通知。如果要持续传递多条消息，单个布尔标志会丢失次数和顺序信息，更适合使用队列或明确的同步协议。</p>
<h2 id="section-volatile自增为什么可能丢失一次更新">volatile自增为什么可能丢失一次更新</h2>
<p>假设<code>volatile int count = 0</code>，两个线程各执行一次<code>count++</code>。自增包含读取、计算和写回：</p>






























<table><thead><tr><th>时刻</th><th>线程A</th><th>线程B</th></tr></thead><tbody><tr><td>t1</td><td>读取0</td><td></td></tr><tr><td>t2</td><td></td><td>读取0</td></tr><tr><td>t3</td><td>计算1并写回</td><td></td></tr><tr><td>t4</td><td></td><td>计算1并写回</td></tr></tbody></table>
<p>最终count为1。每次读写都可以满足volatile语义，但<strong>“读—改—写”整体没有因此获得原子性</strong>。另一次调度也可能得到2，因此一次运行成功不能证明没有竞争。</p>
<p>如果只是一个计数器，可以使用<code>AtomicInteger.incrementAndGet()</code>提供原子更新。如果修改涉及“余额减少”和“可用额度增加”两个字段，需要保护二者共同构成的不变量，分别换成两个原子变量仍可能让其他线程观察到中间状态。</p>
<h2 id="section-synchronized与cas分别怎样协调修改">synchronized与CAS分别怎样协调修改</h2>
<p><strong>synchronized</strong>让同一监视器保护的临界区互斥执行，并提供相应可见性。只有参与者遵守同一保护协议，才能共同维护不变量。若读取方直接绕过锁读取多个字段，就不能自动得到完整一致的快照。</p>
<p><strong>CAS（Compare-And-Set）</strong>根据当前值是否仍等于预期值，决定是否更新。两个线程同时想把0改成1时，只有其中一个能以“预期0”成功，另一个应重新读取并决定是否重试。具体原子类的内存语义以API为准，不把所有弱CAS或不同访问模式当成相同保证。<a href="https://docs.oracle.com/en/java/javase/21/docs/api/java.base/java/util/concurrent/atomic/package-summary.html" rel="noopener noreferrer">Java21原子类</a></p>
<p>CAS循环可能在竞争下反复失败；值由A变成B再回到A时，单纯比较值也看不出中间变化，这就是常说的ABA问题。需要关注变化历史时，可以结合版本信息。无锁算法还要单独证明进展性，不能因为使用CAS就承诺每个线程在有限次数内成功。</p>
<p>锁和原子操作都需要限定范围。本机线程锁无法保护另一台机器上的写入；跨实例的业务修改需要数据库条件更新、版本协议或其他协调机制，见<a href="/blog/backend-agent-s07-transactions/">事务领取任务</a>。</p>
<h2 id="section-面试问答volatile的作用">面试问答：volatile的作用</h2>
<p><span id="q-FQ-doxcnmQMnNfYkP6oPVFzGGZfenf" class="legacy-anchor" aria-hidden="true"></span><a id="user-content-q-FQ-doxcnmQMnNfYkP6oPVFzGGZfenf"></a></p>
<blockquote>
<p>volatile的作用</p>
</blockquote>
<p><strong>回答：</strong> Java中的volatile为该字段的访问提供可见性和有序性相关保证：对volatile字段的写，与同步顺序中后续的读建立同步关系，结合程序顺序和传递性，可以用于安全发布部分状态。它不是互斥锁，不能把任意复合操作变成原子操作。</p>
<p>例如先写answer=42，再写volatile标志ready=true；读取方观察到这次true后读取answer，在没有后续竞争修改等前提下，可以得到发布的42。但count++包含读取、计算、写回，两个线程可能都读0再写1，所以volatile计数器仍可能丢更新。</p>
<p>适用场景包括独立状态标志和满足条件的发布协议。原子计数可以用AtomicInteger，多个字段共同约束的更新通常要使用锁或更完整的协议。volatile也不保证调度及时性，不应拿它代替超时、等待通知或跨机器协调。</p>
<p><strong>延伸追问（自拟）：把引用声明为volatile，里面的集合就线程安全了吗？</strong> 引用读写和对象内部修改是不同操作。volatile可以参与发布引用，但多个线程之后对集合的增删仍要使用合适的并发容器或同步方式。</p>
