共享变量的可见性、原子性与语言内存模型

线程共享内存以后，正确性不能只看单个函数从上到下的代码。一个线程的写入是否能按要求被另一个线程观察到，是可见性问题；几个动作是否作为不可分割的整体发生，是原子性问题。编译器和处理器允许怎样调整执行，还要服从语言的内存模型。

本文使用Java21的语言规则。JMM是Java Memory Model的简称，它规定线程之间允许观察到哪些行为，编译器和硬件实现需要满足这些规则。理解时应先看语言保证的可见性与顺序，再结合具体硬件分析。

happens-before关系与一次状态发布

happens-before规定操作之间的可见性与顺序关系。Java的程序内顺序、同一监视器的解锁与后续加锁、volatile写与后续读等，都能建立相关关系，并通过传递性连接更早和更晚的操作。Java21内存模型

下面是一次发布的示意，省略线程启动代码：

java
int answer = 0;
volatile boolean ready = false;

// 生产者，仅发布这一次
answer = 42;
ready = true;

// 消费者
if (ready) {
    use(answer);
}

生产者先写answer，再写volatile标志。消费者观察到这次ready = true后，再读取answer，通过volatile建立的同步关系和程序顺序，可以观察到发布前的42。这里需要明确“一次发布，之后没有别的线程继续改answer”等前提。

这套规则说明消费者读到ready后可以观察哪些写入；消费者何时获得调度，以及怎样等待通知，还需要其他调度和同步机制。如果要持续传递多条消息，单个布尔标志会丢失次数和顺序信息，更适合使用队列或明确的同步协议。

volatile自增中的读、改、写竞争

假设volatile int count = 0，两个线程各执行一次count++。自增包含读取、计算和写回：

时刻线程A线程B
t1读取0
t2读取0
t3计算1并写回
t4计算1并写回

最终count为1。每次读写都可以满足volatile语义，但“读—改—写”整体没有因此获得原子性。另一次调度也可能得到2，因此一次运行成功不能证明没有竞争。

如果只是一个计数器，可以使用AtomicInteger.incrementAndGet()提供原子更新。如果修改涉及“余额减少”和“可用额度增加”两个字段，需要保护二者共同构成的不变量，分别换成两个原子变量仍可能让其他线程观察到中间状态。

synchronized互斥临界区与CAS条件更新

synchronized让同一监视器保护的临界区互斥执行，并提供相应可见性。只有参与者遵守同一保护协议，才能共同维护不变量。若读取方直接绕过锁读取多个字段，就不能自动得到完整一致的快照。

CAS（Compare-And-Set）根据当前值是否仍等于预期值，决定是否更新。两个线程同时想把0改成1时，只有其中一个能以“预期0”成功，另一个应重新读取并决定是否重试。具体原子类的内存语义以API为准，不把所有弱CAS或不同访问模式当成相同保证。Java21原子类

CAS循环可能在竞争下反复失败；值由A变成B再回到A时，单纯比较值也看不出中间变化，这就是常说的ABA问题。需要关注变化历史时，可以结合版本信息。算法是否具备无锁或无等待等进展保证，需要单独分析，CAS本身只提供条件原子更新。

锁和原子操作都需要限定范围。本机线程锁无法保护另一台机器上的写入；跨实例的业务修改需要数据库条件更新、版本协议或其他协调机制，见事务领取任务。

面试问答：volatile的作用

volatile的作用

回答： Java中的volatile为该字段的访问提供可见性和有序性相关保证：对volatile字段的写，与同步顺序中后续的读建立同步关系，结合程序顺序和传递性，可以用于安全发布部分状态。它不是互斥锁，不能把任意复合操作变成原子操作。

例如先写answer=42，再写volatile标志ready=true；读取方观察到这次true后读取answer，在没有后续竞争修改等前提下，可以得到发布的42。但count++包含读取、计算、写回，两个线程可能都读0再写1，所以volatile计数器仍可能丢更新。

适用场景包括独立状态标志和满足条件的发布协议。原子计数可以用AtomicInteger，多个字段共同约束的更新通常要使用锁或更完整的协议。volatile也不保证调度及时性，不应拿它代替超时、等待通知或跨机器协调。

延伸追问（自拟）：把引用声明为volatile，里面的集合就线程安全了吗？ 引用读写和对象内部修改是不同操作。volatile可以参与发布引用，但多个线程之后对集合的增删仍要使用合适的并发容器或同步方式。
