多个副本之间的通信也会失败

把数据复制到多个节点后，一部分节点仍在运行，却可能无法与另一部分交换消息，这就是需要考虑的网络分区。节点无法仅凭超时立即区分对方崩溃、网络中断或暂时延迟。

假设A、B原来都保存x=0，通信中断后，客户端在A把x写成1并收到成功，再请求B读取x。B没有收到这次更新，接下来要怎样回答？

如果B立即按本地状态返回0，无法满足“已经完成的写之后开始的读要观察到相应新值”的要求；如果B等待通信恢复再确认，就不能保证分区期间每个到达正常节点的请求都能完成。这就是CAP讨论中的冲突。

CAP中的三个词各自指什么

C指线性一致性：操作表现得像在调用与返回之间某个时刻生效，并尊重真实时间上已经确定的先后关系。A指可用性：论文模型要求非故障节点收到的请求最终获得符合操作语义的响应，并非简单返回错误码也算成功。P指必须考虑消息因分区而丢失的执行情况。

在允许分区的异步网络模型中，不能同时保证所有这类执行下的C与A。它不是日常设计中任意勾选两个字母，也不把CAP的C等同于数据库ACID中的业务约束一致性。Gilbert与Lynch的定义和证明

具体业务可以选择不同范围的策略。例如库存扣减在无法确认最新状态时暂不接受，旧公告可以按允许的陈旧度继续展示。需要说明是哪个操作、什么故障下采用哪种响应，不能仅给整个系统贴一个字母标签。

Raft怎样让日志修改有共同顺序

共识让节点在给定故障模型下对一组决定达成一致。Raft用领导者组织复制日志，并把选举、日志复制及安全规则联系起来。任期（term）是逻辑编号，用于区分不同选举阶段和过时领导者。

以固定3个节点A、B、C为教学配置，多数派为2。A在当前任期接收“x改为1”，把日志项保存到自己并复制给B。满足Raft规则后，当前任期日志项已存于多数派，可以提交；C之后再追上。

若A单独被隔离，B、C可以在满足选举条件后产生新领导者。A即使暂时仍以为自己是领导者，也不能凭自己一票提交新的写入。新领导者的选举还受日志新旧程度约束，不能随意选一个落后节点覆盖已提交决定。

这里尤其要保留一个条件：直接通过副本计数判断提交的是领导者当前任期的日志项；旧任期项的提交需要通过相关规则间接确立。 “只要任意日志在两台机器上就永远安全”会漏掉这项限制。Raft论文第5.3、5.4节

Raft也不自动保证任意副本的直接本地读取都是最新的。线性一致读取还需要确认领导权及提交状态等读协议；配置了复制日志，并不意味着应用随意读取副本就获得同样保证。

租约过期为什么还不足以阻止旧工作者

租约赋予某个工作者在有限时间内持有资源的资格。假设A获得租约后长时间暂停，租约过期，B获得新租约并完成写入；随后A恢复，仍可能继续执行先前的代码。

如果资源端只接受一个普通“写入”请求，它不知道A已经失效。可以让每次有效接管获得单调递增的fencing token（隔离令牌），资源端记住已接受的新令牌并拒绝更旧的写入。例如B使用令牌12后，A携带11的延迟写入应被拒绝。

令牌的生成必须可靠、与接管关系一致，资源端也必须实际校验。随机UUID只能区分身份，没有自然的新旧顺序；仅在客户端检查自己还持有锁，检查后到写入前也可能失效。外部系统不支持这些条件时，需要另找幂等、条件更新或串行处理方案。

面试问答：CAP理论

讲一下 CAP 理论

回答： CAP讨论分布式读写对象在允许网络分区的模型下，无法同时保证线性一致性和所有非故障节点上的请求可用性。C约束操作的实时顺序与观察结果，A要求请求完成，P要求考虑节点间消息无法正常传达的情况。

例如A、B失联后，A完成把x从0写成1，随后B收到读请求。B若返回旧值0会破坏该线性一致要求；若等待获知最新状态，就无法保证分区持续期间请求仍完成。不能通过给B返回错误，把两项保证都声称满足。

工程选择应具体到操作及故障处理。库存扣减可能拒绝无法确认的请求，容忍陈旧内容的读取则可能继续服务。多数派协议可以在多数节点连通时保持一致的提交，但少数分区无法继续承诺同样的写入可用性。

延伸追问（自拟）：没有分区时就没有一致性成本了吗？ 仍有协调、复制和延迟成本，也可能出现其他故障。CAP给出特定模型下的不可能性，不能替代平时的性能、持久性和读写协议分析。
