FastAPI接口可以写成普通def，也可以写成async def。应该选择哪一种，要看内部调用的库怎样等待I/O。本站使用同步SQLAlchemy Session和psycopg，所以数据库业务路由采用普通def。

同步函数与异步函数分别在哪里等待

FastAPI调用普通同步路径操作函数时，会在线程池中运行，避免这段同步工作直接占住事件循环。async def路径操作运行在异步执行流程中，只有内部等待的是适合await的异步操作，才能在等待期间让出执行机会。FastAPI并发说明给出了这两类使用条件。

把同步数据库调用放进async def里，却没有正确转移或改用异步驱动，可能阻塞事件循环。仅修改函数声明中的async，不会使内部库自动异步化。普通辅助函数也不会因为被异步函数调用，就自动进入框架线程池。

如果任务主要在进行很长的CPU计算，异步I/O同样不能直接解决，需要评估进程、任务队列或其他计算安排。本站的短反馈事务与模型训练属于不同负载，不应套同一套并发解释。

Depends怎样复用接口前置条件

本站多个写接口都需要检查Origin，因此把检查登记为依赖；管理路由还通过依赖读取Cookie：

python
token: Annotated[str, Depends(require_cookie)]

这里声明“调用这个接口时，先按依赖规则取得token”。require_cookie检查Cookie格式，随后业务中的load_author_session再查询数据库确认令牌有效。格式像令牌，并不代表已经通过会话认证。

依赖可以复用输入与检查逻辑，减少各路由漏掉某一步的机会，但不能把“使用Depends”直接当成权限正确的证明。还需要核对每条敏感路由是否接入、取得的身份是否用于后续授权。依赖机制说明了调用与注入方式。

请求校验、依赖和中间件会共同参与处理，不要根据一张概念流程图就承诺多个错误同时出现时一定返回某个状态。确实依赖优先级的行为，需要按具体版本和请求测试。

中间件和异常处理各放什么

请求体上限适合在读取边界控制，响应安全头适合集中添加。业务判断如“反馈是否已审核”，则留在理解该业务的路由或服务中。本站请求体限制使用ASGI中间件；管理接口的响应带no-store；校验错误经过处理，避免默认诊断把提交的密码或消息原文回显。

HTTPException用于返回明确的HTTP错误。本站数据库相关异常统一返回503及固定提示，不把SQL与连接参数直接暴露给用户。统一提示方便保持界面边界，但定位故障还需要服务端记录合适的脱敏诊断，不能只看一个503就确认根因。错误处理参考介绍了异常与自定义处理器。

线程池、连接池与数据库连接数怎样对应

查看图中细节

一个请求进入同步路径函数后，可能先通过校验，再向SQLAlchemy连接池借连接。本站每个Engine配置pool_size=3、max_overflow=0、pool_timeout=3。因此单个进程的这个池最多同时借出3个连接；第4个需要连接的请求可能等待归还，等候超时则失败。

text
请求A、B、C：各持有1个连接
请求D：等待池中空位
A提交并关闭Session：连接归还
D在超时前取得连接：继续执行

这只是排队推演，不是压测结果。请求尚未用数据库的阶段不一定占用连接；事务时间不同，吞吐量也不同。因此3个连接不能换算成“最多3个用户”或“每秒3次请求”。

Uvicorn增加worker会创建更多进程，每个进程通常都有自己的Engine和连接池。4个worker、每池3连接，可能形成约12个应用连接，还要为迁移与运维连接留余量。当前生产Compose使用1个worker，不应按多进程模型描述现有实例。

限流也有进程边界

本站限流器使用内存中的deque保存时间戳，以动作和客户端地址为键，使用锁保护桶更新。多线程访问同一个对象时，锁有作用；多个worker各有一份内存时，它不会自动共享计数。重启也会清空记录。

这是小规模单进程场景下的限制，不是分布式限流。未来若扩展为多实例，需要决定是在网关统一限制，还是使用共享存储，并定义窗口、键、容量与故障策略。不要先加Redis，再回头寻找它要解决的问题。

查看/health/live能确认进程会响应；/health/ready还会查询数据库。它们回答不同问题，也不能代替真实反馈提交和审核测试。完整业务过程见反馈数据流。
