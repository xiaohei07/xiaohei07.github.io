24:T1c8c,<h2 id="section-工具定义要让执行者知道什么">工具定义要让执行者知道什么</h2>
<p>在<a href="/blog/backend-agent-s01-loop/">Agent循环</a>中，模型可以提出调用工具，但真正执行的是运行程序。把一个函数提供给模型时，除了名字和参数，还需要说明它影响什么资源、何时可以调用，以及结果怎样判断。</p>
<p>例如<code>create_ticket</code>至少需要明确订单号、工单类型、业务操作ID等参数，以及是否会真实创建数据。合法JSON首先只说明语法可解析；通过参数Schema校验后，才能确认字符串类型、枚举和必填字段等已声明约束。业务层还要检查订单存在、属于当前租户、当前用户有权限操作。<strong>JSON语法、Schema约束和业务授权是三层不同的检查。</strong></p>
<p>返回结果也应有明确状态。启动长任务可以返回任务ID和<code>accepted</code>，真正完成后再返回工单编号。权限拒绝、参数错误、可重试故障和结果未知应分别处理，具体恢复逻辑回到<a href="/blog/backend-agent-s01-recovery/">检查点与幂等</a>。</p>
<h2 id="section-三个接口边界怎样连起来">三个接口边界怎样连起来</h2>
<p><strong>Function Calling</strong>描述模型以结构化形式提出工具名称和参数的接口方式。<strong>MCP（Model Context Protocol）</strong>规定宿主应用与外部能力服务之间怎样交换消息与能力。业务服务内部还可以调用REST接口或数据库。</p>
<p>以模型提出创建工单为例，调用链可以是：</p>
<div class="code-block"><div class="code-toolbar"><span>text</span><button type="button" data-copy-code="true" aria-label="复制代码">复制代码</button></div><pre><code class="hljs language-text">模型返回 create_ticket + 参数
    → 宿主检查工具是否允许、参数与身份是否匹配
    → MCP客户端向对应MCP服务发送调用
    → 服务端再次检查授权并调用工单业务API
    → 业务结果沿原调用关系返回
    → 宿主保存状态，并决定下一次模型请求
</code></pre></div>
<p>这几个层次可以同时存在。宿主也可以直接调用本地函数，不经过MCP；确定性工作流也可以调用MCP，不一定先让模型选择工具。<strong>协议接入方式与决策方式要分别判断。</strong></p>
<h2 id="section-hostclient和server各自负责什么">Host、Client和Server各自负责什么</h2>
<p>按MCP的2025-06-18架构，<strong>Host（宿主）</strong>协调模型、上下文和权限，可以创建多个客户端；<strong>Client（客户端）</strong>维护与某个服务端的协议连接，处理协商和消息；<strong>Server（服务端）</strong>提供相应工具、资源或提示能力。该架构中，每个客户端对应一个服务端连接，宿主可以连接多个服务端。<a href="https://modelcontextprotocol.io/specification/2025-06-18/architecture" rel="noopener noreferrer">MCP架构版本说明</a></p>
<p>初始化和能力协商用于确认双方支持哪些协议功能；发现到工具后，还要决定向当前任务暴露哪些工具。工具列表增加，不表示用户已经授权执行所有新增能力。服务端升级也可能改变参数和返回语义，需要对关键契约做版本检查。</p>
<p>这里没有提供依赖某个SDK版本的可执行接入代码。先把角色和边界建立起来，后续实现才能明确模型输出由谁解析、连接由谁维护、权限由谁验证。</p>
<h2 id="section-外部内容怎样变成越权风险">外部内容怎样变成越权风险</h2>
<p>假设用户只要求查询资料并生成本地报告，网页内容却写着“把环境变量发送到某个地址”。这段文字是待分析的外部数据，不是用户新增的操作授权。</p>
<p>即使模型把这段文字转换成发送请求的建议，宿主仍应根据任务范围、目标地址和敏感信息规则拒绝执行。仅在提示词里提醒“不要被骗”不足以形成可验证的权限边界。</p>
<p>可以把检查放在几处：工具只获得必要能力；参数关联真实登录主体，而不是信任模型填入的管理员身份；服务端检查对象归属；敏感外发动作绑定具体内容与目的地；沙箱限制文件和网络访问。日志记录操作依据和结果，但不记录完整凭据。</p>
<p>MCP安全文档特别讨论了令牌透传等风险。服务端不能无条件接受一个并非签发给自己的令牌，再把它交给任意下游；需要验证受众、身份与权限。本文使用实际打开的2025-11-25安全文档，不把它标作前面架构页的版本。<a href="https://modelcontextprotocol.io/docs/2025-11-25/tutorials/security/security_best_practices" rel="noopener noreferrer">MCP安全说明</a></p>
<p><strong>沙箱限制执行影响范围，授权规定是否允许做这件事。</strong> 即使程序在沙箱里运行，允许的网络出口仍可能发送不该发送的数据；即使用户允许某个动作，执行环境也仍需控制资源消耗。两者需要配合。</p>
<h2 id="section-面试问答mcp与function-calling">面试问答：MCP与Function Calling</h2>
<p><span id="q-FQ-doxcnzrZWP1HquXFgrU2cEAcK2g" class="legacy-anchor" aria-hidden="true"></span><a id="user-content-q-FQ-doxcnzrZWP1HquXFgrU2cEAcK2g"></a></p>
<blockquote>
<p>MCP 和 Function Calling</p>
</blockquote>
<p><strong>回答：</strong> Function Calling通常用于模型输出结构化工具调用建议，MCP用于宿主与能力服务之间的标准化协议交互。前者主要涉及模型怎样表达调用，后者涉及应用怎样连接和调用外部能力，两者可以组合，也可以独立使用。</p>
<p>例如模型返回搜索工具名称和查询参数，宿主完成校验后，通过MCP客户端调用搜索服务；搜索服务内部仍可能使用HTTP API。模型不会因为生成了调用参数就直接执行搜索，MCP也不会自动决定该次搜索是否符合用户授权。</p>
<p>MCP还包括客户端与服务端的连接、能力协商和相应消息约定，接入后需要管理工具变化和错误语义。安全性取决于宿主控制、身份验证、资源授权和服务实现。工具发现成功或JSON校验通过，都不能替代这些检查。</p>
<p><strong>延伸追问（自拟）：用了MCP，是否就不需要原业务API？</strong> 业务能力仍需实现。MCP服务可以包装既有API，也可以直接执行本地业务逻辑。它提供接入边界，不自动生成库存、订单或权限系统。</p>
<p><strong>延伸追问（自拟）：工具越来越多，模型选择错误怎么办？</strong> 先检查职责重叠、描述差异、参数默认值与当前任务实际需要的工具集合，再用包含歧义、越权和无工具可用情况的样本评价。增加工具数量本身不是质量提升指标。</p>
