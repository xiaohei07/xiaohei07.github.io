进程占用、Java堆和存活对象是三个观察量

Java进程的内存包含Java堆，也包含线程栈、类元数据、JIT生成代码、GC辅助结构和部分本地分配。-Xmx主要限制最大Java堆，不是整个进程的总内存上限。

对象存活量又小于或等于某次统计下的堆使用量：堆中可能还保留已经不可达、尚未回收的对象。操作系统看到的RSS表示驻留物理页，也不能直接等同于JVM报告的reserved或committed。排查时先统一指标定义，才有办法解释“堆很小但进程很大”。

例如教学监控中，最大堆1GiB，进程RSS达到1.6GiB，并不能直接判定GC失效。需要继续拆分线程数量、直接缓冲区、元空间和其他本地分配；同时核对容器限额是否给这些区域留了余量。

GC Roots怎样确定对象还可能被使用

GC Roots是可达性分析的起点，包括相应线程执行状态、静态引用及运行时持有的根等。收集器从根沿引用关系追踪对象，得到仍可达的集合。具体根的表示和扫描方式与实现、阶段有关。

构造一个图：静态列表L指向A，A与B互相引用。只要L仍引用A，A和B都可达。清除L到A的引用后，即使A、B还互相引用，若没有其他根路径，两者也可被判为不可达。

这解释了Java为什么能处理环引用，也解释了逻辑泄漏：业务不再需要A，但一个长期存在的集合仍持有它，GC无法替业务判断“以后不会再用”。泄漏诊断要追保留路径，而不只是数对象数量。

标记、回收与移动怎样配合

标记负责识别存活，回收释放不再需要的空间；移动存活对象可以压缩空洞，但需要更新引用或使用相应屏障。不同收集器在停顿、并发、空间和吞吐之间采取不同方案。

以JDK21的G1为例，堆划分为Region，年轻代回收会疏散存活对象；并发标记帮助识别老年代区域的存活情况，之后Mixed阶段可以同时选择年轻代和部分老年代区域回收。Mixed不等于每次都回收整个老年代，并发也不意味着完全没有暂停。G1回收周期

停顿目标是调节目标，不是硬实时承诺。分配过快、保留对象过多、疏散空间不足等情况可能使结果偏离目标。谈G1或其他收集器时，应先确定JDK版本、配置和实际日志，不能只按“适合大堆”选一个名称。

两组曲线怎样导向不同假设

教学场景A：每轮请求分配200MiB临时对象，回收后使用量回到约100MiB。峰值反复升高但基线稳定，可能主要是分配速率与回收节奏问题。

教学场景B：相同请求结束并经过可比较的回收后，基线依次100、150、200MiB。这个趋势更值得检查持续保留的对象。若发现一个缓存每轮增加同样数量的键且没有淘汰，再沿根路径确认，才形成较完整的泄漏解释。

这里不能随意把每次GC后的数值拼起来：不同GC阶段回收范围不同，负载也可能不同。要在相近业务条件和足够长窗口下比较，并保留暂停、分配与晋升信息。

堆外增长怎样继续拆解

Native Memory Tracking（NMT）可以记录HotSpot内部内存类别，帮助区分Heap、Class、Thread、Code等。它需要按所用JDK方式启用，存在开销，而且不覆盖所有非JVM本地代码分配。因此“NMT没有发现增长”不能排除所有本地泄漏。JDK诊断与NMT

若Thread类增长，核对线程数量和创建路径；若Class类持续增长，核对类加载器是否被长期保留；若业务使用直接缓冲区或JNI库，再结合相应池指标与操作系统工具。只增加Xmx可能挤占原本就紧张的本地内存。

ThreadLocal也要结合线程池生命周期理解。任务结束不代表工作线程结束，任务残留的数据可能继续被线程持有；适当的finally清理与作用域管理比期待下一次GC更直接。

一套逐步收集证据的方式

先记录版本、启动参数、业务时间窗口、GC日志及容器限制。JDK工具可用下列形式，<pid>必须换成经过确认的目标Java进程；以下为命令格式，不在本轮对其他业务进程执行：

text
jcmd <pid> VM.version
jcmd <pid> VM.flags
jcmd <pid> GC.heap_info
jcmd <pid> Thread.print
jcmd <pid> VM.native_memory summary

NMT未启用时不能把空结果当成“没有堆外问题”。对已启用NMT的受控实验，可以建立baseline后查看summary.diff。堆转储、类直方图和录制工具可能影响进程，也可能包含业务数据，使用前要明确范围和保存位置，不能在排查说明里默认对任意生产服务执行。

得到保留路径后，还要构造重复请求的回归实验：修复前增长，修复后同负载下不再持续保留，同时检查功能正确。吞吐和延迟也要观察，不能用清空所有缓存换来表面上的低内存。

面试问答：GC Roots与垃圾回收

JVM 八股（垃圾回收）：JVM 的垃圾回收过程大致是什么？GC Roots 和可达性分析是怎么回事？

回答： 收集器从GC Roots沿引用追踪存活对象，回收不可达对象，并按算法选择是否移动或压缩。Java主要按可达性判断，所以两个对象互相引用但没有根路径时，仍可被回收；反过来，业务已经不用但仍被静态集合等引用的对象不会自动释放。

具体过程随收集器和版本变化。以JDK21 G1为例，年轻代疏散、并发标记与后续Mixed回收协同工作，仍有暂停阶段。诊断时比较相近负载下的回收后基线和对象保留路径，不能把RSS增长全部归为Java堆泄漏，也不能把某次高峰直接判成泄漏。

延伸追问（自拟）：调用System.gc就能证明没有内存泄漏吗？ 不能。它的实际处理受实现和配置影响，而且可达但业务不再需要的对象仍会保留。需要检查根路径、负载趋势和修复后的回归结果。

原问见逐题映射。本篇按JDK21文档解释机制，没有读取其他业务进程或制造内存耗尽。
