29:T28d2,<span id="section-优化前先确定慢在哪里" class="legacy-anchor" aria-hidden="true"></span><h2 id="section-查询优化前的耗时定位与材料准备">查询优化前的耗时定位与材料准备</h2>
<p>一个接口响应慢，可能耗时在连接池排队、锁等待、查询执行、结果传输或应用处理。<strong>EXPLAIN用于查看SQL的执行计划</strong>，帮助分析数据库准备怎样访问数据；接口调用链中其他部分的耗时，则需要结合对应的观测数据定位。</p>
<p>先保留完整SQL、参数、表结构、索引、数据库版本和实际耗时。查询条件中的租户、时间范围与返回列都可能影响计划；把真实查询改成<code>SELECT * FROM table</code>再分析，已经不是同一个问题。</p>
<p>本篇实验使用<strong>独立的MySQL8.0.35实例和6行任务数据</strong>，便于手工核对查询结果与访问方式。这个规模适合观察执行计划的变化，线上吞吐则需要结合实际数据与负载另行评估。</p>
<h2 id="section-先建立能够手工核对结果的表">先建立能够手工核对结果的表</h2>
<p>以下SQL在独立教学数据库中执行，表名要确认属于实验。真实业务库不要直接复制DROP或初始化语句。</p>
<div class="code-block"><div class="code-toolbar"><span>sql</span><button type="button" data-copy-code="true" aria-label="复制代码">复制代码</button></div><pre><code class="hljs language-sql"><span class="hljs-keyword">CREATE TABLE</span> jobs (

(<span class="hljs-number">1</span>,<span class="hljs-number">7</span>,<span class="hljs-string">'pending'</span>,<span class="hljs-string">'2026-01-01'</span>),
(<span class="hljs-number">2</span>,<span class="hljs-number">7</span>,<span class="hljs-string">'pending'</span>,<span class="hljs-string">'2026-01-02'</span>),

<p>符合条件的是1、2、5，按时间倒序应返回5、2。id作为第二排序键，让相同时间下也有明确顺序。先确认结果语义，再比较访问方式，避免得到一个更快但返回错数据的查询。</p>
<p>本轮索引前的计划显示<code>type=ALL</code>，估算<code>rows=6</code>，Extra包含<code>Using where; Using filesort</code>。这说明计划扫描表并筛选，再完成相应排序。<strong>filesort是额外排序机制的标记，不表示一定把数据写到了磁盘。</strong></p>
<span id="section-联合索引怎样同时服务筛选与排序" class="legacy-anchor" aria-hidden="true"></span><h2 id="section-联合索引对等值筛选排序与覆盖访问的作用">联合索引对等值筛选、排序与覆盖访问的作用</h2>
<p>增加索引：</p>
<div class="code-block"><div class="code-toolbar"><span>sql</span><button type="button" data-copy-code="true" aria-label="复制代码">复制代码</button></div><pre><code class="hljs language-sql"><span class="hljs-keyword">CREATE</span> INDEX ix_jobs
<span class="hljs-keyword">ON</span> jobs(tenant_id, status, created_at, id);
</code></pre></div>
<p>前两列对应等值条件。对于选定的租户和状态，后续created_at、id形成所需顺序，反向扫描可以得到倒序结果。返回列都在相应索引记录中，计划还可以利用覆盖访问。</p>
<p>这次实验得到的计划对比如下：</p>



































<table><thead><tr><th>字段</th><th>索引前</th><th>索引后</th></tr></thead><tbody><tr><td>type</td><td>ALL</td><td>ref</td></tr><tr><td>key</td><td>NULL</td><td>ix_jobs</td></tr><tr><td>rows估算</td><td>6</td><td>3</td></tr><tr><td>filtered估算</td><td>16.67</td><td>100.00</td></tr><tr><td>Extra</td><td>Using where; Using filesort</td><td>Backward index scan; Using index</td></tr></tbody></table>
<p>这张表是特定版本与六行数据上的结果。数据量、统计信息和分布变化后，优化器可能作出不同选择；小表选择全扫描也可能合理，不能把计划字段当成固定答案。</p>
<span id="section-rowsfiltered和actual-rows怎样区别" class="legacy-anchor" aria-hidden="true"></span><h2 id="section-rows与filtered的估算值及analyze的运行统计">rows与filtered的估算值及ANALYZE的运行统计</h2>
<p>传统EXPLAIN中的<strong>rows是优化器预计要检查的行数</strong>，filtered是表条件过滤后预计保留的百分比。例如rows=1000、filtered=10，估计向后续阶段提供100行；它不是已经实测扫描了1000行。<a href="https://dev.mysql.com/doc/refman/8.4/en/explain-output.html" rel="noopener noreferrer">EXPLAIN字段</a></p>
<p>EXPLAIN ANALYZE会实际执行支持的语句并给出运行统计，应先确认语句和环境适合执行。本实验对同一SELECT得到覆盖索引反向查找、实际返回2行、loops=1。LIMIT允许找到所需行后停止，因此估算候选3行与实际产出2行并不冲突。<a href="https://dev.mysql.com/doc/refman/8.0/en/explain.html" rel="noopener noreferrer">MySQL8.0 EXPLAIN与ANALYZE</a></p>
<p>多层循环连接中的rows和time还要结合loops理解，不能把每个节点的平均值直接当成整条查询的总量。一次运行的微秒级差异也受缓存与计时扰动影响，本篇不据此计算“性能提升多少倍”。</p>
<span id="section-key_len和覆盖索引不能只看数字" class="legacy-anchor" aria-hidden="true"></span><h2 id="section-key_len与using-index的含义">key_len与Using index的含义</h2>
<p>key_len受字段类型、字符集、可空性和实际使用的键部分影响。它可以辅助判断联合索引使用情况，但需要结合访问条件和执行计划，不能只用“长度最大就最好”判断。</p>
<p><strong>Using index通常表示可以从索引取得所需列</strong>，它不等于用了某个索引就必然出现，也不等于所有MVCC场景都永远无需额外检查。具体索引与可见性关系见<a href="/blog/backend-agent-s07-index-query/">索引基础</a>。</p>
<p>如果返回正文大字段，索引可能无法覆盖，需要回表；如果时间字段套函数，优化器是否可转换要按版本与表达式判断。改成半开时间区间往往更利于表达边界，但仍要保持时区和日期语义。</p>
<span id="section-连接查询怎样继续分析" class="legacy-anchor" aria-hidden="true"></span><h2 id="section-连接查询的中间结果与循环成本">连接查询的中间结果与循环成本</h2>
<p>两个表连接时，先确认连接条件和期望基数，再看驱动侧筛选能否减少后续工作。若每行都触发大量被连接表扫描，即使单次查找看起来不贵，总循环成本也可能很高。</p>
<p>有索引不代表选择性高。一个状态字段只有两个值，查询命中大多数行时，索引收益可能有限；联合索引应围绕实际过滤、排序和返回列设计。增加索引还会增加写入和空间成本，所以需要比较读写负载，而不是给每列都建索引。</p>
<p>最后还要复查返回行数、锁等待和接口耗时。执行计划改善是优化证据的一部分，不能取代业务正确性与完整请求链的验证。</p>
<span id="section-面试问答explain关注哪些字段" class="legacy-anchor" aria-hidden="true"></span><h2 id="section-面试问答explain的主要字段与分析顺序">面试问答：EXPLAIN的主要字段与分析顺序</h2>
<p><span id="q-FQ-doxcncW6HvvlDZkbtu2eGRGAtUe" class="legacy-anchor" aria-hidden="true"></span><a id="user-content-q-FQ-doxcncW6HvvlDZkbtu2eGRGAtUe"></a></p>
<blockquote>
<p>4、sql优化，说说explain需要关注哪些参数？</p>
</blockquote>
<p><strong>回答：</strong> 先核对SQL、参数、表结构和版本，再关注访问类型type、可能与实际选择的索引possible_keys/key、key_len、估算rows和filtered，以及Extra中的排序、临时表、覆盖访问等信息。连接查询还要看各表顺序、连接条件和预计中间结果。</p>
<p>本例只用主键时扫描6行并排序，增加匹配等值筛选和排序的联合索引后，计划改为ref访问及覆盖反向扫描。rows仍是估算；使用EXPLAIN ANALYZE可以观察实际行数与循环，但它会执行查询，且小数据时间不能代表线上吞吐。</p>
