从一次回答到一个需要执行的任务

假设要完成这样的请求：“查一下订单为什么还没发货，如果符合条件，就创建一张售后工单。”这需要订单系统中的当前信息，也会改变工单系统里的数据。要完成这个请求，系统需要实际查询订单，并在符合条件时创建工单，最后取得对应的执行结果。

为了讲清Agent怎么工作，可以先把这个任务分开看。模型负责根据当前可见的信息提出下一步；运行程序负责检查这一步能不能做，并真正调用外部系统。 外部系统返回结果以后，程序把结果送回下一次模型请求，模型才能依据新信息继续判断。

这个不断根据结果推进任务的过程，通常称为Agent Loop（Agent执行循环）。其中的“自主”是指模型可以在一定范围内选择下一步，可用工具、操作权限和资源预算仍由运行程序限定。

这里还有几个经常放在一起的名称。工具是系统向模型暴露的操作接口，例如get_order(order_id)；接口背后可能是本地函数，也可能是网络服务。状态记录任务进行到哪里、有哪些已确认结果。Harness则是模型外围负责上下文组装、工具执行、状态管理和约束检查等工作的运行系统。工具提供操作入口，状态保存进度，Harness则把这些部分组织成可以运行的系统。

Workflow与Agent的控制流分工

Workflow（工作流）通常由程序预先规定主要执行路径，例如先验参，再查订单，再根据固定规则选择是否允许提交。Agent则把部分路径选择交给模型，让它结合运行时的观察决定下一步。这个区分关注的是控制流由谁决定；实际系统可以把两者结合起来。Anthropic在2024年的设计文章中采用了类似区分，适合用来理解架构，但不同框架的具体模块划分，还需要结合各自实现理解。架构区分

比如查询失败后，要判断是缺少订单号、订单属于另一个账户，还是服务暂时不可用，可能需要动态获取信息；但“当前用户是否有权操作这个订单”仍适合由程序中的确定规则检查。权限检查的结果不能因为模型换了一种说法就改变。

如果任务只有固定字段校验和一次确定查询，普通函数或工作流就可能足够。引入动态决策会增加模型调用成本，也增加对终止条件、状态和错误处理的要求。是否使用Agent，应当看任务是否需要依据中间结果调整路径。

Agent循环中的上下文、工具结果与状态变化

下面继续用这个售后场景推演。假设查询接口返回订单未发货，售后规则允许创建工单，创建接口也支持固定的业务操作ID，用来识别多次请求是否属于同一次创建。

步骤程序持有的数据发生的动作下一步依据
接收任务用户目标、当前身份、订单号记录允许操作和完成条件是否缺少必要信息
构建上下文目标、工具定义、已知订单号发出模型请求模型返回查单建议
校验建议工具名称、参数、当前身份验证参数和订单访问权限校验通过才允许调用
查询订单查询请求与调用ID工具返回订单状态保存结果及查询时间
再次决策订单状态、售后规则、剩余预算模型提出创建工单建议程序再次校验操作资格
创建工单固定操作ID、创建参数工具返回工单编号保存外部执行证据
验收工单编号、用户目标检查目标是否满足形成最终答复

每次模型调用看到的是程序为这一轮准备的上下文。 要让模型继续使用订单状态，程序需要把工具结果放进下一轮上下文，或者提供可再次读取结果的受控入口。上下文具体怎样组织，后面在上下文与记忆展开。

工具返回的数据也需要识别含义。例如{"accepted": true}可能只表示任务已入队；只有接口契约明确表示工单已创建，才可以据此写“创建成功”。HTTP返回成功状态和业务操作完成之间，也需要这层判断。

任务状态中的计划、事实、动作与执行证据

可以先把状态理解成一份任务记录，但它需要区分计划、事实、动作和证据。例如“准备创建工单”是计划，“查到订单未发货”是观察，“发送创建请求”是动作，“查到工单编号T17”才是完成证据的一部分。

下面把这些信息整理成一个简化的任务状态：

json
{
  "run_id": "run-17",
  "goal": "查询订单并按规则创建工单",
  "status": "running",
  "facts": {"order_status": "not_shipped"},
  "next_action": "create_ticket",
  "operation_id": "op-17",
  "ticket_id": null,
  "remaining_tool_calls": 3
}

这些字段需要按来源更新：身份与权限来自可信服务，剩余预算由运行程序计算，外部结果来自工具返回或后续查询。模型可以提出状态修改建议，再由程序核对依据并决定是否接受。

如果工单创建请求超时，状态还需要表达结果未知：此时既不能填入虚构的工单编号，也不能直接当作“没有创建”。这种状态怎样恢复，见检查点与外部副作用。

规划调整、结果反馈与执行终止条件

先列计划再执行，适合有明确子任务和依赖的工作；执行一步、观察一步，再决定下一步，适合信息逐渐暴露的场景。计划用来检查子任务是否遗漏，执行后再用实际结果判断后续步骤是否仍然适用。

比如最初计划是“查订单→创建工单→通知用户”，查单后发现订单已经取消，创建步骤就应重新判断。如果仍照最初计划往下走，说明程序没有把新观察用于控制流。

执行循环还要有程序控制的停止方式。成功需要对应完成证据；缺少订单号可以等待输入；结果未知需要查询或对账；达到调用上限则结束在预算耗尽状态。这些情况应保留各自的结束或等待状态，供调用方继续处理。

检测死循环时，只限制总轮数还不够。可以同时记录动作与参数的摘要、连续错误次数，以及是否获得了新的信息。连续重复同一请求、得到同一错误且状态没有推进时，就需要改变策略或者停止。如果是在等待后台任务，则应有轮询间隔和截止时间，不能把合理等待与无意义重试混为一谈。

面试问答：Agent的核心模块与Loop设计

你如何理解 Agent 系统？可以拆解一下 Agent 的核心模块吗？

回答： Agent系统通过模型决策、外部动作和结果反馈持续推进一个任务。核心职责包括任务与权限约束、上下文构建、模型决策、工具执行、状态保存以及结果验收；具体代码可以合并模块，但这些职责需要有人承担。

任务入口确定目标、身份和资源边界。上下文构建器把相关状态与证据传给模型；模型生成工具调用建议或最终答复。执行器检查名称、参数和权限，实际调用工具，再把结果关联到调用ID并写入状态。调度器依据状态决定继续、等待、失败或结束。验收环节检查产物是否满足用户目标，防止把“模型说完成了”当作唯一证据。

以创建工单为例，模型提出创建建议后，执行器仍需确认用户有操作权限。接口只返回受理成功时，任务还要等待或查询实际创建结果。服务重启后，需要持久状态恢复进度；如果动作可能已经在外部完成，还需要幂等或结果查询。因此，除了聊天记录，还需要保存任务进度、操作标识和外部执行证据。

延伸追问（自拟）：每个系统都要有独立的规划模块吗？ 不需要。简单任务可以由同一次模型调用完成下一步选择，固定流程也可以直接用程序控制。独立规划适合确实需要任务分解与依赖管理的情况；应根据错误类型、可控性和成本验证收益。

Workflow 和 Agent 的 Loop 各自怎么设计？

回答： Workflow按预先设计的节点和条件边推进，Agent Loop则让模型基于当前状态选择部分后续动作。两者都需要状态、错误分支与终止条件，区别在于哪些控制流由代码确定、哪些决策由模型产生。

Workflow可以把验参、查询、判断和提交定义为节点，并明确每个节点的输入输出。Agent Loop则重复执行“组装上下文→模型建议→校验→执行→观察→更新状态”，但权限、预算和成功判定仍由程序约束。例如售后资格检查可以是固定工作流节点，缺少信息时要查询什么可以交给Agent判断。

如果同一个工具持续返回权限不足，应终止该路径或请求用户补充授权，不能让模型不断更换参数尝试。外部结果未决时，应转入查询或对账状态，而不是直接再次提交。设计是否可靠，取决于这些状态转换是否明确，而不取决于循环代码是否写成了while。

延伸追问（自拟）：固定流程里调用了LLM，是否就变成Agent？ 仍应检查控制流。若LLM只做文本分类或信息抽取，后续路径由固定规则决定，用工作流描述通常更准确；名称本身不能证明系统具备自主规划能力。
