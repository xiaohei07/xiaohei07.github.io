在两数之和中，需要反复查找补数以及它的位置，因此用字典保存seen[数值] = 原下标。要理解这一步为什么能加速，先需要分清“已知下标访问数组”和“已知数值寻找位置”。

哈希表的用途：通过键找到关联的值

数组有了下标，就可以通过nums[4]直接读取第5个位置。底层按照起始地址＋下标×单元大小计算地址，通常可以按O(1)分析。可是，如果已知的只有“要找7”，普通数组并没有同时保存7的位置，仍需要逐个检查，或提前建立查询结构。

字典保存的是键（key）→值（value）的对应关系。键用来查询，值保存需要取回的信息。在两数之和中，键是数组里的数，值是它的原下标；换成成绩表，键可以是学号，值可以是成绩。

哈希表是实现这种映射的一种数据结构。它借助哈希函数缩小查找范围，再核对键，找到对应的值。Python的字典在CPython（常见的Python解释器实现）中就采用了哈希表。

键怎样变成查找位置：哈希值、槽位与冲突

哈希函数会把键转换成一个整数，叫作哈希值。表的容量有限，还需要把这个整数映射到表内的位置，这个位置叫作槽位。例如一张8槽的小表，可以先按下面的规则确定查找起点：

h=hash⁡(key),s=h mod 8h=\operatorname{hash}(key),\qquad s=h\bmod 8

哈希值是计算结果，槽位号是表内位置，两者含义不同。表扩容后容量改变，同一个哈希值也可能对应另一个槽位。

假设7、15、23的哈希值分别等于自身，它们对8取余都得到7。这种不同键选中同一个起点的情况叫作冲突。因此，定位到槽位后，还要核对键是否相等，不能只看槽位或哈希值。

冲突处理方法查找怎样继续
链地址法同一个桶保存多条记录，再在桶内比较键；桶可以由链表等结构实现
开放寻址法按确定的探测规则，继续检查表内其他槽位；CPython字典采用这一类方法

可以把槽位理解成资料格的编号，哈希函数决定先去哪个格子找；发生冲突后，仍需要按规则寻找并核对完整编号。查找和插入使用相同的探测规则，才能再次找到存进去的键。两种方法的进一步说明可见链地址法和线性探测。

indices与entries：槽位怎样指向字典条目

下面以CPython3.12.0的整数键合并表（combined table）为例。这种布局把存储分成两部分：indices保存条目下标，entries保存条目的哈希信息以及键和值。

下面取数组nums = [15, 8, 23, 9, 7]，手动按7、15、23的顺序记录三个数的位置，得到{7: 4, 15: 0, 23: 2}。这个写入顺序用于说明位置关系，不是两数之和从左到右扫描的顺序。

查询7时，先算出槽位7，读到indices[7] = 0；再访问entries[0]，核对键为7，取出value为4。槽位号7、条目下标0、原数组下标4，分别属于三个位置。其中4是主动存入的值，字典不会自动计算这个原下标。

从槽位到条目的过程，可以理解为把indices里保存的整数，当作entries的下标使用。两次按已知下标访问数组，不需要重新在entries中搜索。实际字段见CPython条目结构。

冲突与删除：为什么查23要经过槽7、4、5

23的起点也是槽7，但那里对应的键是7；继续探测槽4，读到键15；再到槽5，才找到键23。这个例子采用CPython3.12的扰动探测规则，具体计算放在下方补充中。

如果删除15，槽4会留下DUMMY标记，对应条目可以留下空洞。查询23经过槽4时，仍需继续到槽5。若把槽4直接当成从未使用的空槽EMPTY，查找就会提前停止，后面的23也就找不到了。

EMPTY表示可以结束查找，DUMMY表示需要继续。普通删除不会每次都把末尾条目搬过来填洞，重新建表时才可以整理有效条目并重建索引。CPython字典源码包含这些状态和查找步骤。

CPython3.12的探测公式与7→4→5的计算

CPython3.12.0的槽位数是2的幂，令mask = 容量 - 1，初始槽位为hash & mask。perturb从转换为无符号整数的哈希值开始，每次继续探测时执行：

text
perturb >>= 5
s = (5 * s + perturb + 1) & mask

本例固定8槽，查询23时mask = 7，初始槽为23 & 7 = 7。第一次右移后perturb = 0，后续槽位为：

s1=(5×7+1) mod 8=4,s2=(5×4+1) mod 8=5s_1=(5\times7+1)\bmod8=4,\qquad s_2=(5\times4+1)\bmod8=5

所以访问顺序是7→4→5。这只是选定小正整数和容量后的教学推演，实际解释器还有不同键类型与布局的处理，具体可看查找源码。

平均O(1)的条件：散列分布与扩容

哈希表的一次查找包含计算哈希、访问槽位、比较键。平均O(1)表示平均工作量不会随元素数量持续增长，并不要求只做一次操作。

以链地址法说明，设元素数量为n、桶数量为m，负载因子为：

α=nm,E[Tlookup]=O(1+α)\alpha=\frac{n}{m},\qquad \mathbb{E}[T_{lookup}]=O(1+\alpha)

在键分布较均匀、哈希和比较按常数成本计算的条件下，让桶数量随元素数量增长，把α控制在常数范围内，就能保持期望O(1)查找。开放寻址还需要保留足够空槽，具体成本取决于探测规则。

表装得越来越满时，需要扩容并重新安排有效条目。一次扩容可能花O(n)时间；以容量翻倍为例，多次搬迁的总量是1 + 2 + 4 + …，仍与最终元素数量同阶，分摊到整个插入序列上就是O(1)均摊扩容成本。

“期望”对应散列分布，“均摊”对应一串操作的成本分担。两者结合，才得到常说的期望均摊O(1)插入。大量冲突可能让查找退化为O(n)，长字符串首次计算哈希也需要计入长度成本。

好的哈希函数不一定复杂

判断哈希函数时，需要关注结果是否稳定、计算是否足够快、常见输入是否分布合理。相等的键必须有相同的哈希值，但哈希值相同不保证键相等。

CPython中7、15、23这类小正整数的哈希值就是自身，连续整数也可以分散到不同槽位。函数复杂并不自动带来好效果，需要结合输入和槽位映射来看分布。字符串等类型还采用进程级随机化，因此不能把hash()结果当作跨进程稳定编号（Python哈希约定）。

Python字典的常用操作与使用条件

python
positions = {7: 4, 15: 0}  # 数值 -> 原数组下标
print(7 in positions)     # True：检查键7是否存在
print(positions[7])       # 4：读取键7对应的值
positions[23] = 2         # 新增一个键值对
positions[7] = 1          # 已有键7，更新它的值
del positions[15]        # 删除键15及对应的值

键必须可哈希：哈希值在使用期间保持稳定，相等的键有相同哈希值。整数、字符串是常见键，列表不能直接作键；元组需要其中每个元素也可哈希（可哈希的定义）。

d[key]在键不存在时会抛出KeyError，需要先用key in d判断，或用d.get(key, 默认值)。Python3.7起保证字典按插入顺序迭代：更新已有键不改变位置，删除后重新插入会排到末尾。插入顺序与键的大小顺序不同，有序范围查询仍需其他结构。字典文档列出了完整操作。

选择数据结构：先明确需要怎样查找和修改

需要完成的操作可以考虑的结构
按确定的键查询、计数或记录位置哈希表；两数之和属于“数值→位置”
按键大小查询范围、寻找前驱后继排序数组或平衡搜索树
已知节点及必要链接，频繁移动或删除节点链表；LRU缓存可结合字典定位与双向链表调整顺序
已知连续下标，读取或遍历数据数组

两数之和适合用字典，是因为每一步都需要精确查询补数，并取出已经保存的原下标。把这两个需求写清楚，再回看先查询、后写入的代码，记录的含义和更新顺序就比较容易对应起来了。

需要统计数量时，字典里的值也可以保存次数：字母异位词窗口按字符保存频次，和为K的子数组按旧前缀和保存频次。键、值的含义变了，查询和更新仍然要与当前处理范围对应起来。
