创建任务与接收进度为什么可以分成两个请求

假设生成报告需要几十秒。前端可以先提交创建请求，取得任务ID，再订阅这个任务的进度。页面关闭以后，任务仍可能继续执行；需要回看结果时，通过任务ID查询当前状态即可。

任务是业务对象，连接是传输通道。 一个任务可以经历多次连接，连接结束也不自动表示任务成功。这个区别决定了断线以后应当查询或续传什么。

如果更新很少，定时轮询已经足够；需要持续推送进度时，可以选择SSE；双方都要频繁主动发送消息时，再考虑WebSocket。选型要先看消息方向和交互频率。

SSE怎样把事件交给页面

服务端发送事件（Server-Sent Events，SSE）通过HTTP响应持续向客户端发送文本事件。浏览器可以使用EventSource接收这些事件，再据此更新进度和结果。

服务端响应的媒体类型是text/event-stream，事件流按UTF-8解码。下面是教学事件格式，每个事件由空行结束：

text
id: 41
event: progress
data: {"task_id":"T17","progress":50}

id: 42
event: succeeded
data: {"task_id":"T17","result_id":"R17"}

id是事件标识，event是类型，data是事件数据。这里用递增数字作为应用约定，SSE规范本身并不要求ID必须是整数。收到succeeded以后，页面还应按业务规则更新终态，并在不再需要订阅时关闭事件源。WHATWG事件格式与重连规则

原生EventSource适合GET订阅，不能像任意fetch请求一样自由设置方法、请求体和自定义头。实际鉴权可结合受控Cookie等方案设计；跨源凭据还要检查CORS和资源权限。不要为了方便把长期访问令牌放进容易被日志记录的URL。

重连以后怎样避免进度倒退或重复追加

EventSource可以在连接异常结束后重新连接，并按规范携带已接收的事件ID。自动重连恢复的是连接，服务器仍需实现事件保存与回放。

假设页面已应用41号事件，42号事件在网络断开前后出现了不确定性：

恢复时的情况应用应怎样处理
再次收到41若业务事件已应用，跳过重复更新
收到42且可以衔接应用终态，保存结果引用
服务端只剩44之后的事件返回明确的重置提示，客户端重新获取任务快照
任务仍在后台执行展示处理中，再订阅后续事件
任务不存在或无权访问返回相应错误，停止无意义重连

对累加型文本，重复应用一个事件会把同一段内容追加两次，所以需要稳定事件ID或明确的偏移区间。对进度快照，可以依据版本只接受较新的状态，但“进度100%”仍应与业务成功状态分别判断。

浏览器保存的Last-Event-ID反映接收进度，不等于业务处理一定成功。若事件处理函数报错，页面可能尚未应用已接收事件。要求更可靠的恢复时，应维护应用自己的已应用游标，或者通过权威任务快照重新校正。

WebSocket与SSE的通信方式有什么不同

WebSocket建立双向消息通道，客户端和服务端都可以主动发送文本或二进制消息。经典HTTP/1.1握手使用Upgrade请求，服务端同意后返回101，再进入WebSocket帧传输；这不是每发一条消息都重新进行普通HTTP请求。RFC6455握手与数据传输

SSE本身是服务端向客户端推送，客户端需要提交新动作时，通常另发HTTP请求。WebSocket适合频繁双向交互，但业务层仍要定义消息类型、序号、鉴权、心跳、重连和状态恢复。选择它并不会自动解决重复消费或任务持久化。

这里的握手示例限定HTTP/1.1；其他HTTP版本存在不同接入方式，不能把Upgrade/101泛化成所有WebSocket连接的唯一过程。

已经发送了，页面为什么仍然迟迟不更新

数据可能停在应用缓冲、反向代理、压缩缓冲或客户端处理队列里。排查时分别记录生成事件、应用写出、代理转发和浏览器接收时间，才能知道延迟发生在哪段。

如果客户端处理速度长期低于发送速度，需要合并可替代的进度快照、限制队列，或者断开后重新同步。任务结果和不可丢失事件不能随意按“最新一条”覆盖。心跳只用于连接活性判断，也不能当作任务成功证据。

面试问答：SSE和WebSocket的本质区别

SSE 和 WebSocket 的区别是什么？

回答： SSE使用HTTP响应流向客户端持续发送文本事件，浏览器EventSource提供事件解析和重连支持；WebSocket建立双向消息通道，双方都可以主动发送文本或二进制消息。任务进度、通知等单向更新常适合SSE，频繁双向交互可以考虑WebSocket。

SSE的单向指这一条事件流，客户端仍可通过其他HTTP请求提交动作。原生EventSource的方法和自定义头能力有限，需要配合实际鉴权设计。WebSocket的双向传输也需要应用自己维护消息协议、状态和权限。

两者断线后都要面对业务恢复：任务ID标识长期任务，事件ID或版本处理回放与重复，权威快照纠正缺口。SSE自动携带接收游标不意味着服务器保存了所有历史，也不意味着页面已经成功应用每个事件。
