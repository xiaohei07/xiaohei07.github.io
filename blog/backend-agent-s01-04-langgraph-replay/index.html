先把报告任务表示成状态与节点

假设一个Agent负责整理报告，流程是“检索资料→生成草稿→人工确认→保存报告”。节点表示一次处理步骤，边表示下一步去哪里，状态保存各步骤需要继续使用的数据。

状态可以包含request_id、证据列表、草稿内容、草稿版本和审批结果。节点读取状态后返回更新；多个节点写入同一个字段时，需要预先定义怎样合并。这种合并规则在LangGraph中称为reducer。例如列表可以追加，单个草稿版本可以替换，不能把所有字段都默认相加。

LangGraph提供图式执行、条件分支和持久化等能力，适合需要追踪执行位置、暂停与恢复的流程。框架能够管理这些结构，具体业务的完成条件、权限与错误处理仍由应用定义。

检查点保存了什么

检查点（checkpoint）用于保存执行过程中可恢复的图状态与相关执行信息。通过同一个thread_id，应用可以找到对应任务的状态；历史检查点则可以区分任务在不同阶段的版本。

教学过程可以记为：

检查点草稿版本已完成内容后续动作
C1无检索完成生成草稿
C21草稿已生成等待确认
C31审批通过保存报告
C41保存结果已记录结束

持久化保存器应与运行要求匹配。内存保存器适合本地演示，进程退出后不能据此承诺仍可恢复。需要跨重启恢复时，要使用合适的持久化后端，并处理状态Schema升级、租户隔离和访问权限。

thread_id也只是状态定位信息，不能直接当成鉴权凭证。知道某个任务ID，不应该就能读取或批准别人的任务。

interrupt恢复时，从节点开头重新执行

LangGraph的interrupt()可以把审批内容返回给外部，暂停等待输入；恢复时通过Command(resume=...)提交结果。关键细节是：恢复会重新进入发生中断的节点，中断之前的代码可能再次执行。LangGraph中断说明

下面是节点逻辑示意，省略图的注册与保存器配置：

python
def review_node(state):
    # 这里只准备可重复计算的数据，不发送报告或扣费。
    payload = {
        "draft": state["draft"],
        "draft_version": state["draft_version"],
    }
    answer = interrupt(payload)
    return {"approval": answer}

这个片段依赖LangGraph的interrupt导入，展示的是节点结构，并非独立可运行程序。执行外部写入应放在明确的后续步骤，并为它设置业务幂等键。

例如用request_id + draft_version + action确定保存操作。如果第一次保存成功后进程退出，恢复后再次执行保存，可以查询相同操作的结果，而不是生成重复记录。检查点管理执行状态，幂等处理管理外部世界的重复副作用。

修改草稿以后，旧审批还有效吗

审批应该绑定用户实际看到的草稿版本。用户确认v1之后，如果Agent又把草稿改成v2，就不能沿用v1的批准去发布v2。

可以让审批记录保存草稿哈希、版本和操作类型。保存节点检查当前草稿是否仍与审批对象相同；不一致时重新进入确认流程。审批结果也要检查操作者身份、有效期及是否已经使用，不能只接受前端传来的approved=true。

这类条件应由业务代码验证。提示词可以说明审批规则，但不能代替真正的状态检查。

重放与分支为什么不会撤销外部操作

从旧检查点恢复，可以重新执行后面的节点。使用update_state修改旧状态会形成新的检查点分支，原历史仍然保留。修改时也会应用相应reducer，因此对列表字段的更新未必等同于直接覆盖。LangGraph时间旅行

假设C4对应的报告已经保存到外部系统，回到C2生成另一份草稿，只会改变新的执行分支。外部系统中的旧报告不会自动消失。模型调用也可能得到不同结果，所以重放不能被理解为完全相同的录像回放。

调试时应区分两种目的：查看已经记录的输入输出，只需读取历史；尝试另一条执行路径，才需要重新运行节点。后者可能产生新费用或写入，应使用隔离环境或模拟工具。

怎样验证恢复行为

本篇未安装LangGraph或调用付费模型，代码仅展示节点结构。接入框架后可以用确定性函数代替LLM，准备四个小测试：中断前的计数是否在恢复时增加；拒绝审批是否跳过保存；草稿变更后旧审批是否失效；保存成功后模拟进程退出，再恢复是否只产生一个业务结果。

还要测试状态字段变化与历史检查点兼容。一个旧任务保存的是draft字符串，新代码却期待draft对象时，恢复需要迁移或明确拒绝，不能让任务在半路以难以理解的方式失败。

面试追问：LangGraph的组成与适用范围

LangGraph 有哪些组件，以及它能实现的功能，这个框架的优点在哪里？

回答：核心包括状态Schema、处理节点、普通或条件边、状态合并规则，以及检查点保存与执行配置。它可以组织循环、分支、并行与子图，也能实现中断等待、恢复和历史分支。优势是把长流程的状态与执行关系显式化，便于追踪和恢复；代价是需要维护状态设计与持久化兼容。外部副作用的幂等、权限和业务成功条件仍需应用实现。

自拟追问：暂停在节点中间，恢复后之前的代码还会执行吗？会重新进入该节点，不能依赖普通局部变量保留，也不能在中断前随意放不可重复的操作。
