从少读一些数据开始理解索引

假设任务表有很多行，需要查询某个租户最近7天尚未处理的任务，按优先级取前20条。如果每次都读取全部记录，再过滤和排序，表越大，需要处理的无关数据就越多。

索引是为了支持访问而维护的数据组织。 本文以MySQL8.4的InnoDB为前提，讨论常见B+树索引。数据库以页组织和缓存数据，一次访问的成本不仅取决于比较了几个键，还与访问哪些页、页是否在缓存、是否需要回到完整记录有关。

B+树的内部节点保存导航信息，叶子层保存索引记录。 一个内部节点可以分出多个子节点，因此比同规模的二叉树更容易保持较少层级；叶子记录按键有序，适合定位起点后沿范围扫描。

可以用一个很小的教学树理解这个关系：假设内部节点最多指向4个孩子，每个叶子最多容纳3条记录。只有根和叶子两层时，理想满载容量为4×3=12条；再增加一层内部节点，则为4×4×3=48条。真实页容量取决于页大小、记录宽度、页开销与填充情况，不能用这个例子的数值估算实际数据库。

聚簇索引、二级索引和回表

InnoDB的聚簇索引叶子保存行数据。显式定义主键时，通常以主键组织聚簇索引；没有主键时，有其他选取规则，并非“没有主键就没有聚簇索引”。MySQL8.4索引组织

二级索引记录索引列以及对应主键。假设二级索引中找到任务ID为17，但查询还需要没有包含在该索引里的任务描述，数据库就需要再按主键访问聚簇索引。这个过程通常叫作回表。

如果索引能够提供查询需要的列，就具有覆盖查询的条件，可以减少为读取列数据而进行的回表。具体执行仍应结合可见性判断和执行计划检查，不能只看到列名存在就声称整条查询没有其他访问。

主键宽度也会影响二级索引体积，因为二级索引要保存主键信息。增加索引可以帮助读取，同时会占空间，并增加插入、更新和维护成本。需要根据真实查询选择，不能把所有常用列分别加索引就当作设计完成。

联合索引的顺序具体意味着什么

假设联合索引是(tenant_id, status, priority, id)。可以把它理解为先按租户排序，同一租户内按状态排序，再按优先级，最后按ID排序。

当tenant_id=7 AND status='pending'固定下来后，对应索引范围内部就可以继续按priority,id的顺序读取。若跳过租户条件，只按优先级查询，所有租户的优先级记录通常分散在不同区段，不能直接当作全表按优先级排列。

这就是最左前缀有用的原因。它描述有序组合键怎样支持连续定位，不是给SQL书写顺序加限制。WHERE status='pending' AND tenant_id=7交换条件书写位置，通常不会因此改变等值条件本身能否用于定位。多列索引

范围条件以后，后续列是否还能参与过滤、索引条件下推或其他访问方式，需要看实际计划；“后面所有列一律失效”过于粗糙。应分别判断是否缩小访问范围、是否减少回表、是否提供排序，以及总共扫描多少记录。

同一个任务列表为什么可能有两个合理索引

教学查询如下，:cutoff表示事先确定的7天前时间边界，具体参数绑定方式依驱动而定：

sql
SELECT id, priority, created_at
FROM task
WHERE tenant_id = 7
  AND status = 'pending'
  AND created_at >= :cutoff
ORDER BY priority ASC, id ASC
LIMIT 20;

加入唯一ID作为第二排序条件，是为了让同优先级任务的次序稳定。下面比较的是候选设计，不是本机运行过的执行计划：

候选索引主要优势可能多做的工作
(tenant_id,status,created_at,priority,id)先把候选压缩到近期记录近期范围内不一定直接满足全局priority、id排序
(tenant_id,status,priority,id,created_at)固定前两列后按目标顺序寻找可能跳过很多日期不满足的旧记录

如果最近7天的数据很少，第一个索引先过滤再排序可能更合适。如果按优先级扫描很快就能找到20条近期记录，第二个索引可能更快停止。反过来，若低优先级区段里几乎都是很旧的记录，第二个索引可能扫描很久。

索引选择要结合数据分布和访问目标。 比较时需要查看估计与实际扫描行数、过滤比例、排序、回表和耗时，也要评估索引宽度与写入代价。本文尚未在MySQL环境执行该SQL，不能给出哪一个一定更快的结论。

面试问答：为什么用B+树，联合索引何时没有收益

为什么要用B+树

回答： 对页式存储中的有序索引，B+树可以用较高扇出保持较少层级，并通过有序叶子支持范围扫描和排序访问。性能收益来自减少无关记录与数据页访问，同时适合维护动态插入、删除的数据。

内部节点主要用于导航，叶子保存索引记录。等值查询沿路径定位，范围查询找到起点后继续按键顺序读取。在InnoDB中，聚簇索引叶子保存完整行，二级索引携带主键，查询需要非覆盖列时还要回表，因此访问成本不能只用树高解释。

B+树也有写入与空间成本，页分裂、缓存命中和记录宽度都会影响实际性能。对纯等值查找，哈希结构可能有适合的场景；对写入模式不同的存储系统，也可能选择LSM等组织。不能把B+树描述成所有索引任务的统一最优结构。

延伸追问（自拟）：树只有三层，是否就一定发生三次磁盘I/O？ 不一定。部分页可能已在缓存中，二级索引查询还可能回表，实际I/O还受预读与访问路径影响。逻辑访问层级和物理磁盘读取次数需要区分。

联合索引在哪些场景下会失效？

回答： 先区分三种现象：谓词难以构造有效的索引范围；优化器估计使用该索引不划算；实际使用了索引，但仍扫描大量记录。这三种都可能表现为查询很慢，却不是同一个问题。

联合索引按组合键有序组织，缺少前导列约束时通常难以利用后续列直接缩小连续范围；函数、类型转换和匹配方式也可能影响范围构造，但应按具体表达式与版本判断。即使访问条件可用，如果命中大部分记录、回表成本过高，优化器也可能选择其他路径。存在跳跃扫描、函数索引等功能时，更不能只背绝对禁用清单。

检查应从实际SQL、索引定义和数据分布开始，再用执行计划确认访问类型、使用键列、扫描量、过滤和排序。例如日期范围与优先级排序之间的取舍，需要比较两种候选索引的实际工作量，不能只说“遵守最左前缀即可”。

延伸追问（自拟）：SQL条件的书写顺序必须和索引一致吗？ 对等值AND条件，通常由优化器分析条件，书写先后本身不是组合键的排序规则。更重要的是有哪些约束、对应列顺序，以及实际选择的访问路径。
