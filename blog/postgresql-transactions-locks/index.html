作者审核一条反馈时，至少要更新状态、记录审核时间与审核人，再写一条审计事件。如果只完成其中一部分，之后就难以判断这次处理究竟发生了什么。事务将这些相关操作组织为一个提交单位。

一、commit与rollback分别改变什么

sql
BEGIN;
-- 修改反馈状态、审核信息
-- 插入同一次审核的审计记录
COMMIT;

提交成功后，这些更改一起成为已提交数据；失败并回滚时，这次事务未提交的更改撤销。事务原子性解决的是这一组数据库操作的整体完成关系，不能把已经发送出去的邮件或HTTP响应也自动撤回。事务入门说明了提交、回滚与中间状态。

事务还涉及一致性、隔离性和持久性。业务约束与数据库规则共同维护一致性；隔离性控制并发事务怎样观察和影响数据；持久性取决于数据库的提交与存储保证，不能进一步推成“服务器和磁盘损坏也永不丢数据”。备份仍然需要。

二、两个审核请求同时到达会怎样

假设反馈F初始为pending，请求A要标记resolved，请求B要标记rejected。如果两者分别读取pending，再无条件更新，后写入者可能覆盖前者。

本站使用SELECT ... FOR UPDATE取得反馈行，再检查状态。按默认Read Committed隔离级别推演：

顺序请求A请求B
1锁住F，读取pending尝试锁F，等待
2修改状态并新增审计等待
3提交，释放锁继续取得当前行
4返回成功看到已处理状态，返回409

行锁协调的是数据库事务对对应行的竞争，普通读取仍有MVCC等规则，不是把整张表的所有访问都停住。锁通常保留到事务结束，因此不要在持锁期间等待用户操作或慢速外部请求。显式锁说明列出了冲突和等待行为。

当前接口状态只允许pending转到resolved或rejected。再次审核会报冲突。表里存在某个状态值，与接口允许从任何状态任意转换，是两套规则。

上表依赖Read Committed条件。如果改用Repeatable Read或Serializable，目标在事务开始后被其他事务改变时，可能转为序列化错误；应用需要对应的冲突和重试策略。不能把这里的“等待后409”推广到所有数据库和隔离级别。

三、乐观更新能怎样改写这个例子

一种备选是带条件更新：

sql
UPDATE feedback
SET status = 'resolved'
WHERE id = :feedback_id AND status = 'pending'
RETURNING id;

冒号参数是这里的抽象占位，实际语法取决于使用的驱动或SQLAlchemy接口。更新到0行时，再按业务判断是不存在还是已处理；更新成功时，把审计写入同一事务。这里是备选设计，本站当前采用显式行锁。

选择依据包括冲突频率、事务内需要读取多少信息、是否需要明确等待，以及实现是否容易验证。使用数据库行锁已经能协调本数据库中的审核竞争，增加Redis分布式锁反而需要处理锁过期、续期和数据库提交之间的关系，没有现成理由就不用增加这一层。

四、隔离级别不能用“开了事务”一笔带过

PostgreSQL默认Read Committed下，不同语句可能看到不同的已提交快照。先COUNT再读取一页列表，并不天然保证两次查询之间没有新反馈进入。对作者收件箱，这可能是可接受的实时变化；若要求严格一致的快照，就要重新评估事务隔离和分页契约。隔离级别文档解释了允许出现的现象与序列化失败。

更高隔离级别可能带来重试要求，锁也可能形成死锁。统一锁顺序、缩短事务和有边界的重试，比笼统说“加锁就安全”更准确。本文没有在生产环境制造锁等待或死锁。

五、数据库迁移为什么与改模型不同

修改Python里的字段定义，不会让已经存在的数据库表自动获得相同结构。Alembic记录版本迁移并执行对应DDL，模型文件与迁移文件要一起核对。Alembic教程介绍了版本链和升级流程。

如果以后给反馈增加字段，兼容方式可以是先增加允许旧代码工作的字段，再部署新代码、回填并验证，最后收紧约束。删除旧列之后，旧代码可能无法运行；执行downgrade也不保证找回被删除的值。因此代码回滚、Schema回退和备份恢复应分别设计。

最值得继续追问的失败位置是“提交成功后连接断了”。数据库可能已有结果，客户端却不确定。事务并不能替代请求幂等，这部分会在项目反馈链中继续讨论。
