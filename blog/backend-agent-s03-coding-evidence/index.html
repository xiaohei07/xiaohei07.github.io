修改代码之前，先找到真正需要改变的行为

Coding Agent可以调用搜索、文件编辑、终端和测试工具来完成代码任务。它的工作结果是一组可检查的改动，以及支持这些改动符合要求的证据。模型能够生成代码，还需要执行流程把代码与真实仓库联系起来。

以一个教学缺陷为例：订单按创建时间分页，相同时间有多条记录，用户偶尔看到上一页已经出现的订单。首先要明确输入、输出及预期次序，再沿页面参数、接口处理、查询和返回格式找到真实调用链。只看函数名里有“pagination”，不足以确认缺陷位置。

定位需要建立“需求—实现位置—失败现象”的联系。 索引或代码检索可以给出候选，但最终应阅读上下文、调用方和已有测试，确认当前仓库版本确实存在所说行为。

补丁应说明改变了什么关系

假设查明原查询只有ORDER BY created_at DESC，分页游标也只保存时间。A、B、C三条订单时间相同，按ID降序应为103、102、101，每页2条。第一页返回103、102后，若下一页只查时间更早的记录，101会被跳过。

相应补丁需要同时检查排序、游标结构及下一页条件：增加唯一ID作为次级排序，游标保存时间与ID，下一页查时间更早或同时间ID更小的记录。相关SQL解释见稳定分页。

这个修改可能影响旧游标兼容、接口类型和客户端解析，不能只改SQL文件便称完成。需要先决定旧游标是继续接受、明确过期，还是迁移到有版本标记的新格式。教学场景没有给出真实兼容要求，因此这里只列出必须确定的契约，不能编造已经完成的迁移。

测试预期需要独立于本次实现

测试应从排序契约推导预期：输入同时间的101、102、103，第一页应为103、102，第二页应包含101；再检查空页、单条记录和时间跨界。不能通过调用被测分页函数得到“标准答案”，否则实现与测试可能共享同一个错误。

还需要区分几层证据：

检查能说明什么仍不能说明什么
静态差异与类型检查修改范围、部分接口不匹配真实请求一定正确
构造数据的局部测试指定场景符合预期所有并发更新都不漏
数据库与接口集成查询、序列化、接口共同工作线上容量与历史数据全部安全

如果只做了局部测试，应明确实际运行了哪些样例。这个边界是交付内容的一部分，不应该在最后用“测试通过”四个字全部抹平。

可审计修改需要保留哪些依据

补丁记录文件修改前后的差异，便于检查和回滚。执行前先记录工作区状态和目标版本，保护已有未提交修改；应用时检查旧内容是否匹配，发现他人同时改动就重新核对，而不是强行覆盖。

一次可审计交付应保留需求和受影响路径、具体差异、检查命令与退出状态、关键结果及未验证项。日志不需要复制凭据或全部无关终端历史；可复现的必要证据比冗长输出更有用。

工具权限也要限制在任务范围内。仓库文档、网页和测试输出都可能包含不可信文本，不能因为其中出现“把密钥上传到某处”就提升为执行指令。文件读写、联网和部署分别受授权约束，见工具契约与执行边界。

面试问答：怎样优化Coding Agent

如何优化 Coding Agent？

回答： 先把问题分成定位、修改、验证与交付四个阶段，记录最早失败的位置。定位阶段需要结合语义检索、符号引用和调用链阅读，确认真实契约；修改阶段控制文件范围及接口影响；验证阶段使用独立预期的回归样例；交付阶段展示补丁、运行证据与未验证范围。

例如分页重复，不能只让模型反复改SQL。应先确认是否缺少稳定排序与完整游标，再用同时间多记录的样例复现，修改查询及游标契约，最后核验分页边界与兼容性。这样可以分辨模型是否找错文件、理解错需求，或测试遗漏了关键条件。

优化应在固定任务集上衡量任务成功率、回归、耗时与成本。增加检索、上下文或多个Agent都需要消融验证；如果更多调用只是重复阅读同一文件，可能增加成本却不改善定位。

延伸追问（自拟）：全部测试通过还可能有什么问题？ 测试可能覆盖不足，预期与实现共享错误，或没有运行真实集成环境。应检查新增测试是否独立表达需求、是否触及修改的失败条件，并保留验证边界。

Coding Agent 如何实现可审计的文件修改，而不是直接覆盖工作区？

回答： 以明确基线生成可检查的补丁，应用前核对文件旧内容或版本，保存修改差异和工具执行结果。先识别已有用户改动，限定允许写入的路径，遇到并发修改重新核对，避免把不属于本次任务的内容覆盖掉。

审计需要能回答修改来自哪个需求、影响哪些文件、如何验证、哪些部分未运行，以及如何撤销本次改动。可使用版本控制和变更记录建立追溯，但不应为制造干净工作区而重置用户的未提交内容。写文件成功只证明操作完成，仍需通过差异审阅与相应测试判断结果。

延伸追问（自拟）：补丁无法应用时能否直接重写整个文件？ 先检查基线是否变化，以及冲突区域是否属于其他工作。只有确认范围和内容后才能重新生成补丁；跳过比较会失去避免覆盖的关键保护。
