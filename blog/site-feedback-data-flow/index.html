在文章下填写纠错后，页面会显示一个回执编号。这个编号背后有完整的处理过程：输入框保存字符串，浏览器发JSON，后端检查内容，再写入数据库。只有把这些变化按顺序看清楚，才能解释失败时应该保留什么、能否重试。

本站反馈只供作者查看，类型包括纠错、问题和其他建议。下面使用人工构造的消息，不展示真实读者内容；文章中的请求演示也不会提交生产数据。

一、从输入框到请求体

假设当前文章ID为python-slices，读者选择question，填写“这个例子如何处理空列表”。React的message状态保存输入，contentId由文章详情传给FeedbackForm。

点击提交后，代码先阻止表单默认跳转，清理上一次提示，检查去除首尾空白后的长度，再设置busy。请求体形成如下数据：

json
{
  "content_id": "python-slices",
  "kind": "question",
  "message": "这个例子如何处理空列表"
}

apiRequest把路径组织为/api/v1/feedback，设置JSON内容类型和15秒客户端等待上限。等待期间禁用相关控件，成功才清空输入，失败保留。按钮禁用改善当前页面的连续点击体验，不能阻止脚本客户端或另一个页面发请求。

二、网关与API检查哪些条件

Nginx按/api/路径转发请求，并限制请求体大小；API还有自己的请求体限制。接口检查来源，Pydantic解析模型，限流器检查对应动作与客户端地址，业务逻辑再查内容登记。

FeedbackCreate限定content_id格式、kind允许值和消息长度，拒绝多余字段与NUL。db.get(ContentEntry, payload.content_id)继续确认内容存在且发布状态允许。两步都成功，才能创建反馈。

这里按职责解释检查，并不承诺任意多种错误同时出现时固定先返回某个错误。中间件、依赖和参数解析共同决定具体执行行为，需以实际版本和测试为准。

SQLAlchemy的add还没有完成持久提交，commit成功后才返回201。回执的pending表示等待作者处理，不表示问题已经解决。数据库里的ID是反馈身份，与文章的content_id是两个不同字段。

四、失败发生在不同阶段，结果并不相同

输入不符合规则时返回422，当前请求不会进入正常写库路径。请求过密可能返回429。数据库不可用或SQLAlchemy异常由应用返回503；网关故障还可能形成其他状态或网络错误。

如果在提交前事务失败且回滚，没有本次成功写入。如果提交已经成功，却在返回响应时断开，数据库可能存在反馈，浏览器仍只知道“没有确认成功”。因此客户端的超时提示保留输入，并提醒稍后确认再重试，不把超时直接写成“数据库没有保存”。

当前公开接口没有按请求键查询已有回执的能力，用户无法靠自动查询完成无歧义确认。这是现有设计限制，前端提示只能诚实表达不确定性，不能凭空提供没有的恢复功能。

还要区分三个计时：前端15秒控制浏览器愿意等多久；连接池3秒控制等待空闲连接多久；驱动建立连接的3秒控制新连接阶段。它们作用于不同位置，不是三个数字相加便得到一次请求的固定耗时。数据库取得连接后还可能执行SQL或等待锁，配置没有给出整条链的容量保证。

五、为什么当前还不能保证重复提交只产生一条

同一页面的busy只覆盖一次等待窗口，IP限流只限制频率。第一次提交成功后响应丢失，第二次合法POST仍可能创建另一条记录。本站没有请求幂等键，因此不会把当前实现写成exactly-once。

拟议方案可以为一次逻辑提交生成requestId，服务端使用唯一约束保存该键、请求摘要和回执，在同一事务中完成。相同键且相同内容重放回执；相同键却不同内容拒绝。还要定义匿名客户端范围、过期时间、处理中状态和失败后的重试策略。

“先查询有没有，再插入”不能单独保证并发正确，两次查询可能都没找到。需要数据库唯一性和事务共同约束。若把记录放Redis、业务数据放PostgreSQL，又增加了跨存储一致性问题，这也解释了为什么不能只加一个缓存键就结束设计。

六、如果要把反馈扩展成公开评论

需要新增公开展示条件、审核与删除规则、内容安全处理、滥用控制，以及可能的用户身份。作者把一条反馈标成resolved，并不会自动生成回复文本；当前模型也没有读者点赞关系。

公开评论的读取流与私密收件箱不同，缓存和分页也要重新设计。可以复用输入校验与事务经验，但不应直接把当前管理列表公开给所有人。

读完后可以用请求链演示分别选择正常提交、字段失败和数据库失败。演示只显示已定义的分支，不覆盖“数据库已提交但回执丢失”的全部网络竞态，这种不确定状态仍以上面的文字分析为准。
