psycopg入门：数据库驱动、参数绑定与类型适配

SQLAlchemy已经能写查询，为什么依赖里还有psycopg？因为Python中描述数据库操作，与真正连接PostgreSQL、传送参数、读取响应之间，还需要驱动。本站使用psycopg3完成这一层工作。

Pydantic处理输入模型，SQLAlchemy组织数据库工作，psycopg负责驱动接口。它们并不是三个都要各自校验一次相同业务的库。postgresql+psycopg://...中的前半部分指定数据库与驱动组合，连接信息来自私有配置，不能写进浏览器代码。

本站没有额外使用psycopg_pool，连接池由SQLAlchemy管理。依赖里出现psycopg，不代表同时运行两套池。

直接使用驱动时如何传参数

下面的独立教学片段从环境变量取得练习库连接信息，查询指定内容ID的待审核反馈。不要连接生产库做练习：

python
import os
import psycopg

with psycopg.connect(os.environ["LESSON_DATABASE_URL"]) as conn:
    with conn.cursor() as cur:
        cur.execute(
            "SELECT id, message FROM feedback WHERE content_id = %s AND status = %s",
            ("python-slices", "pending"),
        )
        rows = cur.fetchall()

SQL文本和参数分别传递，%s由驱动按参数规则处理，不是让Python先做字符串格式化。占位符外面也不手工加引号；数值同样通过参数传入。只有一个参数时，元组写成(value,)，逗号不能省略。psycopg参数文档说明了这些约定。

如果用f-string把用户消息拼入SQL，单引号等内容可能改变SQL结构。参数绑定将值作为数据传递，避免这种混入语句结构的情况。它解决SQL值的传递问题，不会自动清理HTML，也不会决定用户是否有权执行这条查询。

表名和排序字段不能当普通值绑定

参数通常用于值，不能用SELECT * FROM %s把任意表名当参数传入。如果业务确实允许选择不同表或排序列，应先做允许值映射，再使用psycopg.sql.Identifier等组合接口处理标识符。

最简单的排序选择往往是让前端提交一个有限枚举，例如newest，后端映射到固定的排序表达式。不要直接接受用户提供的一段ORDER BY文本。ORM同样不能保护程序自行拼接的危险SQL字符串。

Python值怎样变成数据库值

字符串、整数、UUID和日期时间需要在Python表示与PostgreSQL类型之间转换，psycopg的适配器负责这一步。结果返回时再转换为相应Python对象；ORM可以继续把结果组织成映射实例。数据适配说明介绍了这套转换机制。

驱动转换与业务验证也不同。消息是否至少5个字符属于接口约束，PostgreSQL文本不接受NUL又是存储边界。本站在Pydantic模型里提前拒绝NUL，避免把一个可预期的输入问题拖到数据库阶段才变成错误。

连接上下文与事务如何结束

psycopg默认事务模式下，执行查询通常也会启动事务。长期保持连接却不结束事务，可能形成idle in transaction，带来资源和维护问题。连接上下文正常退出时提交，异常退出时回滚并关闭；具体用法还可通过显式事务块控制。事务管理文档说明了默认与autocommit行为。

这与上一篇的with Session(...)不同：不能看到with就假定所有库都自动commit。上下文管理器只是一种语法，退出动作由对象实现决定。本站通过SQLAlchemy Session管理事务时，应遵循Session边界，不在中间随意对底层连接另起一套提交逻辑。

安装形式与运行方式不要混为一谈

本站依赖使用psycopg[binary]，便于取得相应二进制实现；这不等于异步连接，也不代表每次查询都传二进制业务格式。同步/异步API、安装实现和数据适配格式分别是不同维度。

定位驱动报错时，可以按阶段判断：导入失败看解释器与安装；建立连接失败看地址、端口、认证与网络；执行失败看SQL、参数和数据库约束；连接中途断开再考虑事务结果是否确定。不要把所有报错都归为“psycopg没装好”。
