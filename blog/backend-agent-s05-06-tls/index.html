加密连接还需要确认连接的是谁

DNS给出服务器地址后，客户端可以向这个地址建立连接。但如果地址被错误配置，或者网络中的攻击者把请求引到自己的服务器，仅有“这条连接加密了”还不足以确认目标。

TLS同时处理机密性、完整性以及相应模式下的身份认证。HTTPS把HTTP运行在TLS保护的连接上。本篇讨论常见的TLS1.3首次握手、服务器证书认证，不把它与旧版RSA密钥交换或PSK恢复流程混写。

先区分三个对象：证书把服务身份与公钥联系起来；私钥由服务端持有，用来完成相应证明；会话流量密钥用于保护本次连接的数据。服务器私钥不会通过握手发给客户端，证书也不是用来逐段加密网页内容的工具。

一次TLS1.3握手怎样建立保护

客户端发送ClientHello，带上支持的协议与密码参数以及密钥共享信息。服务端通过ServerHello选择参数并给出自己的密钥共享。以常见的临时ECDHE为例，双方各自计算共享秘密，再通过密钥派生过程得到握手阶段和应用阶段的不同密钥。

之后，服务端发送加密的握手内容，其中包括证书、CertificateVerify和Finished。客户端验证后发送自己的Finished，双方再使用相应应用流量密钥保护HTTP数据。这里略去可选客户端认证与HelloRetryRequest分支，保留它们可能导致消息顺序增加的条件。TLS1.3握手结构

CertificateVerify证明对端能够使用证书对应的私钥，并把证明绑定到本次握手记录；Finished核对握手完整性及派生出的密钥。这解释了为何复制一张公开证书，不能直接冒充证书对应的服务器。

证书链可信与名称匹配需要分别验证

假设浏览器访问https://notes.example.test，收到一张SAN中仅包含shop.example.test的证书。即使证书由受信任CA签发，仍然不能用它证明对方是notes.example.test。

客户端通常需要检查：

  1. 证书是否在有效期内，使用目的和算法等是否符合策略。
  2. 能否沿中间证书建立到本地信任锚的有效路径；签名和约束是否成立。
  3. 参考身份与证书身份是否匹配。参考身份来自用户请求的目标或受信任配置，不能拿服务器自己声称的名称替换。
  4. 按客户端策略处理撤销、证书透明度等要求，再结合握手中的私钥证明。

DNS名称主要匹配SAN中的dNSName，不能依赖历史上“随便看Common Name就行”的做法。直接通过IP访问时，需要按IP身份规则核对证书；把DNS名填入Host头不自动改变TLS客户端的验证目标。服务身份匹配规范

SNI帮助服务器在握手中选择要使用的站点配置和证书，主机名校验则由客户端判断证书是否适用于目标，二者有联系但职责不同。SNI选对证书，也不代表证书链一定有效。

三种失败怎样沿验证路径定位

情况可能停在哪一层需要核对的证据
TCP端口无法建立连接TLS之前路由、防火墙、监听端口、连接错误
能取得证书，但提示名称不符身份匹配URL主机名、SNI、SAN、代理转发目标
名称正确，但证书链验证失败信任路径中间证书是否缺失、信任根、期限与系统时间

一个教学部署中，新证书只在服务器上配置了叶证书，客户端缺少中间证书，可能无法建立信任链。补齐服务端应发送的中间链可以解决这类问题；把所有客户端设置成“忽略证书错误”会同时放弃身份验证，错误性质已经改变。

另一个例子是连接开发机IP，但证书只覆盖测试域名。应该使用与证书匹配的名称和解析，或给测试环境配置适当身份，而不是认为“同一台机器就无需名称匹配”。证书认证的是约定身份，机器是否恰好相同不能替代验证规则。

HTTPS对DNS劫持的保护有什么范围

攻击者把DNS结果改成自己的地址，但无法提供目标名称的可信证书和相应私钥证明时，正常验证的客户端应拒绝建立被认证的HTTPS连接。这里成立的前提包括客户端没有跳过验证、信任库没有被恶意改变、目标身份来源可信。

HTTPS不能替应用检查业务授权，也不能解决服务端本身被入侵或客户端在加密前泄露内容。它保护的是连接上的通信与身份关系。登录之后能否读取另一个用户的报告，仍然是应用授权问题。

恢复连接与0-RTT为何需要单独讨论

会话恢复可以减少再次连接的成本，TLS1.3还允许特定条件下发送早期数据。但0-RTT早期数据可能被重放，不能只因为它在加密连接里就把重复提交视为不可能。扣款、创建订单等操作应根据协议及应用策略禁用早期执行，或落实去重和幂等。恢复握手也不等于每次都重新发送完整证书链。TLS1.3早期数据与重放

面试问答：TLS握手流程

TLS 握手流程。

回答： 以TLS1.3首次服务器证书认证为例，客户端和服务端先交换Hello消息及密钥共享，协商参数并派生握手密钥；服务端发送证书、CertificateVerify和Finished；客户端检查信任链、目标身份及握手证明，完成自己的Finished，之后使用应用流量密钥保护数据。

密钥交换、身份验证和握手完整性是互相配合的环节。证书链可信仍需核对目标主机名，持有公开证书也不等于持有私钥。恢复、客户端认证及HelloRetryRequest会改变具体消息路径，因此要先说明版本和模式。

延伸追问（自拟）：证书过期后，数据加密算法一定不能算了吗？ 加密运算未必失效，但对端已经不满足客户端认可的身份有效性条件。不能用“仍能加密”代替“应该信任”。

原问与出处见逐题映射。本篇未对真实站点执行证书探测，示例中的失败原因是机制推演。
