把一个任务交给另一个Agent，需要交代什么

假设主Agent正在整理旅行方案，需要另一个Agent查询交通选项。除了“查一下车票”，还应提供出发地、目的地、日期、允许的预算和返回格式，并明确这里只查询，不购买。

A2A（Agent2Agent）是一种Agent之间交换消息、任务状态与产物的协议。它帮助不同实现之间表达“能做什么、任务进行到哪里、需要什么输入、返回了什么结果”，不要求对方公开内部提示词或全部工具实现。A2A协议

A2A提供通信约定，业务上能否信任某个Agent、是否允许委派、是否有权访问目标数据，需要由宿主与服务单独确定。本文按官方规范中的概念说明；不同协议版本的字段和状态枚举可能不同，接入时应固定版本。

Agent Card、Message、Task和Artifact分别是什么

Agent Card描述Agent身份、服务入口、能力和认证等信息，用于发现与选择。它是能力声明，不是已经验证的能力证明；卡片来源和服务地址也需要可信校验。

Message承载一次交流内容，例如任务请求或补充条件。简单请求可能直接返回Message；需要跟踪的长任务则可以返回Task，带任务ID和状态。Artifact表示任务产物，例如交通选项表、报告文件或结构化结果。

可以把一次教学交互记为：

text
主Agent发送：查询周五A城到B城的交通方案
远端返回：任务T7，缺少具体日期
主Agent补充：2026-11-06，仍只查询
远端更新：处理中
远端完成：产物R2，含方案、查询时间和数据来源

日期只是构造样例，并未执行真实查询。重要的是，补充信息与任务T7关联，结果R2也能追溯到这个任务，而不是散落在没有关联的自然语言消息里。

contextId和taskId怎样区分

contextId用于组织相关交互，taskId标识具体工作单元。一个上下文可以包含多个任务，例如交通查询、住宿查询和最终行程整理。

官方生命周期说明区分等待输入与终态。任务需要补充信息时，可以继续同一任务；已经完成、取消、拒绝或失败的任务不会直接重新启动，后续修改应创建关联的新任务。A2A任务生命周期

等待输入不等于执行失败，任务已受理也不等于产物完成。主Agent必须检查状态，不能收到任务ID后就报告“已经查好”。

流式更新、轮询和回调怎样选择

短任务可以直接等待响应；较长任务可以通过流式事件观察进展，也可以按协议查询状态。支持推送回调时，回调地址与认证需要单独配置。

流断开不代表任务停止。客户端应使用任务ID查询最终状态，而不是马上创建一份重复任务。回调或状态事件也可能重复、迟到，处理端需要按任务版本或事件标识去重，并避免旧事件把终态改回处理中。

取消通常是请求远端停止工作，需要检查最终是否接受取消。已经发生的外部写入未必能撤销，取消交通查询和取消已出票订单的业务含义也不同。

委派出去以后，权限是否一起传过去

主Agent拥有某个账户权限，不表示远端Agent自动获得同样权限。应通过明确的认证与授权机制，只传递完成子任务所需的数据和能力。

旅行查询只需要路线与日期时，不应把整个用户历史、支付凭证和无关文件全部传过去。产物也应检查来源与访问范围：远端返回一个URL，主Agent不能未经验证就带着本地凭证访问它。

如果任务涉及购买，需要保留用户授权的具体对象和条件。一个Agent写“用户已同意”只是消息内容，不能自动替代可信授权记录。协议中的任务关联标识也不能作为权限证明。

多任务协作怎样避免重复与相互覆盖

交通与住宿查询可以在输入独立时并行，最终行程整理则等待必要结果。每个任务返回结构化状态、证据和未解决问题，主Agent负责检查时间和预算是否一致。

如果交通结果更新了到达时间，住宿任务可能需要重算入住安排。应记录依赖版本，例如“住宿建议基于交通产物R2”；不要让旧版本结果在后到达时覆盖新方案。

可以用三个本地模拟任务验证：一个直接完成、一个等待输入、一个超时后仍在远端完成。检查主Agent是否正确继续、查询和合并。本文未连接A2A服务，不能把这种流程推演当成协议联调结果。

面试追问：A2A解决哪类协作问题

Agent 间通信协议：你了解 A2A（Agent-to-Agent 协作与通信协议）吗？

回答：A2A约定Agent之间的能力发现、消息交换、任务状态与产物表达，适合需要独立执行和持续跟踪的跨Agent协作。调用方可以发现服务能力、提交任务、补充输入并获取结果，而不必知道远端内部的模型与工具。实现中仍需处理身份、授权、任务去重、取消和产物验收。

自拟追问：与MCP有什么区别？MCP主要规范宿主与工具、资源等能力服务的交互；A2A围绕另一个Agent承担的任务及其生命周期组织协作。实际系统可以同时使用，远端Agent内部也可能通过MCP调用工具，但不应仅凭名字判断功能边界。
