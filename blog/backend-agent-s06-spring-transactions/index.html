事务注解、代理拦截器与事务管理器

@Transactional表达方法的事务属性，但事务还需要运行时组件执行。以Spring的命令式、代理模式和JDBC事务为例，调用方先经过容器创建的代理，事务拦截器读取配置，通过事务管理器开启或加入事务，再调用业务方法，最后按结果决定提交或回滚。

代理是处在调用方与目标对象之间、能够加入额外处理的对象。事务管理器负责把抽象事务操作落实到数据库连接等资源上。因此，事务生效需要注解配置、实际代理调用和受管理资源共同参与。

这里按Spring官方当前参考文档中的代理事务机制讲解；回滚默认值可被配置覆盖，6.2起也支持改变全局异常回滚默认。项目判断应核对实际版本、事务管理器与配置，确认实际调用采用哪一组规则。Spring事务注解

同类自调用的代理绕过与已有事务

考虑一个没有事务的submit()调用同一对象中的saveOrder()，后者带@Transactional：

text
外部调用 → 代理 → submit目标方法
                     ↓ this.saveOrder()
                 saveOrder目标方法

第二次调用直接发生在目标对象内部，没有重新经过代理。因此在默认代理模式下，saveOrder上的事务声明不会因为这次内部调用而被重新拦截。

需要准确区分两种情况：如果submit本来没有事务，不能期待saveOrder自动新建事务；如果submit已经处于事务中，saveOrder里的数据库操作可能仍在已有事务内执行，但其独立传播设置未必被应用。判断自调用的结果，需要同时检查外层是否已有事务，以及内层声明是否经过拦截。

常见处理是把事务边界放在外部经代理调用的服务方法上，或将需要独立事务的方法放到另一个合适的Bean。AspectJ织入模式的行为不同，不能把代理限制推广到所有模式。

REQUIRED、REQUIRES_NEW与NESTED的传播关系

传播行为决定方法被调用时怎样处理已有事务。它和数据库隔离级别不同：传播讨论事务之间怎样衔接，隔离讨论并发事务怎样观察数据。

传播行为已有事务时的主要行为需要注意的后果
REQUIRED加入现有事务，没有则创建内外逻辑范围可能共用同一个物理事务
REQUIRES_NEW暂停外层事务，使用独立事务内层提交不随外层回滚撤销；需要额外连接资源
NESTED支持时使用同一物理事务的保存点回滚到保存点，最终仍受外层提交约束

例如创建订单和写审计记录都使用REQUIRED，审计失败把共享事务标成rollback-only后，外层即使捕获异常，也不能安全地把整个事务当成可提交。外层提交时可能收到UnexpectedRollbackException。

若审计通过独立代理调用REQUIRES_NEW并提交，之后订单失败回滚，审计仍可能保留。它适合“记录一次失败尝试”等语义，但如果审计写的是“订单已成功创建”，内容就会与真实状态冲突。独立提交改变的是业务语义，同时也增加连接池需求。Spring事务传播

异常规则、线程关联与外部操作的回滚范围

默认规则通常对RuntimeException和Error回滚，对受检异常不自动回滚；实际可通过rollbackFor、noRollbackFor或全局设置改变。异常被业务捕获且正常返回后，拦截器也未必能据此知道需要回滚。应根据业务结果选择抛出适当异常或明确设置回滚状态。

命令式事务通常与当前执行线程关联。自行创建另一个线程执行数据库操作，不会因为调用方有注解就自动继承事务。响应式事务使用不同的上下文机制，不能直接套用ThreadLocal解释。

数据库回滚作用于该事务管理的数据库变更，已经发送的邮件或完成的外部付款则需要独立的业务处理。需要让数据库变更与待发送事件保持一致时，可以使用Outbox等方案，再处理外部操作的幂等与补偿。将耗时网络请求放在长事务中，还可能延长锁持有时间。

面试问答：事务注解的代理实现与生效条件

23.Spring事务注解@Transaction的底层实现

原题写作@Transaction；Spring常用的对应注解名是@Transactional。保留题面，下面按该事务注解回答。

回答： 默认声明式事务通常通过AOP代理实现。外部调用经过代理，事务拦截器解析方法或类上的事务属性，通过适用的事务管理器开启或加入事务，执行业务方法，再根据正常返回、异常和回滚规则提交或回滚。JDBC场景最终操作受管理的数据库连接，隔离语义仍由数据库提供。

是否生效要检查调用是否经过代理、对象是否受容器管理、事务管理器与资源是否匹配，以及方法是否可被所用代理机制拦截。同类内部自调用通常不会触发新的事务拦截；但若外层已有事务，内部数据库操作可能仍加入该事务，所以不能简单说自调用时全部无事务。

传播行为决定与已有事务的关系。REQUIRED通常共享事务，REQUIRES_NEW使用独立事务，NESTED在支持时使用保存点。异常回滚规则可配置，捕获异常后正常返回、跨线程执行或调用外部API，也可能使实际效果与“全部回滚”的预期不同。

延伸追问（自拟）：内层REQUIRED失败，外层捕获异常后为什么还不能提交？ 内层可能已经把共享的物理事务标记为rollback-only。捕获Java异常不会清除这个状态，外层最终提交会被拒绝。需要重新审视事务范围和失败处理，不能只增加try/catch。
