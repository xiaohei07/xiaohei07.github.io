一、题目一：接雨水

42. 接雨水力扣原题 ↗

题目要求

输入高度数组height，其中每个非负整数代表一根柱子的高度，各柱宽度均为1，柱子按数组顺序排列。

计算下雨后这些柱子之间总共能存住多少单位的水。水会从缺少足够高挡板的一侧流走，最后返回各个位置积水量的总和。

示例1

输入：height = [0,1,0,2,1,0,1,3,2,1,2,1]

输出：6

从左到右各列积水为[0,0,1,0,1,2,1,0,0,1,0,0]，相加得到6。

示例2

输入：height = [4,2,0,3,2,5]

输出：9

各列积水为[0,2,4,1,2,0]，相加得到9。下文的柱状图会展示这一组输入。

约束条件

  • n = height.length
  • 1 ≤ n ≤ 2 × 10⁴
  • 0 ≤ height[i] ≤ 10⁵

前面做过的无重复字符的最长子串，以及长度最小的子数组、找到字符串中所有字母异位词，都是让左右边界向右移动来维护窗口。连续按这个方向做题后，遇到接雨水，我也先沿着从左往右处理的思路考虑：先记住左边最高的柱子，再向右寻找能够挡水的柱子，找到后把中间的水算出来。这条思路可以得到正确解法，但分段范围和继续搜索的位置都需要处理清楚。

要判断找墙的逻辑是否正确，可以先把问题缩小到其中一列。假设当前位置的高度为0，左边最高的柱子为4，右边最高的柱子为5。水位可以升到4；如果继续升高，水就会越过左边的墙流走，所以右边再高也无法让这一列存到5。

这里找的是一侧范围内的最高柱，不一定是紧邻的柱子。比如高度[4,2,0,3,5]中，0旁边虽然只是2和3，两侧更远处的4和5仍然能够挡住水，中间较矮的柱子只是被水覆盖了一部分。某一列能存多少水，要看两侧各自最高的墙，再由其中较低的一侧决定水位。

设L[i]是从开头到i的最高柱，R[i]是从i到末尾的最高柱，两个范围都包含当前柱子本身。水位减去已经由柱子占据的高度，就是这一列的积水量：

water[i]=min⁡(L[i],R[i])−height[i]water[i]=\min(L[i],R[i])-height[i]

因为L、R都不低于当前柱，差值不会小于0。柱宽为1，总水量就是各列水量之和。端点也适用这个定义：其中一侧最高只有它自己，所以无法存水。

1.1 第一次尝试：右侧最后一个更高的柱子，未必是最高柱

第一版在右边发现比当前柱高的柱子，就直接覆盖right_max。用[5,0,4,1]看这个问题最清楚：处理高度0时，先找到4，后面又找到1，最后保留下来的是1。

展开第一次寻找右墙的错误逻辑
python
def rain_bug_last_taller(height: list[int]) -> int:
    total = left_max = 0
    for i in range(len(height)):
        if left_max <= height[i]:
            left_max = height[i]
            continue
        j, right_max = i + 1, 0
        while j < len(height):
            if height[j] > height[i]:
                right_max = height[j]  # 错误：后面更矮但仍高于当前的柱会覆盖。
            j += 1
        if right_max > height[i]:
            total += min(left_max, right_max) - height[i]
    return total

高度1虽然高于当前柱，却低于已经找到的4，不能覆盖右侧最高值。因此这段逻辑只算出1单位水，正确结果是4。修正时需要持续取最大值：right_max=max(right_max,height[j])。

这次错误对应着两个不同的问题：“新柱子能不能挡住一点水”和“新柱子是否改变已经知道的最高挡板”。高度1对当前的0来说确实更高，但已经找到的4仍然存在，水位不会因为后面又出现一根矮柱而降低。每扫描一个新位置，都应该把它与已知最高值比较，保留两者较大者。这样right_max才始终表示已扫描范围的最高柱。

代码为便于运行整理成了独立函数，错误版保留对应的算法分支；下面的逐柱版本是按这个修正补充的对照实现。

展开修正后的逐柱扫描基准
python
def rain_column_scan(height: list[int]) -> int:
    total = left_max = 0
    for i, value in enumerate(height):
        left_max = max(left_max, value)
        right_max = value
        for j in range(i + 1, len(height)):
            right_max = max(right_max, height[j])  # 真正维护最大值。
        total += min(left_max, right_max) - value
    return total

左边最高值可以随遍历更新，右边最高值仍然每次重新扫描。扫描次数最多接近(n-1)+(n-2)+…+1，所以逐柱扫描的最坏时间为O(n²)，额外空间为O(1)。

1.2 分段结算的第一次修改：记住右墙的真实位置

逐列计算的问题比较明显：相邻两列往右寻找时，会反复经过同一批柱子。我当时想，既然已经找到了右墙，能不能把两道墙之间的水一次算完，然后直接跳到右墙后面？这样已经结算的区域就不用再逐列重复寻找。

于是开始尝试分段结算。不过，一次向右搜索同时产生了两个位置：一个是扫描最后停下来的位置，另一个是已经找到的最高右墙的位置。起初直接沿用了扫描终点，后面的修改才把右墙位置单独保存下来。

例如[5,0,4,0,3]，从第一个低点向右扫描，没有找到高度达到左墙5的柱子，于是一直扫到末尾。扫描结束位置为j=5，实际找到的最高右墙却在下标2，高度为4。

展开把扫描终点当作结算终点的版本
python
def rain_bug_range(height: list[int]) -> int:
    total = i = left_max = 0
    while i < len(height):
        if left_max <= height[i]:
            left_max = height[i]
            i += 1
            continue
        j, right_max, found = i + 1, height[i], False
        while j < len(height):
            if height[j] > right_max:
                right_max, found = height[j], True
                if right_max >= left_max:
                    break
            j += 1
        if not found:
            return total  # 另一个错误：当前不能接水不代表后面不能。
        for k in range(i, j):
            # 扫到末尾时j不是右墙的位置；这个区间可能跨过真实右墙。
            total += min(left_max, right_max) - height[k]
        if j != len(height):
            i, left_max = j + 1, right_max
        else:
            return total
    return total

如果把下标1到末尾都按水位4计算，得到4+0+4+1=9，就把右墙后面的区域也灌到了4。实际上，后面的低点只有高度3的右墙，那里只能接3单位水，总量应当是4+3=7。

因此需要另存一个wall，记录最高右墙的实际下标，只结算当前起点到这道墙之前的区域。扫描可以越过它去寻找更高的墙，结算范围却不能跟着扫描终点一起扩大。

按修正后的范围走一次：先以高度5为左侧限制，找到下标2的高度4作为右墙，只给下标1结算4单位水；接着继续处理下标3，它右边最高只有3，于是再结算3单位。两段相加为7。虽然第一次搜索为了确认右墙已经读过后面所有柱子，后半段仍然有自己的水位限制，不能把“搜索过”当成“已经结算过”。

1.3 分段结算的第二次修改：当前无水，也要继续检查后面

补上右墙位置后，还有提前返回的问题。

在[5,3,2,1,2]中，处理高度3时，右边没有更高的墙，这一列确实没有水。但后面的高度1夹在两个高度2之间，仍然能接1单位水。当前列没有积水，只能跳过当前列，不能结束整个函数。

另一种情况是[5,1,3,1,2]：先用左墙5和右墙3算出第一个低点的2单位水，右墙后的低点还可以接1单位。如果结算第一段后直接返回，结果就会从3漏成2。

展开记录右墙后仍然提前返回的版本
python
def rain_bug_early_return(height: list[int]) -> int:
    total = i = left_max = 0
    while i < len(height):
        if left_max <= height[i]:
            left_max = height[i]
            i += 1
            continue
        j, right_max, wall, flag = i + 1, height[i], i, 0
        while j < len(height):
            if height[j] >= right_max:
                right_max, wall, flag = height[j], j, 1
                if right_max >= left_max:
                    flag = 2
                    break
            j += 1
        if not flag:
            return total  # 错误：只是当前位置无水，不能停止整段搜索。
        for k in range(i, wall):
            total += min(left_max, right_max) - height[k]
        if j != len(height):
            i = wall + 1
            if flag == 2:
                left_max = right_max
        else:
            return total  # 错误：右墙后的更低盆地仍可能存水。
    return total

这部分当时已经把我卡住了。原本想通过一次算完一段减少重复工作，实际却需要同时考虑右墙在哪里、当前段是否结束、后面是否还有低处能积水。修好一段的结算范围，并没有同时解决后续遍历的问题。经过AI解释后，最后采用的分段写法保留了原来的结构：当前列没有水就继续；找到一段可以结算的区域，就算到真实右墙，再处理墙后面的部分。

展开修正后的完整分段解法
python
def rain_segment_fixed(height: list[int]) -> int:
    total = i = left_max = 0
    while i < len(height):
        if left_max <= height[i]:
            left_max = height[i]
            i += 1
            continue
        j, right_max, wall, flag = i + 1, height[i], i, 0
        while j < len(height):
            if height[j] >= right_max:
                right_max, wall, flag = height[j], j, 1
                if right_max >= left_max:
                    flag = 2  # 找到足够高的墙；左最高已经决定这段水位。
                    break
            j += 1
        if flag == 0:
            i += 1  # 当前位置没水，仍须继续检查后面。
            continue
        for k in range(i, wall):
            # 若未找到足够高的墙，wall就是所扫描后缀的最高墙。
            total += min(left_max, right_max) - height[k]
        if flag == 2:
            left_max = right_max
        i = wall + 1  # 右墙本身不计水；之后仍可能有低盆地。
    return total

扫描时有两种停止结果：如果找到不低于left_max的墙，这段的水位已经受左墙限制，可以提前停止；如果一直没有找到，就用整个剩余范围的最高墙作为右墙。

这两种情况为什么可以这样处理，也能回到逐列公式来看。找到不低于左最高的右墙时，两边较小值已经确定为左最高，再向后寻找更高墙不会改变当前段的水位。反过来，如果整段后缀都没有墙达到左最高，决定水位的就是后缀最高墙本身，而它的位置决定了这一段能够结算到哪里。结束搜索的条件、用于计算的高度、可以跳过的区间，需要分别对应清楚。

等高柱也可以围住低点，例如[2,0,2]。不过，是否需要改成>=要结合后续移动逻辑看，不能仅改一个比较符号就认为所有提前退出和范围问题都解决了。

1.3.1 正确分段法的瓶颈：还在重复扫描后缀

分段后跳过了部分位置，并不代表总扫描次数一定降到了线性。

考虑递减高度[5,4,3,2,1]。左最高一直为5，处理4时扫描右边的3、2、1；处理3时又扫描2、1；处理2时再扫描1。每次都没有水可以结算，但右侧搜索被反复执行。

推广到长度n，后缀检查次数形成等差和，因此修正分段法最坏仍为O(n²)时间、O(1)额外空间。已结算区间的求和不重复覆盖，累计至多O(n)，真正的瓶颈在寻找右墙。

递增数组可以很快跳过，所以分段法的实际工作量会随输入改变。这里没有同环境计时，不能根据复杂度直接写成“快几倍”。

1.4 用左右最大值数组复用扫描结果

避免重复搜索的一种直接办法，是把每个位置两侧最高值先算好。

以右侧最高值为例，若已经知道下标i+1到末尾的最高值，计算下标i到末尾就只多出了height[i]这一根柱子。因此，把它与已经保存的结果取较大值即可，不需要再看一遍后面的所有柱子。这也决定了右表要从右往左计算：先得到较短后缀的结果，才能复用它计算前一个位置。

L[i]=max⁡(L[i−1],height[i]),R[i]=max⁡(R[i+1],height[i])L[i]=\max(L[i-1],height[i]),\qquad R[i]=\max(R[i+1],height[i])

左表从左向右构造，右表从右向左构造，最后套用逐列水量公式。每次都复用前一个位置的结果，不再从当前位置重新扫描整个后缀。

对[4,2,0,3,2,5]，这三组状态是：

下标i012345
当前柱高420325
左侧最高L[i]444445
右侧最高R[i]555555
min(L[i],R[i])−height[i]024120

原来每处理一列，都要临时寻找的两个数，现在可以直接从表中读取。优化的关键在于相邻位置的最高值可以递推复用，所以这一版已经把寻找右墙的重复工作消除了。

展开左右最大值预处理代码
python
def rain_prefix_max(height: list[int]) -> int:
    n = len(height)
    if n == 0:
        return 0
    left_max, right_max = [0] * n, [0] * n
    left_max[0], right_max[-1] = height[0], height[-1]
    for i in range(1, n):
        left_max[i] = max(left_max[i - 1], height[i])
    for i in range(n - 2, -1, -1):
        right_max[i] = max(right_max[i + 1], height[i])
    # 最大值包含自身，因此差值非负，无需额外max(0,...)。
    return sum(min(left_max[i], right_max[i]) - height[i] for i in range(n))

两次预处理加一次求和，总时间为O(n)，两张表占O(n)额外空间。这里存的是前缀最大值和后缀最大值，不是前缀和。

接着可以继续问：算当前这一列时，另一侧最高墙的准确高度是否一定要知道？如果已经发现的墙足够高，剩下更高的墙还会改变结果吗？

1.5 相向双指针：只结算水位已经确定的一侧

让left从开头、right从末尾向中间移动，它们之间是尚未结算的区域。每轮先更新：

  • left_max：从开头到left已经见到的最高柱。
  • right_max：从right到末尾已经见到的最高柱。

当left_max<=right_max时，右边已经有一道至少为right_max的墙，它不低于左最高。即使中间还有更高的右墙，也不会改变两侧取较小值的结果。因此left这一列的水位已确定为left_max，可以准确结算并右移left。

当left_max>right_max时，对称地结算right这一列，再左移right。这里比较的是两侧累计最大值，代码与证明使用同一个判断条件。

可以用一个具体状态理解“右边足够高”是什么意思。假设left列高2，左边最高已经确定为4，而右端已经发现高度5的墙。此时中间尚未处理的区域可能有6、8，也可能都很低，但无论哪种情况，left列的真实右最高都至少为5。两侧取较小值时，结果必然是4，因此这列的水量一定为4−2=2。未知的右侧最高值可以更大，却不再影响当前这一列的答案。

如果反过来，左最高是5，右最高只有3，情况就不同了：此时还不能用3限制left列，因为中间可能有一根更高的右墙。不过right列的右侧最高已经完整知道为3，左侧又已经有5作保障，因此可以先处理right列。这说明选择哪一侧移动，并不是固定先左后右，而是选择目前已经有足够信息确定水量的一侧。

每次只结算端点这一列，并没有把未处理的中间一整段直接算完。端点移入下一列后再更新累计最高值，重复同样的判断。这样既保留了逐列计算的清晰含义，也不再需要为每一列保存完整的左右最大值表。

python
def rain_two_pointers(height: list[int]) -> int:
    left, right = 0, len(height) - 1
    left_max = right_max = total = 0
    while left <= right:
        left_max = max(left_max, height[left])
        right_max = max(right_max, height[right])
        if left_max <= right_max:
            # 右边已经有至少right_max高的墙，左位置水位确定为left_max。
            total += left_max - height[left]
            left += 1
        else:
            # 对称地，右位置水位确定为right_max。
            total += right_max - height[right]
            right -= 1
    return total

循环不变量是：区间[left,right]之外的列已准确结算，尚未结算的列只在一侧水位能确定时移出。初始没有已结算列；每轮确定一列并缩小区间；最后区间为空，所有列的水量都已计入。

1.6 时间、空间以及容易遗漏的边界

每轮left加1或right减1，区间长度减少1，至多执行n轮；更新最大值和水量都是常量操作。所以相向双指针为O(n)时间、O(1)额外空间。它与最大值预处理版同为线性时间，进一步节省的是两张表。

单柱、双柱、单调高度和全等高度都没有积水；等高两墙之间的低点可以存水。代码也允许空列表并返回0，这是额外兼容，原题保证至少有一根柱子。负高度不属于原题范围。

二、题目二：两数之和II—输入有序数组

167. 两数之和II—输入有序数组力扣原题 ↗

题目要求

输入已经按非递减顺序排列的整数数组numbers和目标值target。选择其中两个不同位置，使对应数值之和等于target。

结果为[index1,index2]，这里使用从1开始的题目下标，并满足1 ≤ index1 < index2 ≤ numbers.length。每个输入保证只有一组答案，同一位置不能使用两次。算法只允许使用O(1)额外空间。

示例1

输入：numbers = [2,7,11,15], target = 9

输出：[1,2]

第1个数2与第2个数7相加为9。

示例2

输入：numbers = [2,3,4], target = 6

输出：[1,3]

第1个数2与第3个数4相加为6。

示例3

输入：numbers = [-1,0], target = -1

输出：[1,2]

两个不同位置上的-1与0组成唯一答案。

约束条件

  • 2 ≤ numbers.length ≤ 3 × 10⁴
  • −1000 ≤ numbers[i] ≤ 1000
  • −1000 ≤ target ≤ 1000
  • numbers已按非递减顺序排列；保证恰好一组有效答案。

这个题作为相向双指针的补充例子。与前面的两数之和相比，关键新增条件是数组已经按非递减顺序排列，并且要求常量额外空间。

如果沿用普通两数之和的思路，哈希表仍然可以查询补数，但需要保存此前出现的数，不符合这里的常量额外空间要求。已经有序的条件提供了另一种判断依据：固定一个数后，搭档向右移动只会让总和不减，向左移动只会让总和不增。于是可以尝试从两个端点开始，每次排除一个不可能再参与答案的位置。

取剩余范围的最左端和最右端。如果两数和偏小，那么对当前left而言，即使用最大的right作搭档也不够，更靠左的搭档只会更小。因此可以排除当前left的所有组合，直接把left右移。

如果两数和偏大，对当前right而言，即使用最小的left作搭档也太大，更靠右的搭档只会更大。因此排除right，再左移right。

这里排除的是一个端点与当前范围内其他所有元素的组合，所以一次比较才能省去一整批候选。如果输入没有排序，仅凭当前和偏大就删除右端并不成立。例如[3,1,2]、target=3中，两端之和为5，但右端的2其实可以与中间的1组成答案。有序条件保证当前两端确实是剩余范围的最小值和最大值，排除证明才成立。

python
def two_sum_sorted(numbers: list[int], target: int) -> list[int]:
    left, right = 0, len(numbers) - 1
    while left < right:
        total = numbers[left] + numbers[right]
        if total == target:
            return [left + 1, right + 1]
        if total < target:
            # 即使用当前最大的搭档仍偏小，排除当前left的所有搭配。
            left += 1
        else:
            # 即使用当前最小的搭档仍偏大，排除当前right的所有搭配。
            right -= 1
    raise ValueError("题目保证存在解；此输入不满足该保证")

left<right保证不重复使用同一元素；返回时加1，对应题目要求的从1开始的下标。例如[2,7,11,15]、target=9依次比较17、13、9，最后返回[1,2]。相等的两个数可以来自不同位置，如[3,3]、target=6。

每一步排除一个端点，时间为O(n)，额外空间为O(1)。有序条件使这种排除成立；普通无序两数之和可以用哈希表保存旧值与下标，平均O(n)时间、O(n)空间。直接排序无序数组还会增加排序成本，并需要保留原始下标，不能把167的条件直接搬过去。

两题的联系在于能够证明一侧已经不必保留，才移动相应指针。167依赖排序带来的和的单调性；42不要求高度有序，依赖已知两侧最高值对水位的限制。它们都是从两端向中间移动的相向双指针，与前面同向移动的滑动窗口有不同的依据。
