1d:T2738,<h2 id="section-先确定谁提交谁读取以及何时建立快照">先确定谁提交、谁读取以及何时建立快照</h2>
<p>事务讨论经常省略操作顺序，只说“另一个事务改了，所以能看见”或“RR一直看旧值”。要推演结果，至少需要知道隔离级别、语句类型、快照建立时间，以及当前事务是否做过自己的写入。</p>
<p>本篇使用InnoDB，先比较普通一致性SELECT。<strong>RC（Read Committed，读已提交）</strong>通常为每次一致性读建立新的快照；<strong>RR（Repeatable Read，可重复读）</strong>在事务内复用相应一致性读快照。普通BEGIN与第一条一致性SELECT也不能无条件看作同一时刻。<a href="https://dev.mysql.com/doc/refman/8.0/en/innodb-transaction-isolation-levels.html" rel="noopener noreferrer">MySQL8.0隔离级别</a></p>
<p>实际验证在本地MySQL8.0.35独立实例完成，不访问业务表。实验只用一行余额，目的不是模拟真实金融系统，而是让可见性结果容易核对。</p>
<h2 id="section-初始化一行数据分别打开a和b">初始化一行数据，分别打开A和B</h2>
<p>在专用教学数据库创建：</p>
<div class="code-block"><div class="code-toolbar"><span>sql</span><button type="button" data-copy-code="true" aria-label="复制代码">复制代码</button></div><pre><code class="hljs language-sql"><span class="hljs-keyword">CREATE TABLE</span> balance (
    id <span class="hljs-type">INT</span> <span class="hljs-keyword">PRIMARY KEY</span>,
    amount <span class="hljs-type">INT</span>
) ENGINE<span class="hljs-operator">=</span>InnoDB;
<span class="hljs-keyword">INSERT INTO</span> balance <span class="hljs-keyword">VALUES</span> (<span class="hljs-number">1</span>,<span class="hljs-number">100</span>);
</code></pre></div>
<p>A、B必须是两个不同连接。一个SQL编辑器开两个标签，不一定代表两个数据库会话，应检查连接设置，必要时查询CONNECTION_ID。B的更新按autocommit提交，若把B留在未提交事务中，就改变了本实验条件。</p>
<p>先在A执行：</p>
<div class="code-block"><div class="code-toolbar"><span>sql</span><button type="button" data-copy-code="true" aria-label="复制代码">复制代码</button></div><pre><code class="hljs language-sql"><span class="hljs-keyword">SET</span> SESSION TRANSACTION ISOLATION LEVEL REPEATABLE READ;
<span class="hljs-keyword">START</span> TRANSACTION;
<span class="hljs-keyword">SELECT</span> amount <span class="hljs-keyword">FROM</span> balance <span class="hljs-keyword">WHERE</span> id<span class="hljs-operator">=</span><span class="hljs-number">1</span>;
</code></pre></div>
<p>第一次返回100。随后B执行并提交：</p>
<div class="code-block"><div class="code-toolbar"><span>sql</span><button type="button" data-copy-code="true" aria-label="复制代码">复制代码</button></div><pre><code class="hljs language-sql"><span class="hljs-keyword">UPDATE</span> balance <span class="hljs-keyword">SET</span> amount<span class="hljs-operator">=</span><span class="hljs-number">80</span> <span class="hljs-keyword">WHERE</span> id<span class="hljs-operator">=</span><span class="hljs-number">1</span>;
</code></pre></div>
<p>回到A再做同样的普通SELECT，实测仍为100；A回滚结束事务后再读，可以看到80。这个结果来自A此前建立的读视图，历史版本可以通过undo等机制重建，详见<a href="/blog/backend-agent-s07-transactions/">事务与多版本</a>。</p>
<h2 id="section-只改变隔离级别再重复同一时序">只改变隔离级别，再重复同一时序</h2>
<p>结束A的事务，把值恢复100；在A把隔离级别改为READ COMMITTED，再重复“读100→B提交80→A再读”：</p>




















<table><thead><tr><th>条件</th><th align="right">A第一次普通读</th><th align="right">B提交后A第二次普通读</th></tr></thead><tbody><tr><td>RR，同一事务</td><td align="right">100</td><td align="right">100</td></tr><tr><td>RC，同一事务</td><td align="right">100</td><td align="right">80</td></tr></tbody></table>
<p>本轮两个结果均实际验证。RC避免读到其他事务未提交的更新，但允许两次已提交读之间发生变化。RR为这类一致性读提供稳定快照，却不能直接推出所有DML、锁定读及跨行业务约束都有相同表现。</p>
<p>如果A先BEGIN，B随后提交80，然后A才做第一次一致性读，常见RR路径下A可以读到80。若使用显式一致性快照启动方式，条件又不同。因此必须把建立读视图的动作写进时间线。</p>
<h2 id="section-for-update读取为什么进入另一条路径">FOR UPDATE读取为什么进入另一条路径</h2>
<p><strong>锁定读</strong>用于读取并保护接下来要处理的当前记录，不能简单套用旧快照的返回规则。开启事务后，A对id=1执行：</p>
<div class="code-block"><div class="code-toolbar"><span>sql</span><button type="button" data-copy-code="true" aria-label="复制代码">复制代码</button></div><pre><code class="hljs language-sql"><span class="hljs-keyword">SELECT</span> amount <span class="hljs-keyword">FROM</span> balance <span class="hljs-keyword">WHERE</span> id<span class="hljs-operator">=</span><span class="hljs-number">1</span> <span class="hljs-keyword">FOR</span> <span class="hljs-keyword">UPDATE</span>;
</code></pre></div>
<p>A持有相应行锁期间，B执行：</p>
<div class="code-block"><div class="code-toolbar"><span>sql</span><button type="button" data-copy-code="true" aria-label="复制代码">复制代码</button></div><pre><code class="hljs language-sql"><span class="hljs-keyword">START</span> TRANSACTION;
<span class="hljs-keyword">SELECT</span> amount <span class="hljs-keyword">FROM</span> balance <span class="hljs-keyword">WHERE</span> id<span class="hljs-operator">=</span><span class="hljs-number">1</span> <span class="hljs-keyword">FOR</span> <span class="hljs-keyword">UPDATE</span> NOWAIT;
<span class="hljs-keyword">ROLLBACK</span>;
</code></pre></div>
<p>本轮B得到错误3572，表示无法立即取得锁；A回滚释放锁后，B再次执行相应锁定读成功，读到80。NOWAIT让冲突立即返回，便于区分“没有数据”与“数据存在但当前不可锁定”。<a href="https://dev.mysql.com/doc/refman/8.4/en/innodb-locking-reads.html" rel="noopener noreferrer">InnoDB锁定读</a></p>
<p>SKIP LOCKED则可以跳过无法立即取得的行，适合某些并发任务领取场景，但会得到不完整视图，不适合随意用于要求一致完整结果的统计。使用这些选项之前应明确查询用途和错误处理。</p>
<h2 id="section-四种隔离级别解决的现象怎样连接起来">四种隔离级别解决的现象怎样连接起来</h2>
<p><strong>脏读</strong>是读到其他事务尚未提交的数据；<strong>不可重复读</strong>是同一事务两次读取同一对象发生变化；<strong>幻读</strong>通常描述同一条件下记录集合变化。读未提交、读已提交、可重复读和串行化提供不同级别的限制，但具体数据库通过哪些机制实现，需要结合产品说明。</p>
<p>InnoDB的RR普通一致性读借助快照避免相应结果集合变化，某些锁定范围查询则通过记录锁、间隙锁或next-key lock控制插入。<strong>普通快照读和范围锁不是同一个机制。</strong> 唯一索引精确定位、范围扫描、缺少合适索引，会影响实际锁范围。</p>
<p>业务中的写偏差也提醒我们：每个事务读到自洽快照，不意味着多个事务联合维护的跨行约束必然成立。例如两个值班人都观察到另一个在岗，分别把自己改为离岗，单行更新各自合法却破坏“至少一人在岗”。应使用合适的锁定协议、约束或更强隔离与重试设计。</p>
<h2 id="section-怎样避免把实验结果用错">怎样避免把实验结果用错</h2>
<p>每次实验先结束旧事务并恢复初始值，保存两个连接的语句顺序。超时和死锁是不同结果，处理时通常应重新判断并重试完整业务事务，不能只补跑最后一条SQL。</p>
<p>本轮实际执行的是RC/RR普通读对照，以及同一主键行上的NOWAIT冲突和释放后重试。范围锁、死锁和写偏差在本篇解释机制，但没有伪装成已经执行的测试；小型实验也不提供生产吞吐结论。</p>
<h2 id="section-面试问答四种隔离级别与并发问题">面试问答：四种隔离级别与并发问题</h2>
<p><span id="q-FQ-doxcnyrfpWcjkUbDL4CkWvZeDvp" class="legacy-anchor" aria-hidden="true"></span><a id="user-content-q-FQ-doxcnyrfpWcjkUbDL4CkWvZeDvp"></a></p>
<blockquote>
<p>事务隔离级别：四大事务隔离级别分别解决了什么并发问题？</p>
</blockquote>
<p><strong>回答：</strong> 读未提交允许更弱的可见性；读已提交避免读取其他事务未提交的写入，但不同语句可能看到不同已提交状态；可重复读对相应读取提供更稳定的视图；串行化进一步限制并发异常，使执行效果满足其串行化语义。具体实现不能只靠一张通用表判断，需明确数据库、普通读或锁定读及业务约束。</p>
