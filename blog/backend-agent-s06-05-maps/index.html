从用户ID查计数，先确定键怎样判等

假设要统计每个用户提交的任务数，Map<用户ID, 次数>把一个键关联到一个值。哈希表先把键的哈希值映射到桶，再在桶中定位相等的键。不同键可能进入同一桶，这叫碰撞；不能只看哈希值相同就认定是同一个键。

Java键需要遵守equals与hashCode约定：相等的对象必须具有相同哈希值，反方向不成立。作为键参与判等和散列的字段，在入表后应保持稳定。若把用户名作为哈希依据，插入后又修改用户名，后续查找可能进入另一个桶而找不到原记录。HashMap契约

这也是使用不可变ID作为键的实际理由。线程是否安全是另一层问题，不能通过换一个散列函数顺带解决。

JDK21的桶定位和扩容怎样工作

以OpenJDK21实现为例，哈希值经过扰动，将高位信息混到低位，再使用(n-1)&hash计算容量为n时的桶位置。n采用2的幂，因此这个位运算能把值限制在合法下标范围。

教学容量为16，两个扰动后的哈希值是3和19，它们都落在桶3：

3 & 15=3,19 & 15=33\ \&\ 15=3,\qquad 19\ \&\ 15=3

容量扩成32后，下标分别成为3和19。旧桶中的元素根据新增的那一位分到原位置或“原位置+旧容量”。扩容重新安排桶结构，但不重新定义键的相等关系。 用户仍按原来的equals语义访问它们。

默认负载因子0.75是在空间与碰撞成本之间的取舍。容量16对应常见阈值12，继续增加新键会触发相应扩容判断；构造参数也不意味着底层数组一定在构造时已经分配。

桶中可以使用链表，较长且满足容量等条件时可转为树结构。OpenJDK21设置了树化相关阈值和最小表容量；表太小时可能先扩容。要解释具体插入瞬间，应读所用版本的判断流程，不能只背“达到某个链长一定立即树化”。OpenJDK21 HashMap实现

平均O(1)与遍历成本为什么需要条件

在散列分布合适、负载合理时，get和put具有预期的常数级成本。碰撞、扩容和键比较成本都会改变一次操作的实际时间。很长的字符串做hash或equals，其成本也不能自动记作与字符串长度无关。

遍历HashMap需要考虑容量和元素数量。一个只存10个元素、却预留很大桶数组的Map，也可能付出扫描空桶的成本。提前设容量可以减少扩容，但过度预留并非免费优化。

HashMap不提供并发修改安全保证。多个线程共同修改同一个实例，应使用外部同步或合适的并发容器；不能把迭代时可能抛出的异常当成可靠的并发保护。

ConcurrentHashMap保护了什么

ConcurrentHashMap允许并发访问，检索通常不需要阻塞整个表，更新使用适当的原子操作与局部协调。具体内部结构随JDK版本变化，不能把旧版Segment实现当作全部现代实现。

但以下逻辑仍由两个独立调用组成：

java
Integer old = counts.get("u1");
counts.put("u1", old + 1);

若A、B都读到0，再分别写回1，最终仍是1。每次get和put本身安全，不代表“读取后加1再写回”的组合自动原子化。

对单键计数，可以用merge或compute把计算交给容器完成。回调应短小，避免在其中等待外部网络或递归修改同一个Map。多个键之间的转账不属于单键原子操作，需要更高层同步或事务。ConcurrentHashMap原子更新接口

一个可以运行的计数例子

下面创建两个线程，每个对同一键增加1000次。join等待线程完成后再读取最终结果，避免把中途观察误当成最终值。

java
import java.util.concurrent.ConcurrentHashMap;

public class MapCounter {
    public static void main(String[] args) throws InterruptedException {
        var counts = new ConcurrentHashMap<String, Integer>();
        Runnable add = () -> {
            for (int i = 0; i < 1000; i++) {
                counts.merge("u1", 1, Integer::sum);
            }
        };
        Thread a = new Thread(add);
        Thread b = new Thread(add);
        a.start();
        b.start();
        a.join();
        b.join();
        int actual = counts.get("u1");
        if (actual != 2000) throw new AssertionError(actual);
        System.out.println(actual);
    }
}

例子只验证单键merge与完成后读取，不证明吞吐优势，也没有覆盖删除计数器与递增并发发生的情况。若值本身是可变List，把List放进ConcurrentHashMap仍不自动让List内部修改线程安全。高频统计可以考虑LongAdder，但读取时的一致性语义和业务精确性要另外确认。

面试问答：HashMap与ConcurrentHashMap

HashMap 原理；ConcurrentHashMap 如何实现线程安全

回答： HashMap先计算键的散列并定位桶，再通过哈希及相等关系找到键；碰撞由桶内结构处理，达到负载等条件时扩容。以OpenJDK21为例，容量为2的幂，扩容可以按新增高位把旧桶拆分，链表树化还受表容量等条件影响。平均常数复杂度依赖散列分布和操作成本，HashMap自身不提供并发修改保护。

ConcurrentHashMap通过相应内存可见性、原子操作和局部更新协调支持并发访问，但多次方法调用仍可能交错。两个线程都读到0再各写1就会丢失一次计数，使用单键merge可以把这个更新合并成原子操作。跨键约束、可变值内部状态和外部副作用仍需另外设计。

延伸追问（自拟）：computeIfAbsent中的创建函数只会在程序生命周期内执行一次吗？ 不成立。键被删除、计算返回null或抛异常等情况都可能使后续调用再次计算。它的保障围绕一次调用和当前键状态，不能替代外部系统的永久去重。
