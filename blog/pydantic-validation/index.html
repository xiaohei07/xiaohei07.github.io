浏览器提交的JSON到达后端后，仍然只是外部输入。字段可能缺失、拼错，也可能带上接口根本不允许修改的内容。Pydantic根据模型定义解析和校验输入，让业务函数拿到符合约定的数据对象。

从普通Python类到输入模型

下面是根据本站反馈模型缩小后的教学示例：

python
from typing import Literal
from pydantic import BaseModel, ConfigDict, Field

class FeedbackInput(BaseModel):
    model_config = ConfigDict(extra="forbid", str_strip_whitespace=True)
    content_id: str = Field(min_length=1, max_length=80)
    kind: Literal["correction", "question", "other"]
    message: str = Field(min_length=5, max_length=4000)

继承BaseModel后，类型标注与Field约束共同定义输入。extra="forbid"拒绝多余字段；去除首尾空白后再按相应规则处理字符串；Literal限制反馈类型。本站完整模型还限制内容ID格式，并拒绝NUL字符。

这些规则可以通过FeedbackInput.model_validate(data)用于普通Python代码，也可以由FastAPI在读取请求体时使用。模型并不局限于Web接口。模型说明介绍了验证、序列化和配置。

固定一份输入，逐项改变条件

以content_id="python-slices"、kind="question"、message="这个例子如何处理空列表"作为正常输入。分别改变一处，就能看见每条规则在做什么：

改动预期结果原因
去掉message拒绝必填字段缺失
kind改成reply拒绝不在允许值中
message改成两个字符拒绝不到最小长度
添加status=resolved拒绝客户端不允许指定审核状态
消息首尾有空格按去空白后的内容检查当前反馈模型允许整理首尾空白
消息包含U+0000本站模型拒绝进入PostgreSQL文本处理前阻止非法字符

这些情况中，字段校验可以在进入写库代码前失败。内容ID是否对应已发布文章则需要查询项目内容登记，属于业务检查，不能仅靠正则表达式确定。

“StrictInput”这个类名不等于严格模式

本站父类名叫StrictInput，实际配置是拒绝多余字段和去首尾空白，没有设置全局strict=True。是否允许类型转换，要看字段、模型配置和验证入口，不能按类名推断。

Pydantic可以进行一定的数据转换；严格模式收紧部分转换，但不同输入方式仍有具体规则。需要严格检查时，应明确配置并增加相应样例，见严格模式文档。

另一个需要保留区别的字段是密码。反馈消息可以去首尾空白，密码则不能擅自trim，否则用户输入的凭据会被改变。本站LoginInput没有继承反馈的字符串清理配置，密码使用SecretStr降低意外打印明文的风险，但它本身不负责数据库密码哈希。

自定义validator怎样补规则

本站用field_validator("*", mode="before")检查字符串中的NUL。before表示在通常的字段解析前处理原始值，所以验证器需要考虑输入可能还不是最终类型；不能直接假定所有输入都是字符串。

普通长度和枚举限制优先用现成字段规则，自定义validator用于确有需要的逻辑。若检查涉及数据库或外部服务，要仔细考虑它是否适合放在模型层，避免一个看似简单的解析动作暗中发起网络访问。validator文档说明了不同执行阶段。

输入模型、输出模型与数据库模型为何分开

读者创建反馈时只提供内容ID、类型和消息。数据库还保存ID、状态、时间和审核人。返回给读者的回执又只需要ID与pending状态。这三种对象的字段范围不同，分开定义更容易检查哪些数据可以从外部写入、哪些数据可以向外返回。

本站输出模型通过from_attributes=True读取ORM对象属性，管理列表返回分页对象。数据库模型仍负责外键和约束；Pydantic通过不代表数据库写入必然成功，网络中断、唯一约束或外键冲突都可能发生。

还有一个前后端边界：浏览器JS的字符串长度与Python字符串长度，对某些补充平面字符的计数方式不同。5–4000的提示应结合服务端实际校验理解，测试不只放普通汉字，也应包含空白、emoji、换行与NUL。模型检查是确定规则的好位置，用户提示则应准确解释失败原因。
