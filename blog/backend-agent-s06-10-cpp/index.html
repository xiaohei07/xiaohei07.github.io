资源释放为什么应该跟着对象生命周期

打开文件、获取锁、申请内存或建立连接之后，正常返回、提前返回和异常退出都需要考虑释放。如果每条分支都手写close或unlock，新增一个返回分支就可能遗漏。

RAII（Resource Acquisition Is Initialization，资源获取即初始化）把资源所有权绑定到对象生命周期：对象取得资源，析构时释放。函数的局部拥有者离开作用域时，清理沿语言的对象生命周期执行。C++ Core Guidelines资源管理

RAII管理的是“谁负责释放”，不只针对内存。文件、锁、Socket和事务守卫都可以采用类似设计；但事务提交、回滚等业务语义必须由具体对象定义，不能因为析构函数执行了就断言远端操作已撤销。

异常展开时哪些对象会析构

一个局部对象已经成功构造，随后抛出异常并向外寻找处理器，栈展开会按相应规则析构这些对象，顺序通常与完成构造的顺序相反。如果对象自身的构造失败，该对象的析构函数不会像完整对象那样运行，但已经构造完成的成员和基类会按规则清理。C++异常展开规则

这也是把成员资源交给独立拥有者的重要原因。构造函数拿到裸资源后还可能抛异常，若资源没有被一个已构造的RAII成员接管，就可能在构造失败时泄漏。

RAII依赖正常的作用域退出和适用的异常展开。进程被强行终止、某些立即终止路径或系统崩溃，不保证局部析构全部执行。因此文件落盘、外部提交和故障恢复仍需要各自机制。

unique_ptr和shared_ptr表达不同所有权

unique_ptr表示独占所有权，不能复制，但可以移动。移动把所有权交给新对象，原拥有者不再负责同一资源；通过get拿到的裸指针通常只是观察，不应再次包装成另一个独立拥有者。

shared_ptr通过共享控制块延长对象生命周期，最后一个相应共享拥有者释放后销毁对象。多个shared_ptr互相组成强引用环时，计数可能永远不归零，需要weak_ptr等方式打断不应拥有的关系。

共享所有权也不等于对象内部线程安全。不同shared_ptr实例可以按其规则维护控制块，但多个线程修改同一个业务对象仍需要同步。选择shared_ptr之前，应先问“对象是否真的需要多个独立生命周期拥有者”，不要把它当作默认万能指针。

一段异常路径的完整例子

下面用计数器表示资源是否被持有，同时用lock_guard管理互斥锁。示例不读写文件，也不分配大块内存。

cpp
#include <cassert>
#include <iostream>
#include <memory>
#include <mutex>
#include <stdexcept>

struct Resource {
    static inline int alive = 0;
    Resource() { ++alive; }
    ~Resource() { --alive; }
    Resource(const Resource&) = delete;
    Resource& operator=(const Resource&) = delete;
};

void fail_after_acquire(std::mutex& mutex) {
    std::lock_guard<std::mutex> guard(mutex);
    auto resource = std::make_unique<Resource>();
    assert(Resource::alive == 1);
    throw std::runtime_error("teaching failure");
}

int main() {
    std::mutex mutex;
    try {
        fail_after_acquire(mutex);
    } catch (const std::runtime_error&) {
        assert(Resource::alive == 0);
    }
    // 异常已经离开原作用域，锁守卫应完成解锁
    bool locked = mutex.try_lock();
    assert(locked);
    if (locked) mutex.unlock();
    std::cout << Resource::alive << '\n';
}

resource后于guard构造，异常展开先销毁unique_ptr及其Resource，再销毁锁守卫并解锁。预期最终输出0。这里alive只有一个线程访问，因此使用普通整数即可；若并发构造和析构，就需要另行同步这个教学计数器。

析构函数通常不应让异常逃出，尤其在已有异常展开过程中，再抛出另一个异常可能导致终止。需要报告清理错误时，应通过明确的业务接口或可处理的状态设计，而不是让调用方毫无机会地接住析构异常。

有了锁守卫，还要检查什么并发条件

RAII帮助保证“拿到锁后能按作用域释放”，不自动保证锁的选择和顺序正确。线程A先锁X再锁Y，线程B先锁Y再锁X，仍可能死锁。多个锁可采用统一顺序或适用的联合加锁机制。

条件变量也需要结合谓词循环。等待被唤醒，只说明应该重新检查条件，可能存在虚假唤醒或其他线程已消费条件；用“队列非空或停止”作为谓词，比“收到了通知就肯定有任务”更稳妥。

C++普通共享变量发生数据竞争时可能产生未定义行为。volatile不是通用线程同步工具，不能直接照搬Java volatile的语义。要根据互斥锁或原子操作的内存顺序建立明确关系。

与Python、Java和Go的资源生命周期怎样对照

Python的with把进入和退出资源作用域显式组织起来；Java的try-with-resources调用AutoCloseable；Go常用defer安排退出函数时的动作。它们都能减少分支遗漏，但触发时机和语言规则不同。

例如C++局部守卫通常在所在作用域结束时析构，Go的defer通常在所在函数返回时执行。在很长循环中不断defer关闭文件，可能直到函数退出才释放，不能直接按“每次循环花括号结束就释放”理解。Java和Go有GC，也仍需要及时关闭文件和连接，因为可达性回收与外部资源及时释放是不同需求。

面试问答：RAII是什么

C++ 中什么是 RAII？

回答： RAII把资源所有权绑定到对象生命周期，在构造或取得所有权时建立有效状态，在析构时释放资源。它可以管理内存、锁、文件等，使正常返回、提前返回和适用的异常展开共用清理机制，减少每条分支手写释放。

例如函数先创建lock_guard，再创建unique_ptr管理资源，随后抛异常；栈展开按反向顺序释放资源并解锁。构造失败、强行终止和外部副作用仍有各自边界。unique_ptr表达独占，shared_ptr表达共享，后者的引用计数不自动保护对象内部并发状态。

延伸追问（自拟）：RAII能保证数据库操作回滚吗？ 取决于事务对象和驱动的具体语义。守卫可以安排清理或回滚调用，但连接丢失时远端提交可能已经发生，仍需处理结果未知和幂等。
