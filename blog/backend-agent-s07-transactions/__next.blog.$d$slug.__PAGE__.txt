28:T2a88,<h2 id="section-事务同时执行时要分别解决哪些问题">事务同时执行时，要分别解决哪些问题</h2>
<p>假设两个工作者都要领取同一条待处理任务。普通查询都读到了<code>pending</code>，并不表示两者都获得了执行权。这里同时存在两个问题：<strong>每次读取可以看见哪些数据，以及相互冲突的修改怎样协调。</strong></p>
<p>事务把一组数据库操作组织为一个提交或回滚的单位。隔离级别约束并发时可以观察到的行为，MVCC与锁是实现这些行为的机制。故障恢复所用日志又是另一项职责，不能把这些概念当成同一个“事务开关”。</p>
<p>本文按MySQL8.4的InnoDB讲解。其他数据库也使用RC、RR等名称，但具体实现与保证需要分别查证。</p>
<h2 id="section-rc与rr的普通查询怎样选择快照">RC与RR的普通查询怎样选择快照</h2>
<p><strong>MVCC（多版本并发控制）</strong>让读取能够根据可见性规则访问某个版本的数据。它可以减少普通快照读取与写入之间的相互阻塞，但不意味着所有操作都不加锁。</p>
<p>在InnoDB的<strong>读已提交（READ COMMITTED，RC）</strong>下，每次一致性读建立自己的新快照；在<strong>可重复读（REPEATABLE READ，RR）</strong>下，同一事务中的一致性读通常沿用首次这类读取建立的快照。不能简单说“执行BEGIN就必然建立快照”，还要区分显式一致性快照等情形。<a href="https://dev.mysql.com/doc/refman/8.4/en/innodb-consistent-read.html" rel="noopener noreferrer">一致性非锁定读</a></p>
<p>假设账户余额初始为100，A只进行普通查询，没有自行修改数据：</p>








































<table><thead><tr><th>时刻</th><th>会话A</th><th>会话B</th><th align="right">A在RC下</th><th align="right">A在RR下</th></tr></thead><tbody><tr><td>t0</td><td>开始事务</td><td></td><td align="right">尚未查询</td><td align="right">尚未查询</td></tr><tr><td>t1</td><td>第一次查询余额</td><td></td><td align="right">100</td><td align="right">100</td></tr><tr><td>t2</td><td></td><td>更新余额为80并提交</td><td align="right"></td><td align="right"></td></tr><tr><td>t3</td><td>再次普通查询</td><td></td><td align="right">80</td><td align="right">100</td></tr></tbody></table>
<p>RC第二次查询使用较新的快照，能看见B已提交的80；RR沿用此前快照，仍看到100。这个时间线限定了“普通一致性读”和“A没有自己修改”，不能直接推广到所有SQL。</p>
<h2 id="section-旧版本怎样保留下来读取又怎样找到它">旧版本怎样保留下来，读取又怎样找到它</h2>
<p>前面的100和80需要有实际的存储依据。InnoDB的聚簇索引记录带有最后修改事务等内部信息；更新产生的undo记录保留恢复旧版本所需的信息，记录中的回滚指针把这些信息关联起来。<strong>快照是判断版本可见性的依据，并不是在第一次SELECT时把整个数据库复制一份。</strong></p>
<p>把余额的变化简化为一条版本链：当前记录为80，沿undo可以重建更新前的100。A的RR快照建立在B提交之前，那么B产生的80对这份快照不可见，读取需要继续寻找可见的旧版本，最终得到100。RC下A第二次查询建立新快照，B已经提交，因此80可以被这次查询看到。</p>
<p>实现中的<strong>Read View（读视图）</strong>描述创建视图时的事务可见性边界，包括当时仍活跃的事务等信息。判断不能只比较数据的业务时间戳，也不能仅以“事务ID比较小”推出该版本已提交；创建视图时仍未结束的事务需要单独考虑。本文先用这套可见性关系理解读取结果，不把具体源码字段名当作所有数据库通用接口。</p>
<p>undo同时承担事务回滚和多版本读取所需的信息保存，但两种用途的保留要求不同。已提交事务的旧版本也可能仍被长事务使用，不能提交后立刻全部清除。<strong>长期不结束的快照读取可能延迟旧版本清理</strong>；排查历史版本积压时，需要检查长事务，而不只看当前还有多少写入。<a href="https://dev.mysql.com/doc/refman/8.4/en/innodb-multi-versioning.html" rel="noopener noreferrer">InnoDB多版本机制与undo保留</a></p>
<h2 id="section-当前修改为什么不能照搬旧快照">当前修改为什么不能照搬旧快照</h2>
<p>如果A接着执行更新，数据库需要协调当前记录上的写入冲突，不能允许它只凭旧快照绕过别人已经完成的修改。锁定读和DML的行为，也不能直接套用前面普通SELECT的快照规则。</p>
<p>例如A的快照里某些行还不存在，但B已经插入并提交，A后续的UPDATE在相应条件下仍可能影响这些当前行。A自己的修改又会对后续读取可见。因此，混合普通快照读取与修改时，不能期待所有观察始终等同于某个完全静止的历史数据库。<a href="https://dev.mysql.com/doc/refman/8.4/en/innodb-consistent-read.html" rel="noopener noreferrer">一致性读与DML的区别</a></p>
<p>领取任务时，一个常见做法是条件更新：</p>
<div class="code-block"><div class="code-toolbar"><span>sql</span><button type="button" data-copy-code="true" aria-label="复制代码">复制代码</button></div><pre><code class="hljs language-sql"><span class="hljs-keyword">UPDATE</span> task
<span class="hljs-keyword">SET</span> status <span class="hljs-operator">=</span> <span class="hljs-string">'running'</span>, worker_id <span class="hljs-operator">=</span> :worker
<span class="hljs-keyword">WHERE</span> id <span class="hljs-operator">=</span> :task_id <span class="hljs-keyword">AND</span> status <span class="hljs-operator">=</span> <span class="hljs-string">'pending'</span>;
</code></pre></div>
<p>它把“任务仍待处理”作为修改条件。调用方依据实际受影响行数确认是否领取成功，而不是用之前的SELECT结果宣布获得所有权。长任务还要考虑工作者崩溃、租约和重复执行，见<a href="/blog/backend-agent-s01-recovery/">Agent恢复中的多实例接管</a>。</p>
<h2 id="section-幻读间隙锁与具体查询范围">幻读、间隙锁与具体查询范围</h2>
<p><strong>幻读</strong>讨论的是同一查询条件下，符合条件的记录集合因并发插入或删除而变化。需要先明确读取方式：RR中的普通一致性读使用快照；范围锁定读取则可能通过记录锁与间隙相关锁限制并发插入。</p>
<p>InnoDB在RR下的范围搜索可能使用next-key lock，它结合记录锁及其前方间隙；精确命中唯一索引记录的条件与范围搜索不同。RC通常减少相应间隙锁使用，但仍有外键检查、重复键检查等例外。<a href="https://dev.mysql.com/doc/refman/8.4/en/innodb-transaction-isolation-levels.html" rel="noopener noreferrer">InnoDB隔离级别与锁范围</a></p>
<p>所以“RR解决幻读”后面需要补上机制与语境：普通快照读取的结果稳定，和锁定范围阻止某类插入，是两条不同路径。索引、查询条件与执行计划变化，都可能影响实际锁范围和竞争程度。</p>
<p>死锁则来自多个事务循环等待彼此持有的资源。数据库检测并回滚一个事务后，业务仍需决定是否可以重试整个事务。统一访问顺序、缩短事务、减少锁范围有助于降低冲突，但不能据此承诺永不死锁。</p>
<h2 id="section-面试问答隔离级别与mvcc锁的关系">面试问答：隔离级别与MVCC、锁的关系</h2>
<p><span id="q-FQ-doxcnsmCVEvjUPprLK06S4ptyAd" class="legacy-anchor" aria-hidden="true"></span><a id="user-content-q-FQ-doxcnsmCVEvjUPprLK06S4ptyAd"></a></p>
<blockquote>
<p>MySQL 事务的隔离级别有哪些</p>
</blockquote>
<p><strong>回答：</strong> InnoDB支持读未提交、读已提交、可重复读和串行化。读未提交允许观察到未提交修改；读已提交的普通一致性读每次使用新快照；可重复读的普通一致性读通常复用同一事务首次一致性读的快照；串行化施加更强约束，具体读锁行为还与事务和autocommit设置有关。</p>
<p>区别应结合并发时序说明。例如A先读100，B更新为80并提交，A再普通查询：在本文前提下RC读80，RR仍读100。但A自己的修改、锁定读和DML不能简单套用这个结果。隔离级别决定可观察行为，MVCC和锁分别参与版本可见性与冲突协调。</p>
<p>选择级别要根据业务不变量和负载验证。即使使用RR，先查余额再在应用里计算新值、随后覆盖写回，也不能仅凭级别名称断言不会丢失业务更新。应采用合适的原子条件更新、锁定或版本校验，并检查失败分支。</p>
<p><strong>延伸追问（自拟）：隔离越强是否越好？</strong> 更强的约束通常会影响并发、等待或重试成本。应先明确哪些并发现象会破坏业务，再选择数据库机制，不能只按名称排序。</p>

<p>MySQL 隔离级别、幻读和间隙锁有什么关系？</p>
</blockquote>
<p><strong>回答：</strong> 隔离级别规定并发读写的观察与约束；幻读是符合某条件的记录集合发生变化的一类现象；间隙锁是InnoDB控制索引记录之间插入的一种机制。三者分别是语义、现象和实现手段。</p>
<p>在RR下，普通一致性读依靠快照维持相应结果的稳定；锁定范围读取可能使用next-key lock控制并发插入。精确唯一键查询与范围查询的锁范围不同，RC的间隙锁策略也与RR不同。因此分析是否会出现预期外记录，必须给出隔离级别、读取类型、索引、条件和事务时序。</p>
<p>例如要独占处理一个数值范围内的任务，不能只重复普通SELECT并认为已经阻止别人插入；需要设计锁定或状态领取协议。即使阻止插入，也仍要处理其他事务持锁导致的等待和死锁。</p>
<p><strong>延伸追问（自拟）：普通SELECT没有读到新行，是否证明新行无法插入？</strong> 不证明。它可能只是根据旧快照看不见；限制插入需要相应的并发控制机制。</p>
