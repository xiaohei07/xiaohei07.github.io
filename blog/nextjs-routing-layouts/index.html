在本站打开/blog/会看到文章列表，打开/blog/python-slices/会看到切片文章。这两个URL对应不同页面，但共用导航、主题与部分布局。App Router通过目录和约定文件名组织这种关系。

page与layout分别负责什么

text
app/
  layout.tsx
  page.tsx
  blog/
    page.tsx
    [slug]/
      page.tsx

根page.tsx对应首页，blog/page.tsx对应文章列表，blog/[slug]/page.tsx接收变化的文章标识。目录只表达路由层级；要形成公开页面，还需要对应的页面文件。

layout.tsx包住子页面，适合放多个页面共用的结构。根布局需要提供html与body。简化示例：

tsx
export default function RootLayout({ children }: {
  children: React.ReactNode;
}) {
  return <html lang="zh-CN"><body>{children}</body></html>;
}

children是当前路由对应的子内容。布局可以嵌套；客户端导航过程中，共享布局可以保留，具体状态能否保留还与组件位置、key和是否重新挂载有关。官方布局与页面说明列出了这些文件约定。

动态路径参数怎样找到文章

方括号中的slug是参数名，URL中的python-slices是参数值。当前App Router的页面参数按异步接口读取，教学示例如下：

tsx
export default async function Page({ params }: {
  params: Promise<{ slug: string }>;
}) {
  const { slug } = await params;
  const article = await getArticle(slug);
  return <ArticleDetail article={article} />;
}

这里getArticle与ArticleDetail是项目函数和组件，需要从各自模块导入；片段用于解释调用关系，并不是一个复制后无需依赖就能运行的完整文件。

动态路由表示路径可以带参数，并不自动等于请求到来时动态生成页面。本站在构建时通过generateStaticParams列出允许的slug，再逐个生成文章文件：

tsx
export async function generateStaticParams() {
  const articles = await getArticles();
  return articles.map(article => ({ slug: article.id }));
}

这段省略了本站针对专门文章入口的过滤。真实代码会将cpp-casts交给独立路由处理，因此检查路由覆盖时，要把动态目录与具体目录一起看。generateStaticParams参考说明了静态参数生成的作用。

导航、刷新与404应该分别检查

Next的Link可以进行客户端导航，框架会按适用条件预取或请求路由数据。页面没有完整刷新，并不表示没有网络请求，也不能据此断定内容由SSR生成。导航机制可作为进一步阅读。

测试一篇文章时，至少要区分“从列表点击进入”和“直接在地址栏打开并刷新”。如果前者成功、后者失败，可能是静态文件目录或服务器路径配置不匹配。本站使用trailingSlash: true，导出/blog/<id>/index.html这类结构，Nginx按文件与目录查找，找不到时返回404。

如果直接把所有未知路径都回退到首页HTML，虽然某些客户端应用可以工作，却可能让不存在的文章也返回200，造成错误的内容与索引行为。本站需要真实文章路径和真实404，所以没有把全部未知URL都当成首页。

stable ID、标题、分类与系列为何分开

文章标题可能随着修改更准确，ID应尽量保持稳定。分类说明文章主要解决哪类问题，标签补充技术主题，系列则说明阅读顺序。比如Next.js文章可以属于“前端开发”，同时属于“Next.js入门”系列，并关联“个人主页网站建设”项目。

这些关系不要求复制正文。文章只有一个规范URL，项目页和系列导航都指向它。旧URL通过经过核验的alias映射承接；修改标题不应顺手生成一套新URL，避免既有链接失效。

如果要新增一个页面，可以先列出四个值：稳定ID、规范路径、所属系列、数据来源。之后再判断是否需要新增路由文件。本站多数普通文章只要进入受控内容清单，就能由现有动态路由模板生成；为每篇文章手写一个page.tsx会增加没有必要的重复维护。
