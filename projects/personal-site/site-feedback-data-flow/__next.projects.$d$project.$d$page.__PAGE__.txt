30:T2124,<p>在文章下填写纠错后，页面会显示一个回执编号。这个编号背后有完整的处理过程：输入框保存字符串，浏览器发JSON，后端检查内容，再写入数据库。只有把这些变化按顺序看清楚，才能解释失败时应该保留什么、能否重试。</p>
<p>本站反馈只供作者查看，类型包括纠错、问题和其他建议。下面使用人工构造的消息，不展示真实读者内容；文章中的请求演示也不会提交生产数据。</p>
<span id="section-从输入框到请求体" class="legacy-anchor" aria-hidden="true"></span><h2 id="section-一从输入框到请求体">一、从输入框到请求体</h2>
<p>假设当前文章ID为<code>python-slices</code>，读者选择question，填写“这个例子如何处理空列表”。React的message状态保存输入，contentId由文章详情传给FeedbackForm。</p>
<p>点击提交后，代码先阻止表单默认跳转，清理上一次提示，检查去除首尾空白后的长度，再设置busy。请求体形成如下数据：</p>
<div class="code-block"><div class="code-toolbar"><span>json</span><button type="button" data-copy-code="true" aria-label="复制代码">复制代码</button></div><pre><code class="hljs language-json"><span class="hljs-punctuation">{</span>

  <span class="hljs-attr">"kind"</span><span class="hljs-punctuation">:</span> <span class="hljs-string">"question"</span><span class="hljs-punctuation">,</span>

</code></pre></div>
<p><code>apiRequest</code>把路径组织为<code>/api/v1/feedback</code>，设置JSON内容类型和15秒客户端等待上限。等待期间禁用相关控件，成功才清空输入，失败保留。按钮禁用改善当前页面的连续点击体验，不能阻止脚本客户端或另一个页面发请求。</p>
<span id="section-网关与api检查哪些条件" class="legacy-anchor" aria-hidden="true"></span><h2 id="section-二网关与api检查哪些条件">二、网关与API检查哪些条件</h2>
<p>Nginx按<code>/api/</code>路径转发请求，并限制请求体大小；API还有自己的请求体限制。接口检查来源，Pydantic解析模型，限流器检查对应动作与客户端地址，业务逻辑再查内容登记。</p>
<p><code>FeedbackCreate</code>限定content_id格式、kind允许值和消息长度，拒绝多余字段与NUL。<code>db.get(ContentEntry, payload.content_id)</code>继续确认内容存在且发布状态允许。两步都成功，才能创建反馈。</p>
<p>这里按职责解释检查，并不承诺任意多种错误同时出现时固定先返回某个错误。中间件、依赖和参数解析共同决定具体执行行为，需以实际版本和测试为准。</p>

<span id="section-数据在每一层变成什么" class="legacy-anchor" aria-hidden="true"></span><h2 id="section-三数据在每一层变成什么">三、数据在每一层变成什么</h2>


















































<table><thead><tr><th>位置</th><th>数据表示</th><th>关键变化</th></tr></thead><tbody><tr><td>React状态</td><td>JS字符串和选项值</td><td>用户编辑</td></tr><tr><td>HTTP请求体</td><td>JSON文本</td><td>对象序列化</td></tr><tr><td>Pydantic模型</td><td>受约束的Python字段</td><td>清理、解析与校验</td></tr><tr><td>SQLAlchemy对象</td><td>Feedback实例</td><td>加入会话，准备写入</td></tr><tr><td>psycopg调用</td><td>SQL与参数</td><td>类型适配与协议交互</td></tr><tr><td>PostgreSQL</td><td>已提交记录</td><td>约束检查、事务持久化</td></tr><tr><td>HTTP回执</td><td>ID与pending状态的JSON</td><td>只返回允许公开的结果</td></tr><tr><td>页面提示</td><td>React状态</td><td>展示回执并清空已提交输入</td></tr></tbody></table>
<p>SQLAlchemy的<code>add</code>还没有完成持久提交，<code>commit</code>成功后才返回201。回执的pending表示等待作者处理，不表示问题已经解决。数据库里的ID是反馈身份，与文章的content_id是两个不同字段。</p>
<span id="section-失败发生在不同阶段结果并不相同" class="legacy-anchor" aria-hidden="true"></span><h2 id="section-四失败发生在不同阶段结果并不相同">四、失败发生在不同阶段，结果并不相同</h2>
<p>输入不符合规则时返回422，当前请求不会进入正常写库路径。请求过密可能返回429。数据库不可用或SQLAlchemy异常由应用返回503；网关故障还可能形成其他状态或网络错误。</p>
<p>如果在提交前事务失败且回滚，没有本次成功写入。如果提交已经成功，却在返回响应时断开，数据库可能存在反馈，浏览器仍只知道“没有确认成功”。因此客户端的超时提示保留输入，并提醒稍后确认再重试，不把超时直接写成“数据库没有保存”。</p>
<p>当前公开接口没有按请求键查询已有回执的能力，用户无法靠自动查询完成无歧义确认。这是现有设计限制，前端提示只能诚实表达不确定性，不能凭空提供没有的恢复功能。</p>
<p>还要区分三个计时：前端15秒控制浏览器愿意等多久；连接池3秒控制等待空闲连接多久；驱动建立连接的3秒控制新连接阶段。它们作用于不同位置，不是三个数字相加便得到一次请求的固定耗时。数据库取得连接后还可能执行SQL或等待锁，配置没有给出整条链的容量保证。</p>
<span id="section-为什么当前还不能保证重复提交只产生一条" class="legacy-anchor" aria-hidden="true"></span><h2 id="section-五为什么当前还不能保证重复提交只产生一条">五、为什么当前还不能保证重复提交只产生一条</h2>
<p>同一页面的busy只覆盖一次等待窗口，IP限流只限制频率。第一次提交成功后响应丢失，第二次合法POST仍可能创建另一条记录。本站没有请求幂等键，因此不会把当前实现写成exactly-once。</p>
<p>拟议方案可以为一次逻辑提交生成requestId，服务端使用唯一约束保存该键、请求摘要和回执，在同一事务中完成。相同键且相同内容重放回执；相同键却不同内容拒绝。还要定义匿名客户端范围、过期时间、处理中状态和失败后的重试策略。</p>
<p>“先查询有没有，再插入”不能单独保证并发正确，两次查询可能都没找到。需要数据库唯一性和事务共同约束。若把记录放Redis、业务数据放PostgreSQL，又增加了跨存储一致性问题，这也解释了为什么不能只加一个缓存键就结束设计。</p>
