作者审核一条反馈时，至少要更新状态、记录审核时间与审核人，再写一条审计事件。如果只完成其中一部分，之后就难以判断这次处理究竟发生了什么。事务将这些相关操作组织为一个提交单位。

一、事务提交、回滚与原子性

sql
BEGIN;
-- 修改反馈状态、审核信息
-- 插入同一次审核的审计记录
COMMIT;

提交成功后，这些更改一起成为已提交数据；失败并回滚时，这次事务未提交的更改撤销。事务原子性让同一事务中的数据库修改一起提交或一起撤销。邮件发送、HTTP响应等外部动作有自己的执行过程，如果需要与数据库结果协调，还要单独设计。事务入门说明了提交、回滚与中间状态。

事务还涉及一致性、隔离性和持久性。业务约束与数据库规则共同维护一致性；隔离性控制并发事务怎样观察和影响数据；持久性说明已提交数据如何通过数据库的日志与存储机制保留；服务器或磁盘损坏后的恢复，还需要备份等措施配合。

二、两个审核请求竞争同一反馈行的处理

假设反馈F初始为pending，请求A要标记resolved，请求B要标记rejected。如果两者分别读取pending，再无条件更新，后写入者可能覆盖前者。

本站使用SELECT ... FOR UPDATE取得反馈行，再检查状态。按默认Read Committed隔离级别推演：

顺序请求A请求B
1锁住F，读取pending尝试锁F，等待
2修改状态并新增审计等待
3提交，释放锁继续取得当前行
4返回成功看到已处理状态，返回409

行锁协调对目标行的冲突操作。普通读取则仍按MVCC（多版本并发控制）的可见性规则取得相应版本，因此并非整张表的读取都需要等待。锁通常保留到事务结束，因此不要在持锁期间等待用户操作或慢速外部请求。显式锁说明列出了冲突和等待行为。

当前接口状态只允许pending转到resolved或rejected。再次审核会报冲突。表约束规定可以保存哪些状态，业务逻辑规定哪些状态转换被允许。

上表依赖Read Committed条件。如果改用Repeatable Read或Serializable，目标在事务开始后被其他事务改变时，可能转为序列化错误；应用需要对应的冲突和重试策略。所以，上表的等待与409结果需要连同当前隔离级别一起理解。

三、以状态条件更新实现并发冲突检测

一种备选是带条件更新：

sql
UPDATE feedback
SET status = 'resolved'
WHERE id = :feedback_id AND status = 'pending'
RETURNING id;

冒号参数是这里的抽象占位，实际语法取决于使用的驱动或SQLAlchemy接口。更新到0行时，再按业务判断是不存在还是已处理；更新成功时，把审计写入同一事务。这里是备选设计，本站当前采用显式行锁。

选择依据包括冲突频率、事务内需要读取多少信息、是否需要明确等待，以及实现是否容易验证。使用数据库行锁已经能协调本数据库中的审核竞争，增加Redis分布式锁反而需要处理锁过期、续期和数据库提交之间的关系，选择时需要判断是否出现了数据库之外的协调需求。

四、Read Committed快照与更高隔离级别的重试要求

PostgreSQL默认Read Committed下，不同语句可能看到不同的已提交快照。例如先COUNT再读取一页列表，两条语句执行之间可能有新的反馈提交，总数查询和列表查询就可能基于不同的已提交数据。对作者收件箱，这可能是可接受的实时变化；若要求严格一致的快照，就要重新评估事务隔离和分页契约。隔离级别文档解释了允许出现的现象与序列化失败。

更高隔离级别可能带来重试要求，锁也可能形成死锁。实际设计中，可以通过统一获取锁的顺序、缩短事务和设置有边界的重试来处理这些情况。锁等待与死锁实验应放在独立测试环境中，避免影响真实业务。

五、模型定义、Schema迁移与数据恢复

修改Python里的字段定义，不会让已经存在的数据库表自动获得相同结构。Alembic记录版本迁移并执行对应DDL，模型文件与迁移文件要一起核对。Alembic教程介绍了版本链和升级流程。

如果以后给反馈增加字段，兼容方式可以是先增加允许旧代码工作的字段，再部署新代码、回填并验证，最后收紧约束。删除旧列之后，旧代码可能无法运行；执行downgrade也不保证找回被删除的值。因此代码回滚、Schema回退和备份恢复应分别设计。

最值得继续追问的失败位置是“提交成功后连接断了”。数据库可能已有结果，客户端却不确定。这时需要通过请求标识与结果记录处理重复提交，这部分会在项目反馈链中继续讨论。
