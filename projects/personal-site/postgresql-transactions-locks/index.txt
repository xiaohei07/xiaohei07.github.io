28:T1fdf,<p>作者审核一条反馈时，至少要更新状态、记录审核时间与审核人，再写一条审计事件。如果只完成其中一部分，之后就难以判断这次处理究竟发生了什么。事务将这些相关操作组织为一个提交单位。</p>
<span id="section-一commit与rollback分别改变什么" class="legacy-anchor" aria-hidden="true"></span><span id="section-commit与rollback分别改变什么" class="legacy-anchor" aria-hidden="true"></span><h2 id="section-一事务提交回滚与原子性">一、事务提交、回滚与原子性</h2>
<div class="code-block"><div class="code-toolbar"><span>sql</span><button type="button" data-copy-code="true" aria-label="复制代码">复制代码</button></div><pre><code class="hljs language-sql"><span class="hljs-keyword">BEGIN</span>;
<span class="hljs-comment">-- 修改反馈状态、审核信息</span>
<span class="hljs-comment">-- 插入同一次审核的审计记录</span>
<span class="hljs-keyword">COMMIT</span>;
</code></pre></div>
<p>提交成功后，这些更改一起成为已提交数据；失败并回滚时，这次事务未提交的更改撤销。<strong>事务原子性让同一事务中的数据库修改一起提交或一起撤销</strong>。邮件发送、HTTP响应等外部动作有自己的执行过程，如果需要与数据库结果协调，还要单独设计。<a href="https://www.postgresql.org/docs/current/tutorial-transactions.html" rel="noopener noreferrer">事务入门</a>说明了提交、回滚与中间状态。</p>
<p>事务还涉及一致性、隔离性和持久性。业务约束与数据库规则共同维护一致性；隔离性控制并发事务怎样观察和影响数据；持久性说明已提交数据如何通过数据库的日志与存储机制保留；服务器或磁盘损坏后的恢复，还需要备份等措施配合。</p>
<span id="section-二两个审核请求同时到达会怎样" class="legacy-anchor" aria-hidden="true"></span><span id="section-两个审核请求同时到达会怎样" class="legacy-anchor" aria-hidden="true"></span><h2 id="section-二两个审核请求竞争同一反馈行的处理">二、两个审核请求竞争同一反馈行的处理</h2>
<p>假设反馈F初始为pending，请求A要标记resolved，请求B要标记rejected。如果两者分别读取pending，再无条件更新，后写入者可能覆盖前者。</p>
<p>本站使用<code>SELECT ... FOR UPDATE</code>取得反馈行，再检查状态。按默认Read Committed隔离级别推演：</p>






























<table><thead><tr><th>顺序</th><th>请求A</th><th>请求B</th></tr></thead><tbody><tr><td>1</td><td>锁住F，读取pending</td><td>尝试锁F，等待</td></tr><tr><td>2</td><td>修改状态并新增审计</td><td>等待</td></tr><tr><td>3</td><td>提交，释放锁</td><td>继续取得当前行</td></tr><tr><td>4</td><td>返回成功</td><td>看到已处理状态，返回409</td></tr></tbody></table>
<p><strong>行锁协调对目标行的冲突操作</strong>。普通读取则仍按MVCC（多版本并发控制）的可见性规则取得相应版本，因此并非整张表的读取都需要等待。锁通常保留到事务结束，因此不要在持锁期间等待用户操作或慢速外部请求。<a href="https://www.postgresql.org/docs/current/explicit-locking.html" rel="noopener noreferrer">显式锁说明</a>列出了冲突和等待行为。</p>
<p>当前接口状态只允许pending转到resolved或rejected。再次审核会报冲突。<strong>表约束规定可以保存哪些状态，业务逻辑规定哪些状态转换被允许</strong>。</p>
<p>上表依赖Read Committed条件。如果改用Repeatable Read或Serializable，目标在事务开始后被其他事务改变时，可能转为序列化错误；应用需要对应的冲突和重试策略。所以，上表的等待与409结果需要连同当前隔离级别一起理解。</p>
<span id="section-三乐观更新能怎样改写这个例子" class="legacy-anchor" aria-hidden="true"></span><span id="section-乐观更新能怎样改写这个例子" class="legacy-anchor" aria-hidden="true"></span><h2 id="section-三以状态条件更新实现并发冲突检测">三、以状态条件更新实现并发冲突检测</h2>
<p>一种备选是带条件更新：</p>
<div class="code-block"><div class="code-toolbar"><span>sql</span><button type="button" data-copy-code="true" aria-label="复制代码">复制代码</button></div><pre><code class="hljs language-sql"><span class="hljs-keyword">UPDATE</span> feedback
<span class="hljs-keyword">SET</span> status <span class="hljs-operator">=</span> <span class="hljs-string">'resolved'</span>
<span class="hljs-keyword">WHERE</span> id <span class="hljs-operator">=</span> :feedback_id <span class="hljs-keyword">AND</span> status <span class="hljs-operator">=</span> <span class="hljs-string">'pending'</span>
RETURNING id;

<p>冒号参数是这里的抽象占位，实际语法取决于使用的驱动或SQLAlchemy接口。更新到0行时，再按业务判断是不存在还是已处理；更新成功时，把审计写入同一事务。这里是备选设计，本站当前采用显式行锁。</p>
<p>选择依据包括冲突频率、事务内需要读取多少信息、是否需要明确等待，以及实现是否容易验证。使用数据库行锁已经能协调本数据库中的审核竞争，增加Redis分布式锁反而需要处理锁过期、续期和数据库提交之间的关系，选择时需要判断是否出现了数据库之外的协调需求。</p>

<p>PostgreSQL默认Read Committed下，不同语句可能看到不同的已提交快照。例如先COUNT再读取一页列表，两条语句执行之间可能有新的反馈提交，<strong>总数查询和列表查询就可能基于不同的已提交数据</strong>。对作者收件箱，这可能是可接受的实时变化；若要求严格一致的快照，就要重新评估事务隔离和分页契约。<a href="https://www.postgresql.org/docs/current/transaction-iso.html" rel="noopener noreferrer">隔离级别文档</a>解释了允许出现的现象与序列化失败。</p>
<p>更高隔离级别可能带来重试要求，锁也可能形成死锁。实际设计中，可以通过<strong>统一获取锁的顺序、缩短事务和设置有边界的重试</strong>来处理这些情况。锁等待与死锁实验应放在独立测试环境中，避免影响真实业务。</p>
