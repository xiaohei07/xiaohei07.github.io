修改一篇文章标题后，卡片、正文、搜索和系列导航都应该显示同一份标题。如果分别在这些地方手工改，很容易出现一个入口更新了、另一个入口还保留旧文字的情况。本站通过统一内容对象，将这些展示入口接到同一份正文与元数据上。

一、固定一篇文章，看它怎样进入网站

以稳定ID为python-slices的文章为例。内容清单先指定允许读取的文件与规范路径，读取器分离front matter和正文，检查schemaVersion、ID、栏目、日期、标签和状态，再把正文送入Markdown管线。

得到的Article对象包含标题、摘要、分类、标签，以及生成后的HTML、headings、searchText、字数和阅读时间。卡片只用其中一部分，详情页需要HTML与目录，搜索需要纯文本。不同页面读取不同字段，但内容身份保持相同。

查看图中细节

这张图概括的是构建数据关系，没有表示每个箭头都是一次网络请求。比如Markdown到语法树是在构建进程中处理，读者并不会把Markdown发给FastAPI转换。

二、正文、目录和代码怎样共同生成

本站管线先解析Markdown，再转换HTML树、清理不允许的结构，生成标题ID和代码高亮。随后收集标题信息并装饰代码块、图片和链接，最后输出HTML。

语法树把正文拆成有类型的节点，例如标题、段落、代码和链接。可以用下面这段教学输入理解区别：

markdown
## 边界说明

```python
# 这行只是代码注释，不是文章标题
print("## 也只是字符串")
```

解析器把第一行识别为二级标题，把代码块保存为代码节点。后面的目录收集只取标题节点，因此不会把字符串里的##也放进目录。这也是旧上下标适配只修改普通文本节点的原因：先确定对象，再变换内容，避免全局替换破坏代码。

目录中的href应该与正文真实ID对应。假设目录指向#section-步长，就要确认HTML中存在相应元素；只在Markdown中看见标题“步长”，还不足以证明最终锚点相同。标题中的标点、重复标题、清理前缀和历史alias都会影响结果。

标题增加“一、”“1.1”等编号后，显示文字会变化，但旧读者保存的片段链接仍有价值。兼容时要把旧ID明确关联到当前章节，并检查目标实际存在、别名没有冲突；只保留文章URL还不够。本站既有算法章节的显示装饰，也有旧标题别名机制，分别按明确的内容范围启用。目录怎样从平铺标题形成树、怎样跟随当前章节，继续见React状态与阅读目录。

代码复制按钮也属于呈现层装饰，不应改写原代码。旧上下标兼容只操作文本节点，避免把代码中的~或^当成排版标记。新系列普通代码同样保留语言标记，复杂解释放在代码外，方便阅读和复制。

三、搜索与列表筛选走的是哪份数据

文章列表的分类、标签、时间和字数筛选，主要在浏览器里处理已经取得的文章摘要；全站搜索另外加载构建好的search-index.json，覆盖允许进入索引的文章、研究和项目。

搜索条目只输出ID、类型、标题、摘要、标签、正文纯文本和URL。按规范URL去重，可以让同一篇内容从不同栏目被找到，同时不重复计数。源码路径和私密核对字段不应混入索引。

本站打开搜索时才加载索引，后续输入在本地匹配。英文技术词会考虑完整命中优先级，多词查询与C++这类符号需要明确处理。它没有使用PostgreSQL全文检索，也没有为每次键盘输入调用后端搜索接口。

四、一次标题修改，哪里需要重新生成

假设标题从“列表切片”改成“Python列表切片的起点、终点与步长”，ID不变。原稿更新后，重新导入对应快照，再由构建生成卡片、正文与搜索条目。线上仍要发布新产物才生效。

阶段应检查的内容
原稿标题改了，ID与旧URL关系保留
导入快照字节与清单哈希对应
Article对象title、html、headings与searchText来自当前文件
页面与索引新标题一致，站内链接仍正确
浏览器实际取得新版本，缓存按预期处理

如果正文更新了、搜索还旧，先检查构建索引与缓存；如果所有地方都旧，先检查导入快照。不同故障位置需要不同动作，不能一开始就删全部依赖重装。

五、分类、标签、系列与项目如何同时存在

本轮接入把语言知识、前端开发、后端与数据库、部署与运维、项目建设等按主旨分开，随后又增加Agent分类。技术标签可以横跨类别，系列表达学习顺序，项目关联说明这篇文章与哪个项目有关。

例如“psycopg驱动与参数绑定”属于后端与数据库，标签包含Python、PostgreSQL和psycopg；它也在数据库学习顺序中，并关联个人主页项目。本项目的系列文章使用/projects/personal-site/<id>/正文地址，知识文章同时收录到技术笔记，两处入口指向同一正文，不为每条关联再复制正文。

5.1 标签先归一，再按篇计数

展示层会把部分旧标签归入同一主题。假设A文章同时带有“SSG”和“页面渲染”，B文章只带“页面渲染”，而规则将SSG也映射为“页面渲染”。先对A的标签集合去重，A只贡献1篇，再加B得到2篇；直接累加原标签次数会误算成3。

分类内的标签数量，还应先限制到当前分类。算法稿即使用Python，也不因此自动变成Python语言基础课；本站在展示层区分算法主题与语言知识标签，保留源正文。分类、标签和系列提供不同阅读关系，不需要彼此替代。

5.2 名称排序只改变比较键

中文题名中的“第九篇”“第十篇”如果直接按字符比较，可能不符合阅读顺序。本站先做NFKC规范化，把可识别篇号转换为数字，再交给支持数字比较的中文Intl.Collator，并用稳定ID处理并列。NFKC处理的是全半角等兼容形式；它没有理解整篇文章的含义。

显示题名仍用原文，排序只使用派生的键。普通入口默认按最新时间排列；分享链接明确带有排序状态时保留它。规则只覆盖项目定义的篇号形式，不能据此说能理解所有中文数字表达。

项目总览按系列分组，文章详情显示当前系列位置、前后篇和相关内容。新类别没有文章时显示真实空态，不能为了把界面填满就虚构已经写好的内容。

六、先截断再统计，为什么年份数量会变小

首页归档曾先取全局8条预览，再按年份分组计数。这样统计的实际上是预览中的条数，较早年份的文章没有进入这8条，就不会被完整计入。

用一个缩小的人工数组可以看清这个差别：年份依次为[2026, 2026, 2024, 2023, 2023]，只取前3条再分组，会得到2026年2条、2024年1条，完全没有2023年。完整分组则还有2023年2条。随后即使只显示每年一条预览，也应保留这个完整总数。

工程据此改为先按完整筛选结果分组并保存每年总数，再限制各年预览数量。折叠与展开改变可见条目，不改变统计口径。这个问题没有涉及数据库或缓存，原因就在数组处理顺序，因此排查时先看筛选、分组、排序和截断各使用哪份数据。

七、哈希与发布清单保护什么

7.1 清单和快照先固定输入

清单列出这一批允许使用的文章与资产，快照保存它们相互配套的固定版本。SHA256摘要用来比较字节：假设清单记录稿件摘要A，文件修改后变成B，导入器发现B不等于A就停止，避免拿旧审核结果接入新文件。这里的A、B只是教学符号。

导入还检查真实路径没有越出来源根目录，ID和系列顺序不重复，图片格式与内容符合规则。全部输入检查完毕后，先写快照，再替换当前清单指针，可以减少读到半份交付的机会。这个文件流程不等于数据库事务，也没有承诺任意磁盘故障下都完整原子化。

7.2 公开批准绑定具体版本

本系列源包的publishAllowed:false表示本地预览接入合同，公开决定由独立记录中的approved、snapshot和manifestHash共同控制。集合需要在允许范围内，快照标识和清单摘要还必须与批准项匹配。29篇已经公开，不能因为源包仍有false就判断网站没有发布它们。

例如只调整分类配置，没有改文章字节，清单仍可能发生变化，因此旧manifestHash不再匹配。项目按约定的对象序列化计算摘要，并不是任意JSON排版、键顺序都能得到同一个摘要的通用标准。批准的是一份明确版本，不是此目录以后出现的任意文件。

7.3 正文之外还需要核对什么

交互演示也属于内容的一部分。只冻结文章，却另外替换演示控制器或轨迹，画面可能不再对应解释。算法内容把运行文件、章节方案和资产一起纳入校验，由已知演示标记映射到受控组件；普通Markdown不能随意指定服务器要执行的代码。

公开构建还要同步检查搜索、项目入口与图片的准入，并生成完整的反馈内容登记。否则页面虽可打开，反馈API仍可能因为content_id没有登记而拒绝提交。搜索可以包含配套阅读页，数据库登记服务于可反馈的内容实体，两者数量不必相同。哈希只能证明版本字节一致，技术正确性、素材使用范围和个人贡献仍需单独核对。

八、如果文章数量继续增长，应先优化哪里

当前静态搜索索引需要下载正文纯文本。内容变大后，可以先测索引体积、首次搜索延迟和内存，再评估分片、精简字段、Worker计算或服务端搜索。是否引入数据库全文检索，要看实际检索需求与更新频率。

同样，内容构建时间增长可以从重复解析、缓存范围和受影响页面检查入手。当前方案有清楚的数据入口，这使以后替换搜索方式时可以保留稳定ID和文章URL，减少对其他页面的影响。
