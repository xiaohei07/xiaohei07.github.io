2f:T277f,<p>个人主页同时有文章、侧栏、横幅和代码块。桌面宽屏能放下三列，手机却可能只有一列；图片需要铺满横幅，正文图片又应尽量完整显示。因此，需要分别安排<strong>容器宽度、布局切换、图片裁切和宽内容的滚动范围</strong>。</p>
<span id="section-一先确定容器能分到多少宽度" class="legacy-anchor" aria-hidden="true"></span><span id="section-先确定容器能分到多少宽度" class="legacy-anchor" aria-hidden="true"></span><h2 id="section-一grid列宽最小尺寸与响应式断点">一、Grid列宽、最小尺寸与响应式断点</h2>
<p>可以用Grid描述文章与目录的两列关系：</p>

<p>这个简化布局把剩余空间分给正文，给目录保留15rem。<strong><code>1fr</code>分配剩余空间，<code>minmax(0, 1fr)</code>允许正文列收缩到内容默认最小宽度以下</strong>；代码块则在自身容器内横向滚动，避免长代码把整个页面撑宽。Flex/Grid子项的自动最小尺寸可能保留内容宽度，因此遇到溢出时，<code>min-width: 0</code>是值得检查的条件，具体行为见<a href="https://developer.mozilla.org/en-US/docs/Web/CSS/Reference/Properties/min-width" rel="noopener noreferrer">MDN min-width</a>。</p>
<p>断点根据内容放不下的位置确定，比直接背“手机等于某个像素”更可靠。浏览器缩放、长标题、侧栏文字增大都会改变空间需求。</p>
<p>本站当前阅读目录的宽屏区域约280–320px，在不大于1350px时切到窄屏目录，文首入口滚出后再提供悬浮按钮。这与上面60rem的教学例子是两个范围：代码片段解释布局原则，具体数字以项目当前样式为准。检验断点时，应看两侧是否有重复入口、弹层是否清理、长标题是否仍可读，并在断点附近的多个宽度下观察切换过程。</p>
<span id="section-二图片文件尺寸与显示尺寸怎样对应" class="legacy-anchor" aria-hidden="true"></span><span id="section-图片文件尺寸与显示尺寸怎样对应" class="legacy-anchor" aria-hidden="true"></span><h2 id="section-二图片像素css显示尺寸与响应式资源">二、图片像素、CSS显示尺寸与响应式资源</h2>
<p>一张2560像素宽的图片，可以在CSS中只显示640px宽。前者决定图片包含多少像素，后者是布局尺寸；高像素密度屏幕还会影响需要的清晰度。</p>

<p>练习时需要为示例中的路径准备对应宽度的图片。<strong><code>srcset</code>列出候选资源及其实际宽度，<code>sizes</code>说明图片预计占用的CSS布局宽度</strong>，浏览器再结合DPR等条件选择资源。DPR是设备像素与CSS像素的比例，用于理解同样的显示尺寸在高像素密度屏幕上为何可能需要更大的图片。390px视口、DPR2并不保证选择640宽图片；本项目历史测量中实际选中了1280候选。<a href="https://developer.mozilla.org/en-US/docs/Web/HTML/Guides/Responsive_images" rel="noopener noreferrer">响应式图片说明</a>解释了候选选择与不同裁切需求。</p>
<p><strong><code>width</code>和<code>height</code>还能提供图片比例，让浏览器在资源到达前预留空间</strong>。缺少尺寸时，图片加载后可能把正文向下推，增加布局位移。<code>alt</code>应说明有信息意义的图；纯装饰图可以使用空alt，并避免把装饰描述反复读给辅助技术用户。<a href="https://developer.mozilla.org/en-US/docs/Learn_web_development/Core/Structuring_content/HTML_images" rel="noopener noreferrer">HTML图片参考</a>包含这些基础属性。</p>
<span id="section-三cover为什么会裁掉一部分图片" class="legacy-anchor" aria-hidden="true"></span><span id="section-cover为什么会裁掉一部分图片" class="legacy-anchor" aria-hidden="true"></span><h2 id="section-三covercontain与不同构图的裁切方式">三、cover、contain与不同构图的裁切方式</h2>
<p><strong><code>object-fit: cover</code>保持比例并填满容器，超出的部分会被裁切；<code>contain</code>保留完整图片，容器中可能留出空白</strong>。横幅通常优先铺满，技术图和结果截图更需要完整显示。</p>
<p>裁切位置由<code>object-position</code>影响。人物脸部如果靠近边缘，桌面与手机应分别选取合适位置。本项目曾调整首页横幅的宽度限制和宽窄屏裁切，修的是容器与图片呈现关系，不能仅通过重新压缩文件解决。</p>
<p>不同构图需要不同裁切时，可以用<code>picture</code>按媒体条件提供来源。相同构图只需要不同分辨率时，则可以优先使用<code>srcset</code>。正文中的架构图不能为了铺满卡片把节点裁掉。</p>
<span id="section-四宽公式和表格应该在哪一层滚动" class="legacy-anchor" aria-hidden="true"></span><h2 id="section-四长代码宽公式与表格的局部滚动">四、长代码、宽公式与表格的局部滚动</h2>
<p>长代码、表格或公式可能天然宽于正文。把整个页面加大，会连导航、正文和按钮一起横移；更合适的做法通常是让必要的内容容器局部滚动，正文列仍能收缩。本站10月25日处理的就是长MathML公式在窄屏溢出的问题。代码块和公式使用不同的元素结构，因此要<strong>分别检查它们的宽度约束与滚动容器</strong>。</p>
<p>检查时先比较文档的scrollWidth与可见宽度，再定位哪个元素越界；允许公式内部scrollWidth较大，与整页横向溢出是两种现象。布局修复还要保留公式可读性，不应靠缩小到无法辨认或裁掉末尾解决。</p>
<span id="section-五动画为什么需要看布局绘制与合成" class="legacy-anchor" aria-hidden="true"></span><span id="section-动画为什么需要看布局绘制与合成" class="legacy-anchor" aria-hidden="true"></span><h2 id="section-五动画的布局绘制与合成开销">五、动画的布局、绘制与合成开销</h2>
<p>浏览器更新样式后，可能重新计算布局、绘制内容，再完成合成。修改宽高和位置可能影响布局；<code>transform</code>与<code>opacity</code>在适合的条件下更容易由合成阶段处理，是否独立成层仍由浏览器决定，实际开销还需要结合页面结构和性能记录判断。</p>
<p>大量透明层、模糊、阴影和大图也可能增加绘制或内存成本。优化时应查看实际轨迹，先确认慢在下载、解码、布局还是脚本，再决定减少哪部分工作。</p>
