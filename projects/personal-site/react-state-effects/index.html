在组件中定义一个普通变量，点击后修改它，React并不会因此自动重新渲染界面。需要让React记录、并参与后续渲染的数据，可以用state保存。输入框的内容、当前标签、请求是否进行中，都属于这样的数据。

一、useState保存的是哪一轮状态

tsx
"use client";
import { useState } from "react";

export function Counter() {
  const [count, setCount] = useState(0);
  return <button onClick={() => setCount(count + 1)}>{count}</button>;
}

count是本轮渲染读取到的值，setCount安排新的状态。调用它之后，当前函数里的count不会立刻变成新值；React后续渲染时才会把更新后的状态交给组件。状态快照说明了事件处理函数为何会保留某一轮的值。

例如同一个点击处理里连续执行三次setCount(count + 1)，三次计算用的可能都是同一份count。如果目标是基于前一次待处理值累加三次，可以写三次setCount(value => value + 1)。更新函数接收队列中的前一个值，不能简单把两种写法看成完全等价。状态更新队列有对应过程。

二、输入框怎样保持值与界面一致

tsx
const [message, setMessage] = useState("");

<textarea
  value={message}
  onChange={event => setMessage(event.target.value)}
/>

输入触发onChange，把新的字符串存入state；下一轮渲染再把这个字符串传给value。这种输入由组件状态管理，通常称为受控输入。

本站反馈表单在等待期间禁用输入与按钮，成功后清空字符串，失败则保留。因此处理成功与失败时需要分别更新对应状态，不能在提交函数末尾无条件清空。

数组和对象也应产生新值，例如setTags(tags => [...tags, "React"])，而不是直接对原数组push后继续复用原引用。这样更容易保持每轮状态清楚，也能避免修改其他地方仍在使用的对象。

三、Effect何时需要，何时不需要

useEffect用于将组件状态与React外部系统同步，例如事件监听、计时器、浏览器存储和观察器。若只是根据已有props筛选列表，通常可以直接在渲染时计算，不必额外存一份state再用Effect同步。

tsx
useEffect(() => {
  const onVisibility = () => setVisible(!document.hidden);
  document.addEventListener("visibilitychange", onVisibility);
  onVisibility();
  return () => document.removeEventListener("visibilitychange", onVisibility);
}, []);

这个教学示例订阅浏览器事件，并在清理函数里取消订阅。依赖数组为空，表示没有随组件渲染变化、需要重新同步的响应式依赖；并不适合概括成“任何环境都保证只执行一次”。开发阶段的Strict Mode会额外进行建立与清理检查，组件重新挂载也会重新执行。Effect说明解释了同步、依赖与清理的关系。

如果Effect使用了变化中的值，就应正确声明依赖。为了消掉重复执行而随意删依赖，可能让计时器一直读取旧值。遇到这类问题，先确认Effect究竟要同步什么，再考虑重组代码。

四、横幅切换为什么要保留上一张图

本站横幅维护current、previous和ready。切换时先保存上一张图，再请求下一张；新图成功加载后才进入过渡，过渡结束再释放旧图。

事件当前目标旧图下一步
已显示AA无等待切换
请求BBAA继续可见，等待B加载
B加载成功BA过渡后移除A
B加载失败恢复A失败处理清理过渡状态继续显示成功加载过的A

工程曾记录onError与onLoad共用成功处理，导致失败也被当作“可以结束旧图保留”。修正后将失败回调分开。这个问题要看的是状态转移条件：触发了图片事件，并不一定意味着图片成功显示。

轮播还需要考虑页面是否可见、横幅是否在视口内、用户是否选择减少动态效果。本站通过这些条件决定是否继续计时，并在依赖变化时清理计时器，避免离开页面后仍积累后台任务。

五、阅读目录怎样从标题列表变成可操作的树

目录同时涉及内容结构和交互状态。输入是正文解析得到的标题列表，每项包含id、text、level；输出是可展开的目录分支，以及当前阅读位置的标记。标题文字和层级来自文章，当前节、手动折叠来自用户阅读过程，不能把它们全部混成一份随意修改的数组。

5.1 用栈建立标题的父子关系

栈可以先理解为只从末尾放入、取出数据的列表。这里保存当前标题的祖先链。读到新标题时，末尾如果不比它层级更浅，就移走，直到找到可作为父级的标题。

用教学输入h2:A、h3:B、h4:C、h3:D、h2:E逐步推演：

当前标题处理后找到的父级加入后的祖先栈
A，二级无，作为根节点A
B，三级AA、B
C，四级BA、B、C
D，三级弹出C与B，剩下AA、D
E，二级弹出D与A，作为新根E

最终A下面有B和D，B下面有C；E与A并列。本站headingTree使用的就是这个关系：弹出所有level >= 新标题level的末尾节点，再挂到最近较浅标题下。跳级的h2→h4仍能挂到h2下面，不会凭空造一个h3。

每个标题入栈一次，出栈至多一次，因此建树时间是O(n)，n为标题数。这里分析的是建树步骤，不是整套目录交互都恒定耗时；寻找路径、读取DOM位置和渲染还有各自工作。

5.2 当前节与手动折叠各自保存什么

activeId记录当前阅读标题，headingPath取得从根到该标题的路径。默认只展示根级目录，进入某节后展开它的祖先链，让读者能看到当前位置。

假设读者停在C，手动折叠A。若每次滚动都强制展开A，刚才的操作会立刻失效。本站把手动展开集合与当时的activeId一起保存：仍在C时使用手动选择；进入D后旧选择失效，重新按D的祖先路径展开。这样既能跟随阅读，又能让同一节里的手动折叠保持有效。

当前节由IntersectionObserver、滚动监听和hashchange共同更新。观察器感知可见关系，滚动与锚点事件补充快速跳转等情况；requestAnimationFrame把同一轮滚动工作合并到适当的绘制时机。当前项超出目录视口时，只调整目录容器的scrollTop，避免为了显示一条目录而拖动正文。

5.3 窄屏为什么使用Portal和dialog

当视口不大于1350px，本站使用窄屏目录布局。文首目录滚出后才出现悬浮按钮；这包括较窄的桌面窗口，不是根据设备名称判断“手机”。打开按钮后，读者需要在弹层里看到当前章节，选中目标后回到正文。

Portal改变DOM放置位置，同时保留React树中的关系。 本站把悬浮控件和dialog放到document.body，避开祖先动画容器对fixed定位的影响。上下文和React事件传播仍遵循原组件树，这一点与单纯把DOM搬到另一个父元素的直觉不同。React的Portal说明解释了两种关系。

原生dialog.showModal()提供模态交互基础；代码在打开后把焦点移到当前目录项。点击目录时先关闭弹层，再按链接锚点跳转；Esc或关闭按钮只是收起，不应额外跳动正文。弹层打开期间锁住背景滚动，位置更新也暂停，避免弹层布局变化误判当前章节。原生行为可对照dialog参考。

离开适用断点或组件卸载时，需要移除监听、断开观察器并取消待执行的rAF。Portal和dialog减少了部分定位与模态处理工作，但焦点恢复、关闭清理、减少动态效果及真实设备仍要检查；已有Chrome视口结果不能代替实机Safari和完整无障碍验收。

六、栏目配色怎样区分作用范围、复制和恢复

6.1 先确定保存哪一份状态

亮色、暗色、跟随系统决定明暗主题；栏目色与全站统一色决定配色作用范围，两者是不同维度。state驱动当前画面，localStorage用于刷新后恢复，DOM呈现最终结果，修改其中一个并不保证另两个自动同步。

本站section模式分别保存各栏目颜色，custom模式统一全站。状态还要区分自定义种子色与原始整套色板：一个hex可以生成配色变量，却不一定还原原栏目里文字、背景、边框等变量的原始组合。

保存项用途示例含义
sectionColors栏目自定义hex项目栏目使用自己选定的种子色
sectionThemes栏目取用的原色板项目栏目采用研究栏目的原始色板
customColor / customTheme统一模式下的种子色或原色板全站使用同一个选择

6.2 从复制研究配色到恢复项目原色

假设各栏目先用原色，读者在项目页点击“研究”色卡。目标仍是projects，来源是research；如果来源没有自定义hex，就保存采用研究原色板的选择。导航仍属于项目，颜色来源变化不会把URL或内容分类也改成研究。

若之后研究栏目改成自定义hex，项目保留的是复制当时解析出的选择，不会自动订阅研究的新设置。复制更接近保存一次结果，不能把它理解成两个栏目的颜色永远同步。

接着在项目页点击自身“项目”。旧实现再次读取项目已经保存的研究配色，所以看起来没有恢复。当前copySectionPalette先判断source === target，在这一分支读取项目的原始色板，清除项目覆盖。修正落在动作含义和状态转换上，单改CSS颜色不能解决“再次复制错误来源”的问题。

统一模式下点击自身，会把当前栏目的原色板应用全站；之前各栏目的设置仍保留，以便切回栏目模式。颜色恢复也只重置颜色相关状态，不应顺带清除布局、动态效果等其他偏好。

6.3 刷新首屏为什么也需要相同解析规则

localStorage可能留有旧格式或损坏数据。当前解析只接受白名单栏目、合法枚举、六位hex和有界数值，不把读出来的对象原样应用。首屏入口脚本和运行期使用同一个resolveColorPreferences，让刷新与客户端切页对“当前应使用哪套色板”得到相同判断。

此前还出现过输入框失焦就把未修改的值提交为统一颜色的问题，后来改为显式应用或回车。检验这种交互，应该实际走“聚焦→不修改→Tab离开”的路径；只直接修改变量无法覆盖这个事件顺序。状态恢复能按规则执行，也不等于所有自定义颜色组合都有合格对比度，文字链接仍需要清楚的视觉提示。

七、useRef与state怎样选择

useRef可以保存DOM引用或跨渲染保留的可变值，修改ref.current本身不会触发渲染。需要立刻反映到界面的数据用state；计时器ID、观察器目标等不直接显示的引用，可以考虑ref。选择依据是数据变化后是否需要让界面重新计算，不能把ref当成绕过状态更新规则的捷径。

还可以继续追问：如果连续从A切B再切C，B的加载事件很晚才到，是否会误处理C的状态？应结合组件key、请求身份和回调归属检查。本文状态表先解释单次切换；更复杂的竞态需要单独构造输入验证，不能因为A→B通过就推断所有切图顺序都正确。
