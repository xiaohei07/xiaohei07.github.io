已经能看懂基本SQL后，再看SQLAlchemy就有了对应关系：它帮助Python组织数据库操作，其中ORM（对象关系映射）把类与数据库表联系起来。数据库仍然执行SQL，SQLAlchemy没有替代PostgreSQL。

一、模型、Engine与Session分别是什么

模型声明类与列的映射，例如Feedback.message对应反馈表的消息列。Engine管理数据库方言、驱动调用和连接池；Session负责一段工作中的ORM对象与事务。它们处在不同层次，不应把Session直接理解成数据库本身。

这里的数据库Session与作者登录会话是两个对象。前者通常只围绕一次业务操作建立和关闭，后者靠Cookie令牌关联多次请求，直到退出或过期。它们都可能译作“会话”，阅读代码时要看由谁创建、保存什么、何时结束。

本站的Database对象懒创建Engine，并用锁避免同进程首次访问时重复创建。create_engine建立Engine对象，不会立刻把3个数据库连接全部打开；连接通常在真正需要时借出或建立。ORM入门与连接池说明可以对应阅读。

二、添加对象到返回回执的过程

本站提交反馈的核心关系可以缩小为：

python
with database.session() as db:
    feedback = Feedback(
        content_id=payload.content_id,
        kind=payload.kind,
        message=payload.message,
    )
    db.add(feedback)
    db.commit()
    return FeedbackCreated(id=feedback.id, status="pending")

这里省略了内容登记检查，只用于解释会话和事务。add将对象交给Session管理；flush把待执行变更发送给数据库；commit会在需要时先flush，再提交事务。因此add之后还不能向用户承诺已经持久保存。

普通with Session(...)主要负责结束时关闭Session，不会自动将所有变更提交。with Session.begin()等事务上下文则有不同语义，需要看具体写法。本站明确调用commit()。Session基础说明了flush、提交、回滚与关闭之间的关系。

若flush失败并准备继续使用同一个Session，需要先正确rollback；本站请求直接结束时，也应确保上下文释放资源。不能捕获异常后继续用一个处于失败事务状态的会话查询，再把后续报错当成新根因。

三、expire_on_commit=False为什么出现在本站

默认情况下，提交后ORM对象属性可能被标记过期，之后访问需要重新加载。本站Session设置expire_on_commit=False，方便提交后读取本次对象的ID等属性组成响应。

这不会让对象永远与数据库同步。另一个事务修改数据后，内存对象可能仍是旧值；需要新查询或刷新才能按目标一致性要求取得更新。Session的身份映射避免同一工作范围里无序制造同身份对象，也不能当成跨请求缓存使用。

Session应按请求或明确工作单元管理，不给多个并发线程共享一个可变会话。Engine可以长期复用，Session的生命周期通常短得多。

四、三个连接池参数怎样影响等待

本站配置如下：

python
pool_size=3
max_overflow=0
pool_timeout=3
pool_pre_ping=True
connect_args={"connect_timeout": 3}

pool_size与max_overflow共同限制同时使用的连接数量；pool_timeout限制等池中空位的时间；connect_timeout限制建立连接的等待，二者不是同一个计时。pool_pre_ping在连接借出前检查存活，帮助发现数据库重启后遗留的失效连接。

pre-ping不能挽救事务执行到一半突然断开的连接，也不会自动安全重放业务写入。池超时、连接建立失败、SQL慢和锁等待虽然都可能表现为“数据库请求慢”，需要分别观察。

如果事务里顺手做一个慢网络调用，连接会被占用更久。增加连接数可能暂时降低排队，也可能让数据库同时处理更多工作而更慢，应该先检查事务持有时间和数据库压力。

五、ORM怎样形成查询，哪里还需要懂SQL

python
statement = (
    select(Feedback)
    .where(Feedback.status == "pending")
    .order_by(Feedback.created_at.desc(), Feedback.id.desc())
    .limit(20)
)
items = db.scalars(statement).all()

这是本站列表查询结构的缩小版。ORM表达式最终被编译成数据库能够执行的语句；scalars取结果中的映射对象，分页与索引是否有效仍要回到SQL和执行计划。

以后如果模型增加关联并逐条懒加载，就可能出现一次列表后又发很多查询的N+1问题。当前本站没有因此宣称已经出现或解决N+1；这里说明的是引入关系加载后应该检查的点。需要理解参数怎样送入数据库，可以继续看psycopg驱动与参数绑定。
