本地网页能打开后，还要让其他人的浏览器找到它。云服务器提供持续运行的计算环境，域名与DNS帮助找到入口，Nginx处理外部HTTP请求，容器组织API和数据库运行。先看清它们的位置，再写配置会更容易。

一、云服务器、Linux进程与Docker容器的层次

ECS是本项目使用的云服务器产品，提供虚拟机资源。Linux运行在虚拟机中，Nginx与Docker等程序运行在Linux上。API容器中运行Uvicorn与Python应用，数据库容器运行PostgreSQL。

镜像提供启动所需的文件和配置，容器则是基于镜像运行的实例。容器通常共享宿主机内核，在隔离的运行环境中执行自己的进程；虚拟机则在虚拟硬件上运行操作系统。数据若只留在容器可写层，重建时容易失去，因此数据库目录需要挂载持久存储。Docker容器说明介绍了这一层关系。

二、容器端口、宿主机回环端口与HTTPS入口

本站API在容器内部监听8000，映射到宿主机回环地址127.0.0.1:18000；Nginx接收外部HTTPS请求，再把/api/转到这个本机端口。PostgreSQL在Compose网络中被API访问，没有向宿主机公开数据库端口。

回环地址指向当前网络环境自身：容器里的127.0.0.1指该容器，宿主机的127.0.0.1指宿主机。Compose服务之间可按服务名发现彼此，具体网络规则见Compose网络说明。

把服务绑定到回环地址与配置云安全组分别在不同层控制访问。应用还需要认证和授权；某个端口不直接公开，不表示内部任何请求都可以不检查。

三、Nginx静态文件查找与API反向代理

本站配置可以按用途缩小为：

nginx
root /opt/personal-site/current/web;
index index.html;

location / {
    try_files $uri $uri/ =404;
}
location /api/ {
    proxy_pass http://127.0.0.1:18000;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_set_header X-Forwarded-For $remote_addr;
}

这个片段集中展示静态文件与API两条路径，完整部署还需要TLS所在的server块、缓存和其他位置规则。root与URI共同确定文件路径，try_files依次尝试文件和目录，找不到就404；proxy_pass把对应请求交给上游。Nginx入门解释了静态与代理两种用途。

proxy_pass是否带URI会影响路径替换。这里地址后面没有附加/路径，所以需要保留的/api/v1/...继续传给API。更改时应拿一个确定URL推演，并实测上游收到的路径，详见proxy模块参考。

转发头需要由可信代理设置，并由API按代理来源判断是否采信。当前Nginx用实际remote_addr覆盖X-Forwarded-For，API仅信任配置的代理来源，避免任意外部头直接成为限流依据。以后添加CDN或其他代理，需要重新定义可信链。

四、缓存响应头与资源版本的配合

HTML更新频繁，本站要求重新验证；带内容哈希的JS/CSS资源可以长期缓存；API和管理页使用no-store。no-cache允许保存响应，但复用前需要按规则重新验证；no-store要求不存储响应。304通常让客户端继续使用已保存的响应体。HTTP缓存参考解释了这些差别。

若一直覆盖同名图片，缓存未过期的用户可能看到旧图。改变资源URL更容易表达新版本。反过来，用户已经打开的旧页面可能稍后还请求旧hash文件，所以发布新文件时也要考虑旧资源保留窗口。

五、Compose重启策略、健康检查与持久数据

本站API和数据库配置restart策略，数据库有持久目录，API有ready检查；API与数据库还有内存限制和日志轮转。资源限制约束可使用的上限，实际占用和可承受的并发量需要通过运行记录与适当负载检查。

容器进程异常退出后可以按策略拉起，主机或磁盘故障仍需要其他恢复安排。healthy表示所配置的健康检查通过；反馈提交、审核事务和数据恢复等业务路径，还需要分别观察。

本项目有数据库dump/restore历史核验，10月25日对应发布还做了临时库恢复与六表指纹比对，尚未据此建立自动离机备份。发布与恢复的具体工程过程见本站部署与回滚。读者自己搭建时，应使用独立域名和测试数据先完成检查，不把文章里的目录或端口原样覆盖已有服务。
