<span id="section-ecs操作系统进程和容器分别在哪一层" class="legacy-anchor" aria-hidden="true"></span><h2 id="section-一ecs操作系统进程和容器分别在哪一层">一、ECS、操作系统、进程和容器分别在哪一层</h2>
<p>ECS是本项目使用的云服务器产品，提供虚拟机资源。Linux运行在虚拟机中，Nginx与Docker等程序运行在Linux上。API容器中运行Uvicorn与Python应用，数据库容器运行PostgreSQL。</p>
<p>镜像描述启动容器所需的文件和配置，容器是运行实例。容器通常共享宿主机内核，不等同于再启动一台完整虚拟机。数据若只留在容器可写层，重建时容易失去，因此数据库目录需要挂载持久存储。<a href="https://docs.docker.com/get-started/docker-concepts/the-basics/what-is-a-container/" rel="noopener noreferrer">Docker容器说明</a>介绍了这一层关系。</p>
<span id="section-为什么会同时出现800018000和443" class="legacy-anchor" aria-hidden="true"></span><h2 id="section-二为什么会同时出现800018000和443">二、为什么会同时出现8000、18000和443</h2>
<p>本站API在容器内部监听8000，映射到宿主机回环地址<code>127.0.0.1:18000</code>；Nginx接收外部HTTPS请求，再把<code>/api/</code>转到这个本机端口。PostgreSQL在Compose网络中被API访问，没有向宿主机公开数据库端口。</p>
<p>容器里的<code>127.0.0.1</code>指该容器自身，宿主机的<code>127.0.0.1</code>指宿主机，两者不能混淆。Compose服务之间可按服务名发现彼此，具体网络规则见<a href="https://docs.docker.com/compose/how-tos/networking/" rel="noopener noreferrer">Compose网络说明</a>。</p>
<p>把服务绑定到回环地址与配置云安全组分别在不同层控制访问。应用还需要认证和授权；某个端口不直接公开，不表示内部任何请求都可以不检查。</p>
<span id="section-nginx怎样分发静态文件与api" class="legacy-anchor" aria-hidden="true"></span><h2 id="section-三nginx怎样分发静态文件与api">三、Nginx怎样分发静态文件与API</h2>
<p>本站配置可以按用途缩小为：</p>
<div class="code-block"><div class="code-toolbar"><span>nginx</span><button type="button" data-copy-code="true" aria-label="复制代码">复制代码</button></div><pre><code class="hljs language-nginx">root /opt/personal-site/current/web;
index index.html;

location / {
    try_files $uri $uri/ =404;
}
location /api/ {
    proxy_pass http://127.0.0.1:18000;
    proxy_set_header Host $host;
    proxy_set_header X-Forwarded-Proto $scheme;
    proxy_set_header X-Forwarded-For $remote_addr;
}
</code></pre></div>
<p>这是从实际配置中缩小的片段，省略了TLS所在的server块、缓存和其他位置规则，不能当完整上线配置。<code>root</code>与URI共同确定文件路径，<code>try_files</code>依次尝试文件和目录，找不到就404；<code>proxy_pass</code>把对应请求交给上游。<a href="https://nginx.org/en/docs/beginners_guide.html" rel="noopener noreferrer">Nginx入门</a>解释了静态与代理两种用途。</p>
<p><code>proxy_pass</code>是否带URI会影响路径替换。这里地址后面没有附加<code>/</code>路径，所以需要保留的<code>/api/v1/...</code>继续传给API。更改时应拿一个确定URL推演，并实测上游收到的路径，详见<a href="https://nginx.org/en/docs/http/ngx_http_proxy_module.html" rel="noopener noreferrer">proxy模块参考</a>。</p>
<p>转发头也需要信任边界。当前Nginx用实际<code>remote_addr</code>覆盖X-Forwarded-For，API仅信任配置的代理来源，避免任意外部头直接成为限流依据。以后添加CDN或其他代理，需要重新定义可信链。</p>
<span id="section-缓存怎样与资源版本配合" class="legacy-anchor" aria-hidden="true"></span><h2 id="section-四缓存怎样与资源版本配合">四、缓存怎样与资源版本配合</h2>
<p>HTML更新频繁，本站要求重新验证；带内容哈希的JS/CSS资源可以长期缓存；API和管理页使用no-store。<code>no-cache</code>允许保存响应，但使用前要按规则验证；<code>no-store</code>要求不存储响应。304通常让客户端继续使用已保存的响应体。<a href="https://developer.mozilla.org/en-US/docs/Web/HTTP/Guides/Caching" rel="noopener noreferrer">HTTP缓存参考</a>解释了这些差别。</p>
<p>若一直覆盖同名图片，缓存未过期的用户可能看到旧图。改变资源URL更容易表达新版本。反过来，用户已经打开的旧页面可能稍后还请求旧hash文件，所以发布新文件时也要考虑旧资源保留窗口。</p>
