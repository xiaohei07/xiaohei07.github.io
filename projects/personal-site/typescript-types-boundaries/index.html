本站前端文件中有不少.ts和.tsx。它们使用TypeScript，也就是在JavaScript的基础上增加类型表达和检查能力。.tsx还允许写JSX，用来描述React界面。

如果已经会JS，可以先从“函数期待收到什么、最后返回什么”开始看类型，不必一上来就研究很复杂的泛型。

一、给文章对象写清楚形状

ts
type Article = {
  id: string;
  title: string;
  tags: string[];
  date: string | null;
};

function articleLabel(article: Article): string {
  return `${article.title}（${article.tags.length}个标签）`;
}

string[]表示字符串数组；string | null允许日期是字符串，也允许明确没有日期。函数参数的类型告诉调用者应该传什么，返回类型说明结果是字符串。

这里没有把日期写成可选字段date?: string，是因为“字段不存在”与“字段存在，但日期暂时未知”可以表达不同含义。项目中是否需要区分它们，取决于数据约定。

如果把tags写成一个字符串，编辑器和类型检查就能提醒。类型检查发生在开发和构建阶段，编译后的浏览器代码主要仍是JS；类型标注不会自动变成运行时的检查语句。TypeScript基础类型可以作为这些写法的语法参考。

二、联合类型怎样限制状态

反馈类型只有三种，可以写成：

ts
type FeedbackKind = "correction" | "question" | "other";

type SubmitState =
  | { status: "idle" }
  | { status: "sending" }
  | { status: "success"; receiptId: string }
  | { status: "error"; message: string };

status让这几个对象有了明确区别。检查state.status === "success"之后，TypeScript知道当前分支有receiptId。这样可以减少“状态显示成功，但编号字段根本没有”的组合。它也让代码里应该处理哪些状态更清楚。类型收窄说明了检查条件怎样影响后续类型。

本站表单目前用多个useState变量表示等待、输入和提示。上面是另一种教学组织方式，不代表项目已经改成了这个联合状态对象。

三、泛型说明返回类型，却不会校验网络数据

查看图中细节

本站有这样的调用：

ts
const receipt = await apiRequest<{ id: string; status: string }>(
  "/feedback",
  { method: "POST", body: JSON.stringify(payload) },
);

尖括号中的类型传给了泛型参数T。调用者因此能获得属性提示，但目前apiRequest内部最后使用response.json() as Promise<T>，这个断言只告诉TypeScript按该类型处理结果。

假设服务器意外返回{"id": 12}，as不会把12变成字符串，也不会自动报格式错误。如果这个边界需要强保证，就应把未知输入先视为unknown，检查之后再使用：

ts
function isReceipt(value: unknown): value is { id: string; status: "pending" } {
  if (typeof value !== "object" || value === null) return false;
  return "id" in value && typeof value.id === "string"
    && "status" in value && value.status === "pending";
}

这个函数是教学示例，检查的是回执对象，不包含UUID格式等全部业务约束。生产代码若需要更严格的契约，还应明确字段格式、错误处理和兼容策略。

四、TypeScript与Pydantic为什么都需要

TypeScript帮助前端开发者在写代码时发现错误，Pydantic检查后端实际收到的数据。用户可以通过脚本直接发送HTTP请求，因此不能认为前端通过类型检查，后端就能省略校验。

数据库还有自己的约束。例如反馈状态的允许值、内容外键和消息长度，数据库也会检查。三者处在不同阶段：开发时约定、请求到达时校验、数据最终落库时约束。后两层会在Pydantic输入模型和PostgreSQL表与查询中展开。

TypeScript同样不能保证CSS布局正确、接口一定可用、查询足够快。本站同时执行typecheck、行为测试和实际浏览器检查，就是因为这些检查各自回答不同问题。

可以做一个很小的练习：把示例里的date直接传给只接受字符串的函数，再分别用条件判断和默认值处理。需要确定“未知日期是否应该展示”，再选择代码写法；不要仅为了让类型检查通过，就给每篇文章随意补一个今天的日期。
