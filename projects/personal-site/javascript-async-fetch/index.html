写过简单JS后，应该已经接触过函数、对象和事件。做前后端交互时，还需要补上Promise、async/await、模块和错误处理。这几个内容可以用一个完整过程串起来：点击按钮，等待接口返回，然后更新页面。

一、通过模块复用HTTP请求函数

本站把HTTP请求放在src/lib/api.ts，表单组件再导入其中的函数。简化成JS，结构如下：

js
// api.js
export async function readReceipt(url) {
  const response = await fetch(url);
  if (!response.ok) throw new Error(`HTTP ${response.status}`);
  return response.json();
}

// 页面模块
import { readReceipt } from "./api.js";

export声明模块对外提供的内容，import让其他模块引用这些内容。相对路径需要相对于当前模块理解；本站的@/lib/api则使用了工程配置的路径别名，浏览器并不会天然认识@。构建工具负责解析这类工程写法。

代码拆分的直接收益是，同一套超时与错误提示可以被多个组件复用。如果每个表单各自拼接口地址，后面修改API前缀就容易漏掉一处。

二、Promise表示尚未确定的异步结果

调用fetch()时，请求还没有完成，它先返回Promise。Promise表示尚未确定的异步结果，后续可能兑现为Response，也可能因为网络错误等原因被拒绝。await允许异步函数等到这个Promise完成，再继续执行后面的代码；等待期间，浏览器仍有机会处理其他任务。

js
async function loadTitle() {
  console.log("开始读取");
  const response = await fetch("/example.json");
  const data = await response.json();
  console.log(data.title);
}

这里有两次等待：第一次等待响应可用，第二次等待响应体读取完成并解析为JSON数据。async函数的返回值也会包装成Promise，因此调用者同样需要await或.then()取得结果。练习时，需要自行准备返回JSON的/example.json，或者把路径改成可访问的JSON资源。

需要注意，await不会把CPU密集计算自动移到另一个线程。如果等待结束后运行一个很长的同步循环，页面仍可能卡住。并行下载与并行计算也应分别考虑。

三、将成功、HTTP失败和网络失败分开

下面通过一个独立函数说明发送JSON和检查响应的过程。它会向指定地址提交反馈，练习时应使用自己的测试接口：

js
async function createFeedback(payload) {
  const response = await fetch("/api/v1/feedback", {
    method: "POST",
    headers: { "Content-Type": "application/json" },
    body: JSON.stringify(payload),
    signal: AbortSignal.timeout(15000),
  });
  if (!response.ok) {
    throw new Error(`请求没有成功：${response.status}`);
  }
  return response.json();
}

JS对象要先经过JSON.stringify变成JSON文本；请求头说明正文格式。接口返回422时，浏览器已经收到了HTTP响应，fetch通常会兑现为Response对象；response.ok为false，表示HTTP状态不在200—299的成功范围内，示例据此抛出错误。网络不可达、请求被中止等情况则可能直接使fetch返回的Promise被拒绝。Fetch官方参考对这些行为及请求选项有更完整的说明。

实际项目的apiRequest还统一处理503、401、403、429和422，不把服务端未经筛选的诊断文字直接显示给用户。204没有响应体，因此会单独返回，避免对空响应调用json()。

四、表单提交过程中的输入、等待与结果状态

一次提交至少有输入、等待、成功和失败几种状态。本站将等待标记放在busy里，并在finally恢复：

js
setBusy(true);
try {
  const receipt = await createFeedback(payload);
  setMessage("");
  setSuccess(`已收到反馈，编号：${receipt.id}`);
} catch (error) {
  setError("尚未确认发送成功，输入已保留。");
} finally {
  setBusy(false);
}

finally在成功和失败路径都会执行，因此可以统一把busy恢复为false，让表单结束等待。输入内容则按结果分别处理：确认成功后清空，失败时保留，方便用户继续修改或重试。这里的setMessage等函数来自React状态，具体含义见React状态与Effect。

15秒超时控制的是客户端愿意等待多久。 中止浏览器请求，不保证服务器事务也会同步取消。服务器可能已经提交，只是回执未到达，所以本站没有在这里自动重试POST。

五、请求依赖、并行等待与过时结果处理

如果请求B需要请求A返回的ID，就应该先等A，再发B。两个互不依赖的只读请求可以用Promise.all一起等待，但其中一个拒绝后，其他已经发出的请求不会自动取消；需要全部结果时，可以考虑Promise.allSettled。

搜索还有一种常见问题：用户先输入react，很快改成next，前一个请求却更晚返回。如果直接用每次返回的数据覆盖结果，就会显示过时内容。可以中止旧请求，也可以给请求标记序号，只接受当前序号的结果。上述情况适用于每次输入都会发起请求的搜索。本站站内搜索采用另一种方式：先加载静态索引，再在浏览器中匹配后续输入，因此每次输入不会产生新的服务端搜索请求。

继续追问时，可以把“异步”落实成三个问题：等待的是什么、谁能在等待期间继续工作、结果回来时还是否属于当前操作。比起只记住async/await的语法，这三个问题更有助于检查真实代码。
