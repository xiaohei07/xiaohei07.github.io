DeepSeek Export Plus需要在对话页面中增加导出按钮，读取用户选择的消息，再把整理好的内容交给各个格式的导出模块。为了完成这些操作，本项目使用了内容脚本、网页的MAIN环境和扩展后台，分别承担页面交互、网页数据读取和扩展操作的协调工作。

理解这几个执行位置，可以从一次导出操作开始：用户在网页上选择了一条回答，内容脚本先找到对应的页面元素，再请求后台读取这条回答所关联的数据。后台检查请求后，把读取函数放到网页环境中执行，最后把取得的数据返回给内容脚本。

下面先介绍这些执行位置，再沿着这条数据传递过程说明它们的协作方式。

一、扩展脚本的执行位置

1.1 内容脚本与页面元素

内容脚本（content script）是扩展放到网页中运行的脚本。它可以读取页面中的文字、查找按钮和图片，也可以增加元素、修改样式。本项目通过内容脚本显示导出入口、处理用户的选择，并收集页面上的消息内容。

浏览器会把HTML组织成一棵由元素构成的树，这棵树就是DOM。例如，一条回答中的段落、代码块和图片，都分别对应着DOM中的节点。内容脚本找到这些节点后，就可以读取其中的文字，或者在旁边增加一个导出按钮。

除了页面元素，网页程序还会保存一些用于运行的数据，例如消息属于哪个角色、一次工具调用返回了哪些网址，以及附件对应的下载地址。这些数据可能只保存在JavaScript对象中，页面上显示的文字通常只是其中的一部分。因此，收集页面文字和读取程序数据需要分别处理。

1.2 隔离环境与MAIN环境

Chrome扩展的内容脚本默认运行在ISOLATED环境中。ISOLATED表示隔离：内容脚本与网页脚本分别使用各自的JavaScript变量和对象，同时可以操作同一份DOM。

可以用一个简单的例子说明。假设网页中有以下内容：

html
<p id="message">你好</p>
<script>
  window.messageText = "网页保存的消息";
</script>

然后在扩展默认的内容脚本中执行下面的代码：

javascript
const node = document.querySelector("#message");

console.log(node.textContent);
console.log(window.messageText);

node.textContent = "已选中这条消息";

// 输出：
// 你好
// undefined

第一条输出来自页面元素，内容脚本可以通过DOM读取它，所以得到“你好”。第二条访问的是window.messageText，这个属性由网页脚本设置，内容脚本所在的隔离环境中没有这个属性，因此得到undefined。最后，内容脚本修改了节点的textContent，页面上的文字也会随之变成“已选中这条消息”。

这个例子的关键在于代码的执行位置：HTML中的脚本在网页环境中执行，第二段代码在扩展的隔离环境中执行。如果把两段JavaScript都放到网页控制台中运行，它们就使用了同一个环境，输出也会发生变化。

MAIN是网页脚本使用的JavaScript执行环境。在这个环境中读取window.messageText，就可以取得网页设置的“网页保存的消息”。本项目需要读取消息节点所关联的React数据时，会让一个读取函数进入MAIN执行。

React是DeepSeek网页使用的界面库，组件用于组织界面及其数据。组件和props的基础可以参考React组件与props。本项目自己的扩展界面使用原生JavaScript和CSS，通过MAIN读取DeepSeek页面上的相关数据。

MAIN与网页脚本共享环境，网页本身也可以修改其中的对象。因此，本项目在这里执行有限的数据读取，把请求来源和用户同意状态的检查交给扩展后台。读取范围还取决于网页提供了哪些可访问对象，函数内部未对外暴露的局部变量仍受JavaScript自身的作用域规则限制。

1.3 扩展后台的职责

扩展后台负责响应扩展事件、检查请求并协调操作。它运行在用户的浏览器中。本项目由后台检查消息发送者、向指定页面注入读取函数、处理允许读取的附件，以及管理打印所需的临时数据。

Chrome扩展通过manifest.json声明入口和权限。Manifest V3是这份清单及相关运行机制的第三版，它使用service worker作为后台脚本。后台会在收到扩展消息等事件时被唤醒，完成相应处理；浏览器也可能在它空闲时结束当前实例。

后台没有网页DOM，因此查找消息节点、显示按钮和调整页面样式，都需要由页面中的脚本完成。内容脚本找到节点后，再通过消息把需要后台处理的操作交过去。

扩展通过Chrome提供的API调用消息、存储和脚本注入等功能。API可以理解为程序调用现成功能的接口，后面会用chrome.runtime.sendMessage()说明消息接口的具体用法。这几个执行位置在本项目中的分工如下：

执行位置可以使用的主要对象或能力本项目承担的工作
内容脚本的ISOLATED环境页面DOM、扩展提供给内容脚本的消息等API显示导出入口、接收选择、收集页面内容
网页的MAIN环境网页的JavaScript对象及页面DOM读取消息节点关联的数据，观察符合范围的历史响应
扩展后台消息发送者信息、扩展注入和存储等API检查请求、协调读取、管理临时数据

二、消息传递与网页数据读取

2.1 发送请求和返回结果

消息传递是不同执行环境交换数据的方式。发送方把要执行的操作和参数整理成消息，接收方处理后，再把结果返回给它。

下面通过一次简单的发送和回复说明这个过程。

内容脚本：

javascript
async function askBackground() {
  const reply = await chrome.runtime.sendMessage({
    type: "example:ping"
  });

  console.log(reply.text);
}

askBackground();
// 输出：已收到

后台：

javascript
chrome.runtime.onMessage.addListener(
  (message, sender, sendResponse) => {
    if (message.type !== "example:ping") return;

    sendResponse({ text: "已收到" });
  }
);

内容脚本使用sendMessage()发送一个对象，其中的type表示这次消息的用途。后台的监听函数收到消息后，先检查type，再调用sendResponse()返回结果。内容脚本中的await等待回复完成，然后从回复对象中取出text并输出。

这次回复在监听函数中立即完成。如果后台需要先执行异步读取，再通过sendResponse()回复，可以让监听函数返回字面量true，使这个回调的响应通道继续保持打开。具体用法见Chrome消息传递文档，await的基础可以参考JavaScript异步与fetch。

消息中的数据通常使用字符串、数字、数组和普通对象。DOM节点属于页面中的对象，传递节点时需要换一种表示方法；本项目使用临时标记，让另一个执行环境能够重新找到同一节点。

2.2 页面中的结构化消息数据

结构化消息数据，就是网页程序按字段保存的消息信息。例如，可以把一条回答简化为下面的数据：

json
{
  "role": "assistant",
  "text": "可以参考以下资料。",
  "toolResults": [
    {
      "title": "资料标题",
      "url": "https://example.com/reference"
    }
  ]
}

这里的role表示回答者的角色，text保存正文，toolResults保存工具返回的资料标题和网址。字段名称为了讲解进行了简化，实际数据还会包含其他信息。

网页可能只显示正文和“已搜索”等提示，而把具体网址保留在程序数据中。如果只读取显示出来的文字，就缺少了这些网址。因此，本项目还会从消息节点关联的React内部对象中查找需要的数据。

本项目读取到的这类数据，来源是网页程序保存的消息对象；另一类可用数据来自后面介绍的历史响应。没有取得结构化消息对象，或对象解析失败时，提取模块才改从页面中已经显示的元素读取内容，再按元素的位置整理，这个处理就是DOM回退。对象解析成功后，程序直接使用解析结果；其中缺少思考或工具字段时，目前尚未实现从DOM逐项补齐。

有了这些具体对象后，后文中的“数据来源”就可以明确到某一种位置：是页面组件关联的数据、历史响应中的消息，还是DOM中已经显示的内容。

2.3 读取一条回答的完整流程

假设用户已经同意处理对话，并在当前页面中选择了一条回答。本项目取得这条回答所关联数据的过程如下：

  1. 内容脚本找到回答节点，添加临时标记。这个随机标记写在DOM节点的属性上，内容脚本和MAIN中的函数都能通过DOM看到它。
  2. 内容脚本把操作类型和标记发送给后台。后台收到消息时，还会取得Chrome提供的sender，其中包含消息来自哪个标签页、哪个frame以及对应的页面地址。
  3. 后台检查来源和用户同意状态。确认发送者来自允许的DeepSeek页面、操作符合要求，并记录这次读取开始时的授权代次。
  4. 后台向同一标签页、同一frame注入读取函数。通过chrome.scripting.executeScript()指定world: "MAIN"，使函数能够在网页环境中读取数据。
  5. 读取函数根据标记找到节点，提取需要的字段。它检查节点所关联的React数据，返回角色、正文片段、工具和附件等允许使用的信息。
  6. 后台再次检查授权，再返回结果。内容脚本收到有效数据后，把它交给会话提取模块继续整理，并清除节点上的临时标记；读取失败时也会执行相应清理。

其中，frame表示一个页面文档环境。一个标签页里还可能嵌入其他页面，每个页面都有自己的DOM。因此，后台需要使用发送者对应的标签页和frame，才能让读取函数在正确的位置找到目标节点。

临时标记负责定位节点，sender负责提供发送者信息，用户同意状态负责决定当前是否允许读取。它们分别解决了“读取哪个节点”“请求来自哪里”和“这次是否允许处理”这三个具体问题。

浏览器权限还提供了另一层前提。例如，扩展需要按Chrome的权限规则使用scripting能力，才能向页面注入函数；本项目则在拥有相应能力后，继续检查用户是否同意处理对话。用户可以在扩展的隐私设置页中管理这项同意。

三、数据读取范围与历史观察

3.1 有界遍历的作用

React内部对象可能包含多层状态，还可能出现循环引用。例如，对象A引用了对象B，对象B又引用了对象A。如果读取函数沿着所有引用一直查找，就可能重复访问相同对象，或者花费大量时间检查与导出无关的数据。

因此，本项目会记录已经访问过的对象，并设置遍历深度和检查数量上限。查找过程中只提取允许返回的消息字段，从而控制一次读取的工作量和数据范围。

例如，遇到某个对象时，函数先检查它的类型、当前深度以及是否已经访问过；已访问的对象会被跳过。数组和React内部状态链也各有检查上限。达到上限后，本次查找就会停止继续深入。

这些限制使读取过程具有明确的范围。对应的不足是：过深或超出检查数量的数据可能无法完整取得。并且，React内部对象的形状会受到网页实现影响，DeepSeek更新页面结构后，本项目仍可能需要调整读取方式。

3.2 历史响应的观察方式

除了读取当前页面中已经建立的消息节点，本项目还使用了历史观察脚本。用户同意后，后台会注册这个脚本，并给已经打开的DeepSeek页面补装。它运行在MAIN环境中，观察页面随后通过fetch和XMLHttpRequest取得的、符合范围的历史消息响应。

fetch和XMLHttpRequest是网页发起网络请求的两种方式。历史观察脚本会包装这些请求函数，并保留原有调用行为：fetch分支克隆响应后解析，XHR分支监听请求完成事件后读取响应，再把允许保存的消息字段写入当前会话缓存，供后续导出使用。

缓存可以理解为临时保存的数据。比如，网页加载历史对话时取得了一批消息，观察脚本把符合要求的内容暂时保存起来，后续提取时就可以利用这批已有数据。

请求经过已经安装的包装器后，历史观察脚本才能处理对应响应。例如，页面先发出请求A，随后安装了观察脚本；A后来返回时，仍沿原来的调用过程结束。页面再发出请求B，B经过新的包装器，符合范围的响应就可以被观察。安装前已经发出的请求，需要页面重新请求后才有新的观察机会。本项目通过页面自身的请求获取历史数据，没有额外发起带用户认证的完整历史拉取。

当前节点读取适合取得眼前消息的数据，历史观察适合保留页面后续加载的数据。两种方式的调用时间和数据来源各有侧重。缓存本身还受到数量和长度限制，切换会话、重新生成等操作也需要使相关旧缓存失效。

四、独立页面与打印会话

4.1 后台生命周期与临时存储

前面介绍过，后台service worker可能在空闲时被浏览器结束。之后有新的事件到达时，浏览器会启动新的实例，普通全局变量也会重新初始化。

打印预览需要跨越两个操作：先准备好正文，再打开打印页读取它。如果把正文只保存在后台的一个全局Map中，那么后台实例结束后，这份Map中的数据也会丢失。打印页稍后再读取时，就可能找不到刚才准备的内容。

Map是一种按照键查找值的容器。在这个例子中，会话ID作为键，打印正文作为值。问题出在这份容器只属于当前后台实例，所以本项目把打印会话保存到了storage.session中。

storage.session是Chrome扩展提供的会话存储。它保存的数据可以跨后台实例的回收继续使用，适合正文准备完成后、打印页稍后再读取的过程。

本项目通过随机会话ID关联打印内容，并设置过期清理和大小预算；所选附件会保存到该次会话的白名单中，后台处理附件请求时再检查它是否属于这份名单。这样，打印页能够找到本次导出的内容，临时数据也有明确的使用范围和清理条件。

扩展重载、更新、禁用或浏览器重启时，storage.session中的数据会被清除。因此，准备长期保留的对话需要下载为文件，打印会话只承担这次预览过程中的临时保存。平台提供的存储类型及生命周期可以参考Chrome storage文档。

4.2 隐私设置页与打印预览页

扩展的独立页面有自己的HTML、样式和脚本，可以显示界面并处理用户操作。本项目主要使用了两类页面：

  • 隐私设置页：说明数据处理方式，让用户管理是否同意处理对话，并把选择保存为扩展中的授权状态。
  • 打印预览页：从storage.session读取本次会话，渲染正文和附件信息，再调用浏览器的打印功能。用户可以在打印对话框中选择“另存为PDF”，保存得到的文件。

这两类操作都需要DOM来显示和组织内容，所以由独立页面承担。后台负责打开页面、准备所需数据及相关检查。

4.3 Word与PNG使用的临时iframe

iframe是页面中嵌入的另一个文档。它可以使用自己的样式和宽度，适合为导出内容建立临时的排版区域。

本项目导出Word或PNG时，会创建一个受限制的iframe，把经过HTML净化的正文放进去，再准备本地字体和图片。净化会过滤不允许的HTML内容。iframe的sandbox属性用于限制其中允许执行的操作，本项目只保留allow-same-origin，使外层导出代码能够访问这个同源文档并测量内容，脚本执行等能力继续受到限制。

图片解码、字体准备完成后，导出模块再测量尺寸并执行对应的转换或绘制；完成或取消后，临时iframe会被移除。

这样的处理让导出内容拥有相对独立的排版环境，便于按照导出尺寸处理文档。与此同时，布局测量和部分同步绘制仍然会占用页面线程，较长内容的处理可能影响页面响应。实际采用的线程与渲染方式，决定了这部分工作的性能边界。

五、构建入口与依赖加载

5.1 多个入口的组成原因

内容脚本由网页加载，后台由扩展事件唤醒，隐私页和打印页则各自打开一个文档。它们的启动位置和需要处理的对象不同，因此构建时也需要生成各自能够加载的入口文件。

本项目使用esbuild完成打包。esbuild会整理源文件及依赖，为内容脚本、历史观察脚本、后台、独立页面和按需导出模块生成相应文件。

5.2 按需加载与静态依赖

Word和PNG共用一个按需加载的导出包。用户选择相关格式后，扩展才动态加载这个包，再根据选择执行对应的导出分支。

这个共享包中包含docx和html2canvas：前者用于生成Word文档，后者用于把页面内容绘制到画布。由于它们放在同一个包中，选择其中一种格式时，也会加载这份共享包所包含的代码。

其他依赖按照实际导入关系加载。例如，marked负责解析Markdown，DOMPurify负责净化HTML，KaTeX负责显示公式；它们已经通过静态依赖链进入相关构建入口。因此，判断某个库的加载时间，需要查看它被哪个入口导入、采用什么导入方式，再与界面实际显示的时间分别对应起来。

六、授权撤回与扩展更新处理

6.1 授权代次与过期结果

读取操作需要一定时间。在请求发出后、结果返回前，用户可能撤回同意，也可能再次同意。后台需要判断返回的数据是否仍属于当前有效的那次授权。

为此，本项目使用了授权代次。可以把它理解为授权状态的一次版本编号：开始读取时保存当前编号，读取结束后再与最新编号比较。

例如，某次读取开始时记录的是第3代授权。等待期间，用户撤回了同意，然后重新同意，授权编号已经发生变化。此时即使用户再次处于同意状态，第3代请求返回的数据仍属于旧授权，后台会拒绝继续使用这份结果。

所以后台在异步操作前后都会检查同意状态和授权代次：前者确定现在是否允许读取，后者确定这份结果是否属于当前授权。

6.2 超时与撤回的处理范围

本项目给单次元数据读取设置了5秒等待上限。超过等待时间后，调用方进入后续回退处理，继续尝试取得可用内容。

这里需要区分等待和执行：计时结束可以让调用方停止等待，但已经注入到MAIN中的函数可能还在执行。因此，迟到的结果仍需检查授权状态和代次；对于支持中止的读取，则通过相应取消机制减少后续工作。更完整的时序可以参考任务取消与过期结果。

用户撤回同意时，本项目还会清理已经开始的工作：

  1. 注销历史观察脚本的动态注册，停止后续按该规则注入。
  2. 通知已打开页面中的观察脚本停止，恢复它包装的请求函数，并清理缓存。
  3. 中止后台登记的待处理读取，清理打印会话，并拒绝随后返回的旧授权结果。

动态注册决定了脚本以后何时注入，已经在页面中运行的实例则需要单独停止。因此，注册清理和运行实例清理都包含在撤回流程中。

6.3 扩展更新后的页面恢复

扩展更新或重新加载后，原来打开的网页中可能还留着旧内容脚本。它连接的扩展上下文已经失效，继续调用旧扩展API时，就可能出现异常。

本项目识别这种失效后，会停止旧界面的工作、清理相关状态，再显示刷新提示。提示通过页面DOM显示，刷新操作使用页面自身的location.reload()。这样，即使旧扩展连接已经失效，用户仍然可以按提示刷新网页。

网页重新加载后，当前版本的内容脚本会再次进入页面，恢复与扩展的连接。其他下载或读取错误则继续按各自的错误类型处理，让提示与实际发生的问题对应。
