拾程要处理的事情可以连成一条线：取得通知，整理信息，形成候选，人工确认，必要时提醒。但这条线不应该全部塞进一个模型请求，也不需要每一步都增加一个常驻服务。

项目面对的是资源有限、同时运行其他服务的个人云主机。我的需求是先把固定流程做好，能从手机查看，也能在本机处理较复杂的微信材料。因此它采用原生网页、Python API、SQLite和直接模型调用，把业务状态留在服务器，将批量微信处理放在本机，邮件用独立短时任务执行。

一、先看完整的数据流

text
手机或网页提交文字、链接、图片
  → API收件 → 持久任务 → 服务端串行提取
  → 校验与保存候选

本机选定微信记录
  → Tulpa导出 → 上下文、网页和图片处理
  → 本机模型提取 → 缓存、归并与结构化结果同步
  → 服务端再次校验与保存候选

候选与来源 → 人工筛选、确认 → 日程或招聘资料
已确认且单独授权的精确时间日程
  → 提醒账本 → 独立邮件任务 → SMTP结果

两条入口共享后面的业务规则，却不共享同一种执行过程。本机结果到达/v1/local-results后，服务端做校验和落库，不再调用一次模型；手机提交原始材料，则进入服务器的任务队列。

本机同步会包含需要的材料和来源，不能把“本机提取”理解为原文绝不离开电脑。它改变了复杂处理发生的位置，也让流程依赖本机已经同步的微信记录与相应工具。

二、页面、API与数据库分别承担什么

组成工具做什么
网页界面HTML、CSS、原生JavaScript显示收件、候选与日程，管理筛选和多选，发送操作请求
HTTP入口FastAPI、Uvicorn接收请求、认证、路由、调用业务逻辑并返回结果
持久状态SQLite与Python标准库sqlite3保存材料、任务、候选、来源、修订和邮件账本
模型适配HTTPX与MiniMax接口提交文字和图片，读取完整响应，进行自定义结果校验
任务组织asyncio、线程执行器和项目任务代码串行领取服务端任务，把阻塞处理转交线程
运行与提醒systemd、Nginx、SMTP管理服务、HTTPS入口、定时唤醒邮件脚本与提交邮件

Uvicorn负责运行ASGI应用，FastAPI负责组织接口；更完整的请求过程可以直接看FastAPI请求链。这里没有Next.js、React或Vue前端，也没有SQLAlchemy ORM。数据库操作使用原始参数化SQL，模型调用使用HTTPX直接请求，没有另加模型SDK或Agent框架。

providers是项目自己的模型适配模块，jobs负责处理任务，domain负责业务状态改变，storage负责数据库连接与事务。这些名称描述本地代码职责，不是额外部署的四个产品。

三、为什么把数据分成几个对象

对象保存内容为什么不能混在一起
materials，材料原文、链接、时间、附件与缺失说明保留提取依据，一份材料可能包含多个事项
reviews，待确认项候选、疑点和处理状态提取结果还没有获得用户确认
events，日程已确认安排、时间、地点和版本需要修改、取消与提醒规则
opportunities，招聘资料企业、岗位等信息不一定有线下地点，也不一定要建立日程
来源关联材料与候选、日程的对应关系多份转发可以指向同一事项
reminder_outbox，提醒账本发送意图、期限与结果邮件状态不能由“材料处理完成”推导

假设一份汇总包含三家公司，它可以产生三项候选；同一活动被三个群转发，又可能只对应一项日程。材料数、候选数和日程数因此不应强行一致。保留关联，才能在用户质疑时间时找到具体依据。

四、本机工具怎样接上服务器

Tulpa是已经存在的微信记录工具。拾程主增量流程调用它的导出CLI，明确账号、群和时间范围，再处理导出结果；补取特定媒体的脚本另通过受限MCP接口工作。这不是模型自主选择工具，也不是自行实现微信协议。

本机流程使用PowerShell入口启动项目Python环境，依次完成增量筛选、上下文组材、网页与图片补充、提取、归并和同步。网页读取使用受限制的HTTP与HTML处理，不运行目标网页脚本；Pillow校验图片文件和尺寸，招聘内容由远程模型理解，Pillow本身不是OCR引擎。

每个阶段保留缓存和进度。这样一组图片里前半部分成功、后半部分失败时，可以按规则复用已完成结果，不必把全部内容当成从未处理。具体预算单位仍要区分，见模型提取与调用预算。

五、串行处理与独立邮件为什么这样组合

API的生命周期中有一个任务循环，一次等待一个run_one完成，再领取下一个。同步工作通过asyncio.to_thread进入线程，事件循环仍能处理其他请求。单Web worker、串行提取与只有一条线程是不同概念。

SQLite记录任务状态，网络请求放在写事务外，返回后再用令牌、租约与材料版本核对。对于当前个人工具，这减少了常驻组件，也让失败状态集中可查；代价是处理量上来会排队，写事务仍会竞争，不能把轻量等同于无限扩展。

邮件则由systemd timer每分钟唤醒独立脚本，直接扫描数据库账本，不依赖模型或者API请求正在运行。它仍依赖主机、数据库和SMTP可用，因此这是一种故障范围的分离，不是另一台高可用机器。

六、如果从头搭一个类似项目

可以先完成一条最小业务线：提交文字、保存材料、提取候选、人工确认、查看日程。确认对象与状态稳定后，再加入本机批量输入、图片分组和增量游标；最后增加邮件与恢复，检查重复执行和外部结果不确定时怎么办。

通用HTTP、FastAPI、SQL和安全前置直接使用已有博客；SQLite事务与ICS日历格式补本项目新增知识。阅读模块时重点看每一步交给下一步什么，而不是试图记住所有文件名。

项目还没有Redis、独立消息队列、向量聚类或持续日历同步。未来如果负载和使用方式变化，应先观察真实瓶颈，再决定是否引入这些组件；增加技术栈数量本身不构成功能改善。
