拾程的主要流程是取得通知、整理信息、形成候选、人工确认，再按需要发出提醒。其中，模型负责提取信息，业务程序负责校验和保存，用户负责确认安排，独立邮件任务负责发送提醒。各部分通过明确的数据和状态连接起来。

项目面对的是资源有限、同时运行其他服务的个人云主机。我的需求是先把固定流程做好，能从手机查看，也能在本机处理较复杂的微信材料。因此它采用原生网页、Python API、SQLite和直接模型调用，把业务状态留在服务器，将批量微信处理放在本机，邮件用独立短时任务执行。

一、完整数据流与两条入口

text
手机或网页提交文字、链接、图片
  → API收件 → 持久任务 → 服务端串行提取
  → 校验与保存候选

本机选定微信记录
  → Tulpa导出 → 上下文、网页和图片处理
  → 本机流程调用模型提取 → 缓存、归并与结构化结果同步
  → 服务端再次校验与保存候选

候选与来源 → 人工筛选、确认 → 日程或招聘资料
已确认且单独授权的精确时间日程
  → 提醒账本 → 独立邮件任务 → SMTP结果

两条入口共享后面的业务规则，执行过程则各自独立。本机结果到达/v1/local-results后，服务端对结果做校验和落库，不再调用模型；手机提交的原始材料则进入服务器的持久任务队列，由服务端串行提取。

本机同步会包含处理所需的材料和来源，部分原文会随结果离开电脑。本机流程改变的是复杂处理发生的位置，也让整个流程依赖本机已经同步的微信记录与相应工具。

二、页面、API与数据库的职责划分

组成使用工具承担的工作
网页界面HTML、CSS、原生JavaScript显示收件、候选与日程，管理筛选和多选，发送操作请求
HTTP入口FastAPI、Uvicorn接收请求、认证、路由、调用业务逻辑并返回结果
持久状态SQLite、Python标准库sqlite3保存材料、任务、候选、来源、修订和邮件账本
模型适配HTTPX、MiniMax接口提交文字和图片，读取完整响应，自定义校验结果
任务组织asyncio、线程执行器、项目任务代码串行领取服务端任务，把阻塞处理转交线程
运行与提醒systemd、Nginx、SMTP管理服务、提供HTTPS入口、定时唤醒邮件脚本并提交邮件

Uvicorn负责运行ASGI应用，FastAPI负责组织接口；ASGI是Python异步Web应用与服务器之间的接口约定，更完整的请求过程可以看FastAPI请求链。前端使用HTML、CSS和原生JavaScript；数据库访问使用标准库sqlite3和参数化SQL；模型请求由HTTPX直接发往MiniMax接口。这套组合把页面、数据和模型调用所需的组件集中在较少的运行单元中，适合当前个人工具的维护需求。

providers、jobs、domain、storage是Python项目中的代码模块名称。其中，providers负责模型适配，jobs负责任务处理，domain负责业务状态改变，storage负责数据库连接与事务。阅读源码时，可以根据需要追踪的功能找到对应模块。

三、材料、候选、日程与招聘资料的分层保存

对象保存内容分开保存的原因
materials，材料原文、链接、时间、附件与缺失说明保留提取依据；一份材料可能包含多个事项
reviews，待确认项候选、疑点和处理状态提取结果尚未经过用户确认
events，日程已确认安排、时间、地点和版本后续需要修改、取消并参与提醒
opportunities，招聘资料企业、岗位等信息不一定有线下地点，也不一定转成日程
来源关联材料与候选、日程的对应关系多份转发可以指向同一事项
reminder_outbox，提醒账本发送意图、期限与结果邮件状态独立于材料处理，需要单独追踪

假设一份汇总包含三家公司，它可以产生三项候选；同一场活动被三个群转发，又可能只对应一项日程。材料数、候选数和日程数因此不需要一致。保留来源关联后，用户质疑时间时，可以回到具体材料核对依据。

四、本机微信材料的处理流程

Tulpa是已经存在的微信记录工具。拾程主增量流程调用它的导出CLI，明确账号、群和时间范围，再处理导出结果；补取特定媒体的脚本另通过受限MCP接口工作。工具选择和调用顺序由本机流程固定，微信数据的取得依赖Tulpa已有的导出能力，项目没有自行实现微信协议。

本机流程使用PowerShell入口启动项目Python环境，依次完成增量筛选、上下文组材、网页与图片补充、提取、归并和同步。网页读取使用受限制的HTTP与HTML处理，目标网页的脚本不会在这个阶段执行；Pillow校验图片文件和尺寸，招聘内容交给远程模型理解，Pillow只负责图片文件与尺寸检查。

每个阶段保留缓存和进度。一组图片里前半部分成功、后半部分失败时，流程可以按规则复用已完成结果，不必把全部内容当成从未处理。具体预算单位仍要区分，见模型提取与调用预算。

五、串行任务与独立邮件任务的组合原因

API以单Web worker运行，生命周期中有一个任务循环，一次等待一个run_one完成，再领取下一个。同步工作通过asyncio.to_thread进入线程，事件循环仍能处理其他请求。单Web worker、串行提取和线程执行属于三个不同层面：worker决定API进程数，任务循环决定同时领取多少任务，线程执行器负责把阻塞调用移出事件循环。

SQLite记录任务状态。网络请求放在写事务外，返回后再用令牌、租约与材料版本核对是否仍可落库。对当前个人工具，这种组合减少了常驻组件，失败状态也集中在数据库中可查。处理量上来后，任务会排队，写事务仍会竞争，因此这套结构适合当前负载，扩展能力有明确上限。

邮件由systemd timer每分钟唤醒独立脚本，脚本直接扫描数据库账本，不依赖模型或API请求是否正在运行。它仍依赖主机、数据库和SMTP可用，这种组合分离的是故障范围，不构成高可用部署。

六、类似项目的最小搭建顺序

可以先完成一条最小业务线：提交文字、保存材料、提取候选、人工确认、查看日程。确认对象和状态稳定后，再加入本机批量输入、图片分组和增量游标；最后增加邮件与恢复，并检查重复执行、外部结果不确定时的处理。

通用HTTP、FastAPI、SQL和安全前置可以参考已有博客；SQLite事务与ICS日历格式补本项目新增知识。阅读模块时，重点看每一步交给下一步什么；文件名可以按需再查。

当前方案围绕固定处理流程、持久状态和失败恢复组织。以后负载变化时，可以先观察排队长度、数据库等待和资源占用，再决定需要扩展哪一部分。
