拾程需要保存候选、人工决定和邮件账本，但使用规模不要求一开始就维护独立数据库服务。因此项目采用SQLite：数据库引擎嵌入应用，数据保存在文件中，Python通过标准库sqlite3访问。

表、约束和事务的基础可以先看关系表与SQL以及事务与锁。本篇只展开SQLite在拾程中的实际差异，不把PostgreSQL行锁或MySQL的MVCC机制套进来。

一、一次确认为什么需要一个事务

确认候选不是只改一个状态。可能要创建日程，关联来源，保存修订，再把候选标为已处理；若用户另行启用邮件且条件满足，还需要保存提醒意图。

假设前三步成功，最后一步失败，如果每步都单独提交，就可能出现日程已经存在、候选仍然等待确认的半套结果。事务将这些相关修改组织为一次提交：成功后一起保留，失败时回滚这组修改。

数据库只能维护已经写出的约束，不能判断用户是否真的想参加。事务也无法撤回已经送到远程邮件服务器的正文，所以确认落库与实际发信仍要分开。

二、DELETE回滚日志与WAL是不同机制

拾程显式使用journal_mode=DELETE。数据库以页为单位管理数据，回滚日志保存修改前所需的页信息，未完成提交时可以恢复旧状态；完成提交后删除日志。可以对照SQLite原子提交说明。

WAL则把变更追加到单独日志，再通过检查点合入数据库文件。它是另一种可选模式，不能因为看见SQLite就默认项目使用WAL，也不能将MySQL的redo/undo过程直接搬过来。

项目连接启用外键，设置有限的忙等待和synchronous=FULL，并由程序显式管理事务。FULL强调相应同步策略，但硬件、文件系统与实际故障仍是持久性条件，不能写成任何断电或存储损坏都不会丢数据。

三、BEGIN IMMEDIATE提前争取写入资格

SQLite可以有多个连接，但同一时刻只允许一个写事务。BEGIN IMMEDIATE在事务开始时尝试取得写入资格；另一个写者可能等待，也可能在超过等待条件后得到busy。规则见SQLite事务文档。

拾程使用isolation_level=None，再明确执行BEGIN、提交或回滚。这里对应现有Python接口的使用方式，不需要套用另一版Python新增的事务参数。

阶段是否持有写事务原因
领取任务、写令牌和预算是，尽量短这些状态需要共同改变
请求模型或SMTP否远程等待不应占住数据库写入资格
核对令牌、版本并保存结果是，尽量短防止旧结果覆盖新状态

这两段事务之间不是空白：材料可能被修改，任务租约可能过期，因此返回时必须重新检查条件。网络操作移出事务提高了其他写入可进行的机会，也要求更清楚的状态协议。

四、有写锁为什么仍需要版本检查

手机打开日程时版本是3，电脑随后修改到4。手机晚一点取得写锁，不代表它手里的内容也变成了4；如果直接覆盖，仍然会丢掉电脑刚才的修改。

下面是缩小的教学SQL，用于表达条件更新，不是生产完整语句：

sql
UPDATE events
SET location = ?, revision = revision + 1
WHERE id = ? AND revision = ?;

最后一个参数是用户读取时的预期版本。若匹配行数为0，就要检查记录是否已删除或版本是否变化，不能仍返回“修改成功”。问号表示绑定参数，不通过拼接用户输入生成SQL。

唯一约束解决另一件事：同一个业务键不能被插入两次。例如提醒账本用活动、场次、时间版本和提醒类型等字段表达一次意图。锁、版本条件与唯一约束各管一层，不是任意一个都能替代另外两个。

五、批量操作怎样保留单项结果

一次选择A、B、C三项，其中B已经被另一端处理。项目可以在外层事务中为每项建立SAVEPOINT：A成功，B遇到已知业务冲突时回退到自己的保存点，C继续；最终由外层事务决定是否提交。

SAVEPOINT是事务里的局部回退位置。释放它不代表那一项已经独立持久提交；如果后面出现未知异常，外层事务仍可能整体回滚。具体语义见SQLite SAVEPOINT。

这让界面可以解释“哪些项完成、哪些项需要刷新”，但不能借批量操作跳过分类、版本、邮件授权等业务检查。具体场景见人工确认与恢复。

六、什么时候需要重新评估选择

当前方案适合单主机、低写入并发和少组件的个人工具。若长期读事务或大量写入造成锁等待，应先记录耗时和冲突位置，再评估WAL或独立数据库；不能只改日志模式就承诺所有性能问题消失。

对这个项目而言，先把网络等待移出写事务、让更新带上前提、用约束表达不可重复的意图，比先增加数据库种类更直接。备份时则使用SQLite backup接口并检查数据库与原件，见备份、导出与回退。
