27:T148f,<p>拾程的输入既可能是一段手工粘贴的通知，也可能是本机选定的微信记录、公众号链接和海报。材料入口需要先把这些内容组织成可处理对象，后面的模型才有机会理解“这句话补充的是哪一份通知”。</p>
<p>这里的材料是一次提取所使用的文字、链接、图片、发布时间和缺失说明，不等同于一项日程。原始微信记录由既有Tulpa工具导出；拾程处理明确选定的结果，不自行实现微信协议。</p>
<h2 id="section-一手机收件与本机微信处理走不同路径">一、手机收件与本机微信处理走不同路径</h2>
<p>从用户看，两条入口最终都能得到待确认内容；从实现看，模型在哪里调用、进度怎样保存并不相同。</p>
<div class="code-block"><div class="code-toolbar"><span>text</span><button type="button" data-copy-code="true" aria-label="复制代码">复制代码</button></div><pre><code class="hljs language-text">手机或网页主动提交
  → 服务器接收材料 → SQLite处理任务 → 串行调用模型
  → 校验结果 → 保存候选和来源

本机选定微信导出
  → 增量筛选 → 上下文与网页图片处理 → 本机调用模型
  → 校验、归并与缓存 → 向服务器提交结构化结果
  → 服务端再校验 → 保存候选和来源

候选 → 人工确认或筛选 → 日程/招聘资料
已确认日程 + 单独邮件授权 → 提醒账本 → 独立邮件任务
</code></pre></div>
<p>第二条路径通过<code>/v1/local-results</code>接收结果，<strong>不会在服务器重复调用一次模型</strong>。复杂网页图片与批量微信材料主要在本机处理，云服务器接收结果并维护业务状态。这减少了服务器承担的解析工作，但桌面流程也因此依赖本机已同步记录和相应工具，不能写成无人值守的微信持续采集。</p>
<h2 id="section-二相邻消息可以一起理解不等于同一项活动">二、相邻消息可以一起理解，不等于同一项活动</h2>
<p>考虑同一人在一个群里的三条消息：10:00分享甲公司链接，10:02补充“这个岗位主要招后端”，10:03又分享乙公司链接。前两条放在一起，有助于理解岗位；第三条则应当作为另一份材料处理。</p>
<p>项目的消息合组函数<code>contextualize</code>按同发送人、同会话、相邻不超过600秒等条件尝试合组，同时限制条数和字符量。如果新旧两边都含链接而链接集合不同，就停止相邻合组；明确的招聘汇总也不套用普通相邻规则。合组文本保留各条原发布时间和发布人，让模型看到消息之间的关系。</p>
<p>这些条件是<strong>上下文线索</strong>，不是活动身份。提供了共同上下文后，模型仍需按企业和事项拆分；后续还要判断是否为同一场。时间接近不能证明企业相同，企业相同也不能证明两场活动相同。</p>
<h2 id="section-三网页图片补充在本机不应套到全部服务器收件">三、网页图片补充在本机，不应套到全部服务器收件</h2>
<p>有些文章的关键信息都在海报里，单取正文会很少甚至为空。本机流程从页面图片属性读取地址，检查实际格式、尺寸和哈希，再按限制串行分组提交模型。每部分保存状态，缓存键还包含文本、原发布时间、模型和提示版本，减少复用旧规则结果的风险。</p>
<p>云服务器普通URL收件主要进行受限正文获取，并不因此拥有完整网页图片处理能力。需要登录、依赖脚本展示或限制访问的页面仍可能失败；缺失要明确留下，不能把未读到内容写成已确认没有内容。</p>
<h2 id="section-四来源要跟着具体事项走">四、来源要跟着具体事项走</h2>
<p>一份汇总里可能有甲、乙、丙三家企业，不能把三个链接都挂到每一项下面。项目在提取、合并和保存时保留来源关联，让用户能从某项候选回到它对应的通知。</p>
<p>这也是材料与事项分表的原因：一份材料可以产生多项候选，多份转发也可以对应同一场活动。关联表记录这些对应关系。只把一段总结放进数据库，虽然看起来更简单，却会失去后续判断“这个时间究竟从哪一条消息来的”的依据。</p>
