拾程的输入可能是一段手工粘贴的通知，也可能是本机选定的微信记录、公众号链接和海报。材料指一次提取所使用的文字、链接、图片、发布时间和缺失说明；它保存的是理解通知的依据，日程则是用户确认后形成的安排。原始微信记录由已有的Tulpa工具导出，拾程只处理明确选定的导出结果，不自行实现微信协议。

一、手机收件与本机微信处理走不同路径

从用户看，两条入口最后都会得到待确认内容；实现上，模型在哪里调用、进度保存在哪里并不相同。

text
手机或网页主动提交
  → 服务器接收材料 → SQLite处理任务 → 串行调用模型
  → 校验结果 → 保存候选和来源

本机选定微信导出
  → 增量筛选 → 上下文与网页图片处理 → 本机调用模型
  → 校验、归并与缓存 → 向服务器提交结构化结果
  → 服务端再校验 → 保存候选和来源

候选 → 人工确认或筛选 → 日程/招聘资料
已确认日程 + 单独邮件授权 → 提醒账本 → 独立邮件任务

第二条路径把结构化结果提交到/v1/local-results，服务端校验并保存这些结果，不再为同一份材料排一次模型任务。复杂网页和批量微信材料主要在本机处理，云服务器接收结果并维护业务状态。这样分担了服务器的解析工作；桌面流程因此依赖本机已同步的记录和相应工具，不能当成无人值守的微信持续采集。

二、相邻消息可以一起理解，活动身份另外判断

考虑同一人在一个群里的三条消息：10:00分享甲公司链接，10:02补充“这个岗位主要招后端”，10:03又分享乙公司链接。前两条一起看有助于理解岗位；第三条应当作为另一份材料处理。

项目的消息合组函数contextualize按同发送人、同会话、相邻不超过600秒等条件尝试合组，同时限制组内条数和字符量。新旧两边都含链接而链接集合不同时，合组停止；“就业小闹钟”“招聘汇总”这类明确的汇总消息也不套用普通相邻规则。合组文本保留各条消息的原发布时间和发布人，模型能看到消息之间的先后关系。

这些条件为模型提供相邻消息的上下文。合组后，模型继续按企业和事项提取候选；两份材料是否对应同一场活动，则由活动归并规则比较企业、标题、日期、地点、城市和场次。相邻消息的组织与后续活动匹配因此分别使用各自需要的依据。

三、网页图片补充在本机完成

有些文章的关键信息都在海报里，只取正文会很少甚至为空。本机流程从页面的data-src、data-original和src属性读取图片地址，检查图片的实际格式、尺寸和哈希，把通过检查的图片放进有界缓存。图片数量超过单请求上限时，流程按限制串行分组提交模型，每个分组分别记录started、done、failed状态。分组缓存键包含正文、原发布时间、图片哈希、模型和提示版本，规则或内容变化后会生成新的缓存记录。

云服务器的普通URL收件主要做受限正文获取，并不因此拥有完整的网页图片处理能力。需要登录、依赖脚本展示或限制访问的页面仍可能失败；抓不到正文或原图时，程序保留明确的缺失说明，不把未读到的内容写成“已经确认没有活动”。

四、来源跟着具体事项走

一份汇总里可能有甲、乙、丙三家企业，不能把三个链接都挂到每一项下面。项目在提取、合并和保存时保留来源关联，用户可以从某项候选回到它对应的通知，核对时间、地点和企业名称。

材料与事项因此分表保存：一份材料可以产生多项候选，多份转发也可以对应同一场活动，关联表记录这些对应关系。只把一段总结放进数据库，看起来更简单，却会失去后续判断“这个时间究竟从哪一条消息来”的依据。

五、网页读取的地址与资源约束

读取用户提供的URL时，项目限制协议为HTTP/HTTPS、端口为80/443，拒绝带嵌入账号的地址；DNS解析出的全部地址都要检查，连接时使用已校验的具体地址，HTTPS仍按原域名校验证书；每次重定向都重新检查目标。响应在传输中和解压后的大小分别受限，并设有总时限。safe_url是项目内封装的受限网页读取模块，这些检查由本项目代码执行。

SSRF、DNS变化与连接地址之间的关系可以参考网页读取安全讲解。读取失败时，拾程会保留缺失说明，再交给模型提取模块处理，让后续结果带着实际取得材料的范围进入确认流程。
